시작

1단계: 프로젝트 기술 스택 선정 및 아키텍처 구상
강의 진행 중 화자는 복잡한 기술 대신 본인에게 익숙하고 빠르게 MVP (Minimum Viable Product, 최소 기능 제품: 시장의 반응을 빠르게 확인하기 위해 핵심 기능만 구현한 최소한의 제품)를 만들 수 있는 기술들을 선택합니다. 어떤 기술을 왜 선택하고 제외했는지 그 이유를 살펴보겠습니다.

백엔드 프레임워크 (Django 선택):

화자는 Fatsia (Fast Application Programming Interface, 속도가 매우 빠르지만 구조가 가벼운 파이썬 웹 프레임워크)나 Elixir (일렉서), Phoenix (피닉스: 대규모 동시 접속 처리에 강점이 있는 프로그래밍 언어와 웹 프레임워크) 같은 신생 혹은 이색적인 기술 대신 Django (장고: 파이썬으로 웹사이트를 빠르고 안전하게 만들 수 있도록 도와주는 대표적인 서버 프로그램)를 선택했습니다.

이유: 이미 장고를 다룬 경험이 많고, 자신이 가장 잘 아는 기술이기 때문에 최소 기능 제품을 가장 빠른 시간 안에 완성할 수 있기 때문입니다. 화자가 운영하는 교육 플랫폼이나 커뮤니티(AI Shipping Labs) 역시 장고 기반으로 구축되어 있습니다.

데이터베이스 (PostgreSQL 선택):

데이터베이스는 안정적이고 널리 쓰이는 PostgreSQL (Postgre Structured Query Language, 안정성과 성능이 뛰어나 기업이나 서비스에서 가장 널리 사용하는 신뢰성 높은 데이터베이스 관리 시스템)을 선택했습니다.

프런트엔드 (Django 템플릿 + Alpine.js):

복잡한 프런트엔드 프레임워크 대신 Django 템플릿과 Alpine.js (알파인 자바스크립트: 복잡한 도구 없이 HTML 태그 안에서 간단하게 자바스크립트 기능을 구현할 수 있게 해주는 가벼운 프런트엔드 도구) 조합을 선택하여 불필요한 복잡성을 낮추고 빠르게 개발하고자 합니다.

인증 시스템 (범위 축소):

초기 구현에서는 복잡한 이메일 인증 링크 발송 기능 등을 과감히 제외(Scope cutting, 범위 축소: 정해진 시간 안에 개발을 끝내기 위해 욕심부리지 않고 꼭 필요한 기능만 남겨두고 나머지는 과감히 빼는 과정)하기로 결정했습니다. 이메일 백엔드나 인증 절차 없이 단순한 회원가입/로그인 구조로 심플하게 시작합니다.

오디오 처리 및 AI 모델:

복잡한 외부 API(예: Deepgram) 대신 OpenAI의 Whisper (위스퍼: 오픈에이전시에서 만든, 음성을 텍스트로 아주 정확하게 변환해 주는 인공지능 음성 인식 모델) 모델을 사용해 음성 녹음을 처리합니다.

나> 화자가 이 과정에서 의도한 것 즉 코스의 목적은 은 무엇인가. 

GEM> 이 과정(코스)을 통해 화자가 궁극적으로 달성하고자 하는 목적은 "AI 코딩 에이전트를 활용하여 사람이 일일이 수동으로 개입하지 않고도, 명확한 역할 분담과 자동화된 루프(Loop)를 통해 혼자서 완성도 높은 소프트웨어를 빠르게 개발하는 워크플로우를 구축하고 전파하는 것"입니다.

이를 세부적인 목적들로 나누어 보면 다음과 같습니다.

1. AI 에이전트 기반의 워크플로우(Graph Engineering) 실습:
단순히 코드 한 줄을 생성하는 것을 넘어, 제품 관리자(PM), 소프트웨어 엔지니어(Engineer), 품질 검증(QA)이라는 명확한 역할을 가진 서브 에이전트(Sub-agent)들을 오케스트레이터(Orchestrator)가 조율하며 유기적으로 협업하는 시스템을 구축합니다.

2. 맥락 및 루프 엔지니어링(Context & Loop Engineering)을 통한 자율성 확보:
세션이 바뀔 때마다 에이전트가 혼란스러워하지 않도록 규칙과 문서(AGENTS.md, process.md)로 맥락을 제공하고, 사람이 계속 지켜보지 않아도 에이전트가 스스로 백로그(Backlog)를 처리하며 완주할 수 있도록 목표(Goal) 기반의 자동 실행 루프를 만듭니다.

3. 모호함 제거와 품질 향상:
태스크를 그대로 던져주는 것이 아니라, 제품 관리자 역할을 하는 에이전트를 통해 체크 가능한 명확한 인수 조건(Acceptance Criteria)을 사전에 정의함으로써 AI가 엉뚱한 방향으로 구현하는 것을 막고 제품의 품질을 높입니다.

4. 도구 및 엔진 독립성 유지 (Tool Agnostic):
특정 AI 코딩 도구나 플랫폼에 종속되지 않고, Claude Code, Codex 등 다양한 에이전트 환경에서 공통으로 적용할 수 있는 범용적인 1인 개발 자동화 방법론을 공유합니다.

2단계: GitHub 레포지토리 생성 및 이슈 관리 과정
강의에서 화자는 프로젝트를 본격적으로 시작하기 앞서, 작업할 작업 목록인 이슈 (Issue: 깃허브 등에서 프로젝트가 해야 할 작업이나 버그 수정을 등록하고 관리하는 단위)들을 생성하고 이를 체계적으로 분류합니다.


이슈 생성 및 범위 분류:

프로젝트에 필요한 기능과 작업들을 이슈로 등록합니다.

이때, 당장 구현해야 하는 핵심 기능들은 MVP (Minimum Viable Product, 최소 기능 제품: 시장의 반응을 빠르게 확인하기 위해 핵심 기능만 구현한 최소한의 제품) 라벨을 붙이고, 나중에 해도 되는 부가적인 기능들은 Post-MVP (포스트 엠브이피: MVP 단계 이후에 적용하기로 미뤄둔 추가 기능이나 고도화 작업) 라벨로 구분합니다.

명확한 인수 조건 (Acceptance Criteria) 정의:

제품 관리자 역할을 하는 에이전트를 통해 각 이슈마다 Acceptance Criteria (액셉턴스 크라이테리아, 인수 조건: 프로그램 기능이 정상적으로 완성되었는지 명확하게 판단하기 위해 충족해야 하는 구체적인 검증 기준)를 상세히 작성합니다.

이를 통해 AI 에이전트가 무엇을 만들어야 하는지 정확히 이해할 수 있도록 돕고, 나중에 테스트 과정에서 이 기준을 그대로 사용하여 코드가 잘 작동하는지 검증합니다.


커밋 선행 원칙 (Commit first, then make changes):

프로세스나 문서를 수정할 때, 에이전트에게 바로 수정을 맡기는 것이 아니라 먼저 Git commit (깃 커밋: 소스 코드나 문서의 변경 사항을 깃 저장소에 기록하여 저장하는 행위)을 수행한 뒤 변경 작업을 진행하도록 지시합니다.

이렇게 하면 팀의 작업 방식이나 프로세스가 어떻게 바뀌었는지 Git (깃: 프로그램 소스 코드의 변경 이력을 관리하고 여러 사람이 협업할 수 있게 해주는 버전 관리 시스템) 로그를 통해 명확하게 추적할 수 있습니다.

여기까지 두 번째 단계인 'GitHub 레포지토리 생성 및 이슈 관리 과정' 지침을 안내해 드렸습니다.

이 내용을 확인하셨다면, 다음 단계(루프 엔지니어링과 목표 설정 과정)로 넘어가도 될까요? 허락해 주시면 다음 단계를 이어 나가겠습니다.





3단계: 루프 엔지니어링과 목표 설정 (Loop Engineering & Goal Setting)
화자는 에이전트가 중간에 멈추지 않고 스스로 일을 끝마치게 만들기 위해 Loop Engineering (루프 엔지니어링: 사람이 계속 명령하지 않아도 에이전트가 반복적으로 작업을 수행하며 목표를 달성하도록 자동화된 실행 구조를 설계하는 기술) 개념을 도입합니다.

프롬프트, 컨텍스트, 루프 엔지니어링의 차이:

Prompt Engineering (프롬프트 엔지니어링): 코딩 에이전트에게 내리는 개별 명령어와 질문을 효과적으로 작성하는 기술입니다.

Context Engineering (컨텍스트 엔지니어링: 에이전트가 올바른 판단을 내릴 수 있도록 AGENTS.md 파일이나 개발 프로세스 문서 등 필요한 배경 지식과 규칙을 제공하는 기술): 에이전트가 작업할 때 참고할 수 있도록 규칙, 문서(AGENTS.md), 프로세스 등을 미리 준비해 주는 환경 설계입니다.

Loop Engineering (루프 엔지니어링): 사람이 일일이 채팅창에 프롬프트를 치며 지켜볼 필요 없이, 에이전트가 스스로 다음 작업을 찾아 실행하도록 '반복 실행 고리(Loop)'를 만드는 상위 개념의 메타 설계입니다.

Goal (목표) 기반의 자동 실행:

Claude Code나 Codex 같은 도구에서 제공하는 goal 기능을 활용해 "모든 MVP 이슈를 검토하고 인수 조건을 작성하라" 같은 큰 목표를 설정합니다.

4단계: 소프트웨어 엔지니어와 QA 에이전트 역할 분담 (Role Separation & QA)
화자는 제품 관리자(PM)가 정리한 백로그와 인수 조건을 바탕으로, 코드를 직접 구현하고 검증하는 다중 에이전트 역할 분담 시스템을 구축합니다.

Software Engineer (소프트웨어 엔지니어 에이전트):

제품 관리자(PM)가 구체화하고 인수 조건이 정의된 태스크를 받아 실제로 코드를 작성하고 구현하는 역할을 담당합니다.

QA Engineer (Quality Assurance Engineer, 품질 검증 엔지니어 에이전트):

QA (Quality Assurance, 품질 보증: 소프트웨어가 사용자의 요구사항과 인수 조건을 정확히 만족하는지 꼼꼼하게 테스트하고 검증하는 과정)를 전담하는 역할입니다.

개발자 본인이 자신의 코드를 검토하면 실수를 놓치기 쉽기 때문에, 별도의 독립된 QA 에이전트가 인수 조건을 기준으로 코드를 철저하게 검증합니다.

검증 결과는 언제나 Binary (바이너리: 참과 거짓, 성공과 실패처럼 딱 두 가지 값으로만 떨어지는 상태) 값인 Pass (패스, 통과) 또는 Fail (페일, 실패) 중 하나로 명확하게 판정됩니다.

피드백 루프 (Feedback Loop):

만약 QA 검증 단계에서 결과가 Fail 판정을 받으면, 작업은 다시 소프트웨어 엔지니어에게 되돌아갑니다. 엔지니어는 지적된 문제점을 수정하고, QA는 다시 테스트를 진행하는 반복 고리를 형성하여 코드의 완성도를 높입니다.

여기까지 네 번째 단계인 '소프트웨어 엔지니어와 QA 에이전트 역할 분담' 지침을 안내해 드렸습니다.

5단계: 오케스트레이터와 그래프 엔지니어링 워크플로우 (Orchestrator & Graph Engineering)
개별 에이전트들의 역할을 정했다면, 이들이 유기적으로 맞물려 돌아가도록 전체 흐름을 조율하는 Graph Engineering (그래프 엔지니어링: 여러 AI 에이전트 간의 작업 흐름과 상태 전환을 순서도 형태의 그래프로 설계하여 복잡한 업무를 자동화하는 기술) 체계를 구축합니다.

Orchestrator (오케스트레이터, 총괄 관리 에이전트):

전체 시스템의 메인 세션이자 지휘자 역할을 합니다.

직접 코드를 짜거나 테스트를 수행하지 않고, 제품 관리자(PM), 소프트웨어 엔지니어, QA 에이전트를 Sub-agent (서브 에이전트: 메인 에이전트의 지시를 받아 특정 하위 업무를 전담하여 수행하는 보조 인공지능 에이전트)로 호출하고 조율합니다.

그래프 기반 워크플로우 (Graph Workflow):

작업이 흘러가는 순서를 순서도(그래프) 형태로 정의합니다.

1단계 (백로그 풀): 작업 목록(이슈)에서 태스크를 하나 꺼냅니다.

2단계 (기획/검토): 아직 구체화되지 않았다면 PM이 인수 조건을 다듬습니다.

3단계 (구현): 소프트웨어 엔지니어가 태스크를 구현합니다.

4단계 (테스트 및 판정): QA 에이전트가 검증을 수행합니다. 결과가 Pass이면 작업 완료, Fail이면 다시 엔지니어에게 돌려보내 수정하는 루프를 반복합니다.

토큰 소비와 품질의 트레이드오프 (Trade-off):

이러한 다중 에이전트 그래프 프로세스를 도입하면, 단순 코딩보다 Token (토큰: 인공지능이 문장을 읽고 처리할 때 사용하는 글자 및 단어 단위의 기본 처리 조각) 소비량이 4~5배 이상 늘어날 수 있습니다.

하지만 사람이 일일이 개입하지 않고도 AI들이 서로 검증하기 때문에 소프트웨어의 Quality (품질)가 대폭 향상된다는 확실한 장점이 있습니다.

1단계: 추적할 프로젝트 등록하기 (project add)

매주 진행 상황을 관리하고 싶은 프로젝트들을 프로그램에 등록합니다.

각 프로젝트마다 고유한 별칭(키), 이름, 담당자, 경로, 태그를 붙여줄 수 있습니다.

PowerShell
wfb project add api --name "Billing API" --owner alexey --path ~/code/api --tag core
# 설명: 'api'라는 짧은 키로 빌링 API 프로젝트를 등록합니다. 담당자는 alexey, 경로는 ~/code/api, 태그는 core로 지정합니다.

wfb project add web --name "Web app" --owner sam --tag core
# 설명: 'web'이라는 키로 웹 앱 프로젝트를 등록합니다.


2단계: 이번 주 피드백 기록하기 (add)

등록한 프로젝트에 대해 이번 주 상태, 점수, 성과, 이슈, 차단 요소, 다음 단계를 기록합니다.

PowerShell
wfb add api -s red --score 2 `
    -H "refunds endpoint live" `
    -i "flaky integration tests" `

1. 데이터 파일의 탐색 순서 (Where the data lives)
프로그램은 실행될 때 아래와 같은 우선순위 순서로 데이터를 저장할 JSON 파일의 위치를 찾습니다.

--file PATH (또는 -f) 옵션: 명령어를 실행할 때 직접 지정한 파일 경로 (※ 윈도우 환경에서 C드라이브 공간을 아끼고 E드라이브에 데이터를 모아두기 위해 우리가 실무에서 주로 활용하는 방식입니다.)

환경변수 $WEEKLY_FEEDBACK_FILE: 시스템 환경변수에 설정된 파일 경로 (※ PowerShell 등에서는 $env:WEEKLY_FEEDBACK_FILE="E:\...\weekly-feedback.json" 형태로 지정할 수 있습니다.)

현재 디렉토리의 ./weekly-feedback.json: 만약 현재 작업 중인 폴더 안에 이 파일이 존재한다면, 프로젝트 자체에 이력이 귀속되도록 해당 파일을 자동으로 선택하여 사용합니다.

기본 사용자 홈 디렉토리의 ~/.weekly-feedback/feedback.json: 위 조건들에 해당하는 파일이 없을 때 기본적으로 찾아가는 위치입니다. (※ 기본값은 C드라이브 홈 폴더가 되므로, C드라이브 용량 관리에 유의해야 합니다.)

2. 데이터 병합 및 저장 방식 (Merging & Atomic writes)
스마트한 데이터 병합:
동일한 프로젝트에 대해 같은 주차에 반복해서 add 명령어를 호출할 경우, 데이터를 무조건 덮어쓰지 않고 기본적으로 자동 병합(Merge)됩니다. (리스트 항목들은 뒤에 이어붙여지고 중복은 건너뛰며, 상태와 점수는 최신 값으로 갱신됩니다.) 만약 기존 기록을 완전히 무시하고 새로 덮어쓰고 싶다면 --replace 플래그를 사용하면 됩니다.

안전한 원자적 쓰기 (Atomic writes):
파일을 저장하는 도중에 프로그램이 강제로 종료되더라도 JSON 파일이 깨지지 않도록, 임시 파일(.tmp)에 먼저 안전하게 기록한 뒤 최종 파일로 깔끔하게 교체하는 방식을 사용합니다.

uv (초고속 파이썬 일꾼): 파이썬 프로그램을 실행하려면 필요한 부품(패키지)들을 잔뜩 받아야 합니다. 옛날 방식(pip 등)과 달리 터보 엔진을 단 것처럼 순식간에 부품들을 제자리에 꽂아주며, 내 컴퓨터에서 곧바로 프로그램을 띄울 때 씁니다.

Docker Compose (마법의 상자): "내 컴퓨터에서는 되는데 왜 남의 컴퓨터에선 안 되지?" 하는 개발자들의 골칫거리를 해결해 줍니다. 데이터베이스부터 웹 서버까지 필요한 모든 환경을 하나의 상자(컨테이너)에 포장해서 명령어 한 줄(docker compose up)로 어디서나 똑같이 띄워줍니다.

3. 프론트엔드 빌드 방식 (지혜로운 역할 분담)
왜 이렇게 나눴을까요?: 화면을 예쁘게 꾸미는 Node.js 같은 도구들은 프로그램이 실행되는 내내 무겁게 켜져 있을 필요가 없습니다. 내 컴퓨터(호스트)에서 미리 뚝딱 디자인 결과물(CSS/JS)을 만들어(빌드) 놓고, 프로그램은 그 결과물만 가져다 쓰도록 똑똑하게 역할 분담이 되어 있습니다.

🔑 실전 시동 걸기: retroloop을 움직이는 정확한 순서
공식 리포지토리의 가이드를 바탕으로, 내 컴퓨터에서 이 웹 서비스를 온전하게 켜고 구동하는 실제 명령어 흐름입니다.

1. uv sync (파이썬 부품 보따리 풀기)
내용: 프로젝트에 필요한 파이썬 패키지 의존성을 초고속으로 동기화합니다.

2. cp .env.example .env (환경 설정 파일 준비)
내용: 기본 설정 틀을 복사하여 내 컴퓨터용 환경 변수 파일(.env)을 만듭니다. (※ 윈도우 환경에서는 Copy-Item 명령어를 사용합니다.)

3. 프론트엔드 화면 자산 빌드 (npm 명령어)
npm install: 화면을 예쁘게 꾸미는 데 필요한 도구들을 설치합니다.

npm run build:css: Tailwind CSS 등의 스타일 파일을 브라우저가 읽을 수 있는 정적 파일로 미리 빌드합니다. (회고 보드 등 JS 확장이 필요할 경우 npm run build:js도 함께 쓰입니다.)

4. 데이터베이스 준비 및 마이그레이션 (migrate)
내용: PostgreSQL 데이터베이스가 실행 중인 상태에서, 앱의 데이터 구조를 잡아주는 uv run manage.py migrate를 실행합니다. (※ 데모 데이터를 가볍게 채워보고 싶다면 선택적으로 seed_demo를 활용할 수도 있습니다.)

5. uv run manage.py runserver (서버 시동 켜기!)
내용: 모든 준비가 끝나고 웹 서버가 구동되면, 인터넷 주소창(http://localhost:8000/)에 접속하여 완성된 웹사이트를 직접 확인할 수 있습니다.

이로써 retroloop의 개념부터 구조, 그리고 실전 시동 순서까지의 탄탄한 흐름이 완성되었습니다.
