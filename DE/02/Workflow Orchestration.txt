2.1 워크플로우 오케스트레이션 입문
이 섹션에서는 워크플로우 오케스트레이션의 기초와 그 중요성, 그리고 현대 데이터 생태계에서 Kestra가 어떤 위치를 차지하고 있는지 배우게 됩니다.

2.1.1 워크플로우 오케스트레이션이란 무엇인가?
음악 오케스트라를 떠올려 보세요. 오케스트라에는 다양한 악기들이 있습니다. 각 악기는 역할이 다르고 개수도 제각각이죠. 이 모든 악기가 제시간에 맞춰 조화로운 소리를 내기 위해서는, 전체를 조율하며 연주 시점을 알려주는 지휘자가 필요합니다.

이제 이 **악기들을 '데이터 도구'**로, **지휘자를 '오케스트레이터'**로 바꿔서 생각해보겠습니다. 우리는 보통 여러 도구와 플랫폼을 함께 사용해야 합니다. 어떤 작업은 정해진 시간에 맞춰 실행되어야 하고, 어떤 작업은 특정 이벤트가 발생했을 때 시작되어야 하죠. 이때 오케스트레이터가 등판하여 이 모든 도구가 협업할 수 있도록 관리합니다.

워크플로우 오케스트레이터가 하는 주요 작업:

미리 정의된 단계들로 구성된 워크플로우를 실행합니다.

오류를 모니터링하고 기록하며, 에러 발생 시 추가 조치(재시도 등)를 취합니다.

스케줄(시간)이나 특정 이벤트에 따라 워크플로우를 자동으로 실행합니다.

데이터 엔지니어링에서는 데이터를 한 곳에서 다른 곳으로 옮기고, 그 과정에서 데이터를 수정(변환)하는 일이 빈번합니다. 오케스트레이터는 이 모든 단계를 관리하는 동시에, 전체 과정을 한눈에 파악할 수 있는 가시성을 제공합니다.

이번 모듈에서는 Kestra를 중심으로 ETL(Extract, Transform Load: 추출, 변환, 적재) 데이터 파이프라인을 직접 구축해 볼 것입니다. 하지만 본격적인 구축에 앞서, Kestra가 정확히 어떻게 작동하는지 먼저 이해해 봅시다!




2.1.2 Kestra란?

Kestra는 오픈 소스 기반의 무한 확장 가능한 워크플로 오케스트레이션 플랫폼으로, 모든 엔지니어가 비즈니스 핵심 워크플로를 효율적으로 관리할 수 있도록 설계되었습니다.

Kestra는 워크플로 오케스트레이션 도구로서 다음과 같은 강점을 가지고 있습니다.

Flow 코드(YAML), 노코드, 또는 AI Copilot을 활용해 워크플로를 구축할 수 있어, 작업 방식에 유연하게 대응 가능

1,000개 이상의 플러그인을 제공하여, 사용 중인 다양한 도구들과 손쉽게 연동 가능

모든 프로그래밍 언어를 지원하므로, 작업에 가장 적합한 언어를 자유롭게 선택 가능

스케줄 기반 또는 이벤트 기반 트리거를 지원하여, 데이터 변화에 따라 워크플로가 자동으로 반응

2.2.1 Kestra 설치하기

Kestra는 Docker Compose를 사용해 설치합니다.
이미 모듈 1에서 Postgres 데이터베이스와 pgAdmin을 설정했으므로, 이를 Kestra와 함께 계속 사용할 수 있습니다. 다만, Docker Compose 파일에 몇 가지 수정이 필요합니다.

아래의 예제 Docker Compose 파일을 사용하여:

1. 새로운 2개의 서비스(Kestra, Postgres)를 올바르게 추가하고

2. 볼륨(volume)을 정확하게 설정합니다.

3. 또한 사용자 이름(username)과 비밀번호(password) 설정에 대한 정보도 추가해야 합니다.


//
나> volumes:
  ny_taxi_postgres_data: # 기존 볼륨 유지
  pgadmin_data:          # 기존 볼륨 유지
  kestra_postgres_data:  # Kestra용 새 볼륨
  kestra_data:           # Kestra용 새 볼륨

이건 뭘의미함?



GEM> 이 부분은 Docker에서 가장 중요한 **'데이터의 영속성(Persistence)'**을 설정하는 구간입니다.

쉽게 설명하자면, **"컨테이너(프로그램)가 삭제되거나 멈춰도, 우리가 쌓아온 데이터는 하드디스크의 이 이름표를 붙인 공간에 안전하게 따로 저장해라"**라고 명령하는 것입니다.

각 볼륨 이름이 의미하는 바는 다음과 같습니다:

1. 각 볼륨의 역할
ny_taxi_postgres_data:

내용: 모듈 1에서 넣었던 뉴욕 택시 데이터와 테이블 구조가 저장되는 곳입니다.

의미: 이 이름이 유지되어야만 기존에 고생해서 넣었던 데이터를 그대로 불러올 수 있습니다.

pgadmin_data:

내용: pgAdmin에서 설정한 서버 연결 정보, 사용자 설정 등이 저장됩니다.

kestra_postgres_data: (새로 추가)

내용: Kestra라는 지휘자가 앞으로 실행할 워크플로우 기록, 로그, 성공/실패 여부 등의 '상태 정보'가 저장됩니다.

kestra_data: (새로 추가)

내용: Kestra가 내부적으로 처리하는 파일들(예: 다운로드한 CSV 파일 임시 저장 등)이 들어가는 내부 스토리지 공간입니다.


2. 왜 이렇게 선언하나요? (작동 원리)
Docker Compose 파일 하단에 이렇게 이름을 나열하는 것은 **"이 이름들을 가진 가상의 외장 하드디스크를 준비해줘"**라고 선언하는 것과 같습니다.

그 후, 각 서비스(Service) 설정 내의 volumes: 항목에서 다음과 같이 연결합니다: - ny_taxi_postgres_data:/var/lib/postgresql

왼쪽(ny_taxi_postgres_data): 내 컴퓨터(Host)에 저장될 이름표(볼륨)

오른쪽(/var/lib/postgresql): 컨테이너 내부의 데이터 저장 경로

이렇게 연결해두면, 컨테이너를 지우고 새로 만들어도 이름표가 같은 볼륨이 있으면 Docker가 자동으로 기존 데이터를 다시 연결해 줍니다. 그래서 사용님이 "기존 환경을 망치고 싶지 않다"고 하셨을 때, 이 이름들을 그대로 유지하는 것이 핵심인 것입니다.

💡 요약
이 설정 덕분에 사용님은 docker compose down을 하더라도 데이터 걱정 없이 안심하고 Kestra 설정을 추가하고 테스트하실 수 있는 것입니다.

1. docker-workshop과 terrademo를 따로 둔 이유
보통 강의에서 이 둘을 나누는 이유는 **관리 대상(인프라 vs 서비스)**이 다르기 때문입니다.

terrademo (Terraform): 구글 클라우드(GCP) 같은 외부 클라우드 자원을 생성하고 관리하는 "건축 설계도"입니다.

docker-workshop (Docker): 내 컴퓨터(Local) 안에서 실행되는 데이터베이스나 툴들을 관리하는 "가구 배치도"입니다.

결론부터 말씀드리면: terrademo 폴더는 절대 삭제하지 마세요. 모듈 2의 후반부(2.4 섹션)에서 다시 GCP(BigQuery, GCS)를 사용하게 되는데, 그때 테라폼으로 만든 자원이 필요합니다.

3. "하나의 폴더로 통합하면 안 되나?"에 대한 답변
불가능하지는 않지만, 폴더를 나누는 것이 훨씬 바람직합니다.

복잡도: 한 폴더에 모든 .tf 파일과 .yml, 그리고 파이프라인 코드들이 섞이면 나중에 관리가 불가능해집니다.

충돌 방지: 각 모듈(주차)마다 사용하는 설정이 조금씩 달라질 수 있습니다. 폴더를 분리해야 "01단원 실습 상태"를 그대로 보존하면서 "02단원"을 마음껏 수정할 수 있습니다.

볼륨(데이터) 공유: 폴더를 복사해도 하단 volumes에 적힌 이름(ny_taxi_postgres_data)만 같으면, Docker 엔진이 알아서 기존 데이터를 새 폴더의 컨테이너에 연결해 줍니다. 즉, 폴더 위치와 상관없이 데이터는 따라옵니다.

구체적으로는 다음과 같은 오케스트레이션(지휘)의 핵심 원리를 배우는 용도예요.

1. 입력과 변수 제어 (inputs, variables)
용도: 실행할 때마다 값이 바뀌는 상황을 처리합니다.

실제 예시: "오늘은 1월 데이터를 처리해", "내일은 2월 데이터를 처리해"라고 명령을 내릴 때, 코드 전체를 수정하지 않고 실행 시점에 '월' 정보만 입력받아 처리하는 법을 익히는 것입니다.

2. 작업 간의 데이터 전달 (outputs)
용도: 앞선 작업의 결과물을 다음 작업이 이어받는 법을 배웁니다.

실제 예시: 1단계에서 '데이터 다운로드'를 하면, 2단계에서 '다운로드된 파일 이름'을 알아야 압축을 풀겠죠? 이렇게 태스크끼리 정보를 주고받는 메커니즘({{ outputs.return_data.value }})을 확인하는 용도입니다.

3. 자동 실행 예약 (triggers)
용도: 사람이 버튼을 누르지 않아도 정해진 시간에 작동하게 합니다.

실제 예시: "매일 새벽 3시에 어제 데이터를 정리해라" 같은 배치(Batch) 작업을 자동화하는 법을 배웁니다.

4. 정책(플러그인) 확인 (tasks)
용도: 이 시스템(Kestra)이 어떤 기능(Log, Return 등)을 제공하는지 확인합니다.

아까 발생했던 Sleep 에러처럼, "이 버전에서는 이 기능을 쓸 수 있는가?"를 체크하는 가장 기초적인 단계입니다.

2.2.2 - 케스트라 개념
Kestra에서 워크플로우를 구축하려면 몇 가지 개념을 이해해야 합니다.

Flow 는 작업과 해당 작업의 오케스트레이션 로직을 담는 컨테이너입니다.

📘 Kestra 핵심 개념 (Core Concepts)
Flow - 작업(Task)들과 그 오케스트레이션 로직을 담는 컨테이너입니다.

Tasks - 흐름 내의 단계입니다.

Inputs - 런타임에 흐름에 전달되는 동적 값입니다.

Outputs - 작업과 흐름 간에 데이터를 전달합니다.

Triggers - 워크플로 실행을 자동으로 시작하는 메커니즘입니다.

Execution - 특정 상태를 갖는 흐름의 단일 실행입니다.

Variables - 여러 작업에서 값을 재사용할 수 있도록 해주는 키-값 쌍입니다.

Plugin Defaults - 하나 이상의 흐름 내에서 특정 유형의 모든 작업에 적용되는 기본값입니다.

Concurrency - 워크플로가 동시에 실행될 수 있는 횟수를 제어합니다.

이 흐름도는 01_hello_world.yaml이러한 모든 개념을 하나의 워크플로 안에 담아 보여줍니다.

이 워크플로는 5개의 작업으로 구성됩니다. 2개의 로그 작업과 1개의 수면 작업입니다.
이 흐름은 name라는 이름의 입력을 받습니다.
name입력값을 받아 전체 환영 메시지를 생성하는 변수가 있습니다 .
반환 작업에서 출력이 생성되어 이후의 로그 작업에 기록됩니다.
이 워크플로는 매일 오전 10시에 실행되도록 설정되어 있습니다.
플러그인 기본 설정은 두 로그 작업 모두 메시지를 동일한 ERROR수준으로 전송하도록 하는 데 사용됩니다.
동시 실행 제한은 2개입니다. 2개의 프로세스가 실행 중인 동안 추가로 실행을 시도하면 실패합니다.

Flow: 
방금 주신 방대한 공식 문서를 토대로, Kestra의 가장 핵심적인 설계 원칙을 데이터 엔지니어의 시각에서 다시 한번 매끄럽게 정리해 드릴게요.

이 내용은 단순한 설명서가 아니라, 앞으로 우리가 짤 모든 코드의 **'설계 가이드라인'**이 될 것입니다.

🏗️ Kestra Flow 설계의 핵심 가이드
1. Flow: 오케스트레이션의 기본 단위
Flow는 단순히 작업의 나열이 아니라, 로직과 순서를 담는 컨테이너입니다.

필수 요소: id (식별자), namespace (그룹화), tasks (수행할 작업 목록).

선언적 정의: YAML 파일로 작성하거나, 복잡한 코딩 없이 UI의 No-Code Editor로 구성할 수 있습니다.

2. Task의 두 얼굴: Runnable vs Flowable
이 구분을 이해하는 것이 매우 중요합니다.

Runnable Tasks (실행형): 실제 데이터 처리를 담당합니다. (예: Python 실행, SQL 쿼리, API 호출) 무거운 연산을 수행하며 Worker가 이 짐을 짊어집니다.

Flowable Tasks (흐름 제어형): 논리적인 흐름을 결정합니다. (예: 조건문(Switch), 반복문, 병렬 처리) Executor가 관리하며, 절대 무거운 연산을 시키면 안 됩니다.

3. 데이터의 흐름: Inputs & Outputs
Inputs: 실행 시점에 외부에서 넣어주는 값입니다. FILE 타입의 입력을 넣으면 Kestra 내부 저장소에 올라가 모든 Task가 공유할 수 있게 됩니다.

Outputs: 각 Task가 만들어낸 결과물입니다. 다음 Task에서 이를 재사용하거나 필요한 경우 브라우저에서 직접 다운로드할 수 있습니다.

4. 효율적인 관리를 위한 도구들
Variables (변수): {{ vars.key }} 형태로 호출하며, Flow 안에서 반복되는 값을 한 곳에서 관리합니다.

Plugin Defaults: 특정 플러그인(예: Log)을 쓸 때마다 매번 설정하기 귀찮은 공통 속성(로그 레벨 등)을 미리 정해둡니다.

Revision (버전 관리): 수정할 때마다 자동으로 버전이 매겨집니다. 실수로 코드를 날려도 과거 기록으로 되돌릴 수 있는 안전장치입니다.

5. 자동화의 시작: Triggers

Tasks: 
아래는 Kestra 공식 문서 “Tasks” 페이지 내용을 자연스럽고 매끄럽게 한국어로 번역한 설명입니다. (Kestra 워크플로우에서 Task가 무엇인지, 종류, 공통 속성 등 핵심 내용을 정리한 것입니다)

🧩 Task(작업)란 무엇인가?

**Task(작업)**는 Flow(워크플로)의 개별 단계 하나를 의미합니다.
워크플로 안에서 입력값(inputs)과 변수(variables)를 처리하고, 처리 결과를 **다음 작업 또는 사용자에게 전달할 수 있는 출력값(outputs)**을 생성합니다.

즉, Flow는 여러 개의 Task가 차례로 또는 조건에 따라 실행되면서 전체 워크플로를 완성하게 됩니다.

🧠 Task의 두 가지 주요 종류
1. Flowable Tasks

Flowable Task는 실제 계산 작업을 수행하는 것이 아니라, 워크플로의 흐름을 제어하는 역할을 합니다.
다른 작업을 병렬로 실행하거나, 조건 분기(branch), 반복(loop) 등 워크플로의 구조와 논리를 다루는 데 사용됩니다.

✔️ Flowable Tasks 특징

무거운 계산 작업을 수행하지 않음

워크플로 실행 순서, 조건 제어, 반복 등을 처리

Flow 내부의 제어 흐름을 구성

📌 대표 예시

io.kestra.plugin.core.flow.Parallel – 병렬 실행

io.kestra.plugin.core.flow.Switch – 조건 분기

io.kestra.plugin.core.flow.ForEachItem – 각 항목 반복 처리

2. Runnable Tasks

Runnable Task는 실제로 작업을 수행하는 Task입니다.
파일 읽기/쓰기, API 호출, DB 질의, 스크립트 실행 등 실제 계산과 처리 작업을 담당하며, 워커(worker)가 이를 실행합니다.

✔️ Runnable Tasks 특징

실제 작업(연산/IO/네트워크)을 실행

워커가 실행하며, 경우에 따라 고비용 계산도 가능

플러그인을 통해 다양한 작업이 추가됨

📌 대표 예시

io.kestra.plugin.scripts.python.Commands – Python 스크립트 실행

io.kestra.plugin.core.http.Request – HTTP 요청

io.kestra.plugin.notifications.slack.SlackExecution – Slack 알림 전송

📋 모든 Task가 갖는 공통 속성

Task는 종류와 상관없이 다음과 같은 공통 속성(properties) 을 가집니다.

| 속성             | 설명                                    |                  |
| -------------- | ------------------------------------- | ---------------- |
| `id`           | Task의 고유 식별자(Flow 안에서 유일해야 함)         |                  |
| `type`         | Task 종류를 나타내는 Java 클래스 이름             |                  |
| `description`  | Task에 대한 설명(사용자 정의)                   |                  |
| `retry`        | 실패 시 재시도 설정                           |                  |
| `timeout`      | 최대 수행 시간 (ISO 8601 Duration)          |                  |
| `runIf`        | 조건식이 false일 경우 Task 건너뛰기              |                  |
| `disabled`     | true로 설정하면 실행 중 해당 Task 생략            |                  |
| `workerGroup`  | (Enterprise) 이 Task를 실행할 worker 그룹 지정 |                  |
| `allowFailure` | 실패해도 다음 Task로 진행 허용                   |                  |
| `allowWarning` | Warning이 있어도 성공으로 판단                  |                  |
| `logLevel`     | 저장할 로그 레벨 지정                          |                  |
| `logToFile`    | 로그를 파일로 저장 여부(내부 저장소)                 | ([kestra.io][1]) |

[1]: https://kestra.io/docs/workflow-components/tasks?utm_source=chatgpt.com "Tasks"


※ logToFile은 로그가 매우 많은 Task에서 DB 저장 대신 파일로 저장할 때 유용하며, UI에서 다운로드할 수 있습니다.

🔄 동적 속성 vs 정적 속성 (Dynamic vs Static)

Task 속성은 정적(static) 이거나 동적(dynamic) 으로 설정할 수 있습니다.
동적 속성은 표현식(expression)으로 값을 지정해 실행 시점에 결정됩니다.

정적 속성: 고정값

동적 속성: {{ }} 템플릿 표현식으로 설정

일부 복잡한 객체 타입 속성은 동적 지원이 제한될 수 있으며, 내부 속성부터 하위로 내려가면 대부분 동적으로 설정할 수 있습니다.

🧠 정리

🔹 Task = Flow 내의 한 단계 작업
🔹 Flowable Tasks = 워크플로 제어(분기·반복·병렬)
🔹 Runnable Tasks = 실제 처리 작업(스크립트/IO/API)
🔹 공통 속성으로 Task 실행 동작을 제어 가능
🔹 동적 속성은 표현식 기반으로 템플릿처럼 사용 가능

🧩 Inputs(입력)란?

**Inputs(입력)**은 워크플로 실행 시 외부에서 동적으로 전달되는 값입니다.
즉, 같은 Flow라 하더라도 실행할 때마다 다른 입력값을 주면 여러 상황에 대응할 수 있는 유연한 워크플로를 만들 수 있습니다.

예를 들어, 처리할 파일 경로나 사용자 이름 같은 값을 하드코딩하지 않고 Inputs로 받으면, 하나의 Flow를 다양한 환경/데이터로 재사용 가능하게 만들 수 있습니다.

입력값은 실행 콘텍스트(execution context)에 저장되며, 워크플로 내부에서는
{{ inputs.parameter_name }}처럼 템플릿 표현식으로 접근할 수 있습니다.

🧠 Inputs 정의 방법

Inputs는 Flow 정의에서 리스트 형태로 선언합니다.
각 입력은 적어도 id(이름)과 type(자료형)을 가져야 하며, 필요에 따라 기본값(defaults)이나 필수 여부(required) 등을 설정할 수 있습니다.

inputs:
  - id: user
    type: STRING
    defaults: Zoyd Wheeler


위와 같이 설정하면, 실행 시 {{ inputs.user }}로 해당 값을 참조할 수 있습니다.

📌 Inputs 속성

Inputs가 가질 수 있는 주요 속성들은 다음과 같습니다:

id: 입력 파라미터의 고유 식별자. Flow 안에서 inputs.id로 참조됨

type: 입력값의 자료형 (예: STRING, INT, BOOL, ARRAY 등)

required: 필수 입력인지 여부 (true/false)

defaults: 입력값이 지정되지 않았을 때 사용할 기본값

prefill: 초기 제안값으로 설정되며 null로 재설정 가능

dependsOn: 다른 입력값에 의존하는 경우 설정

displayName: UI에서 표시할 라벨

description: 입력 설명(마크다운 가능)

expression: Pebble 표현식으로 동적 기본값 설정

autoSelectFirst: 드롭다운에서 첫 값을 자동 선택 (SELECT/MULTISELECT에만)

✅ 입력값 유효성 검사 (Validation)

Kestra는 입력값의 자료형을 자동으로 검증합니다. 또한 일부 자료형은 추가 검증 규칙도 지원합니다:

STRING: 정규식(validator)으로 패턴 검사 가능

INT / FLOAT / DURATION: min, max로 범위 제한

DATE / TIME / DATETIME: after, before로 유효 범위 지정

예를 들어, 나이 입력은 18~64 범위로 제한하고, 사용자 이름 입력은 특정 패턴으로 검증할 수 있습니다.

🔹 중첩(Nested) Inputs

id에 .(점)을 사용하면, 중첩 구조의 입력을 만들 수 있습니다:

inputs:
  - id: nested.string
    type: STRING
  - id: nested.int
    type: INT


이 경우도 {{ inputs.nested.string }}처럼 접근할 수 있습니다.

🔹 배열(Array) Inputs

리스트 값이 필요할 때는 ARRAY 자료형을 사용하고, itemType으로 내부 항목의 타입을 지정해야 합니다:

- id: my_numbers
  type: ARRAY
  itemType: INT
  defaults: [1,2,3]


이처럼 여러 개의 정수값을 입력으로 받을 수 있습니다.

📌 입력값 사용 방법

Inputs는 워크플로 내부에서 항상 템플릿으로 사용할 수 있습니다:

{{ inputs.name }}


만약 id에 하이픈(-) 같은 특수문자가 포함되면 대괄호 표기법을 사용합니다:

{{ inputs['my-file'] }}


이 값은 Task의 동적 속성에도 활용할 수 있습니다.

🧠 Execution 시 입력값 설정
🤖 Web UI

UI에서 실행을 만들 때 입력값을 폼으로 입력할 수 있으며, UI는 inputs 정의에 따라 자동으로 생성됩니다.

🧑‍💻 API

API(ex: curl)로 실행할 때는 multipart/form-data 형태로 입력값을 전달해서 실행을 생성합니다.

🐍 Python

Python 코드를 사용해 API로 실행할 때도 입력값을 함께 전달할 수 있습니다.

🔁 Inputs vs Variables

Inputs는 실행 시점마다 값이 바뀔 수 있는 파라미터입니다.
반면 Variables는 실행이 시작된 이후 변경할 수 없는 상수값에 가깝습니다.
즉, 고정값은 Variables로, 실행마다 유동적으로 바꿀 값은 Inputs로 사용하는 것이 좋습니다.

📌 요약

✅ Inputs는 Flow 실행마다 값이 들어오는 매개변수
✅ 실행 조건/환경에 따라 재사용 가능한 워크플로 구성 가능
✅ 타입 검증, 기본값, UI 라벨 등 다양하게 설정 가능
✅ 배열, 중첩 구조도 지원

03_getting_started_data_pipeline.yaml아직 플로우를 추가하지 않았다면 UI에서 플로우를 추가하고 실행하여 결과를 확인하세요. 간트 차트 및 로그 탭을 검토하여 플로우 실행 과정을 이해할 수 있습니다.



id: 03_getting_started_data_pipeline
namespace: zoomcamp

inputs:
  - id: columns_to_keep
    type: ARRAY
    itemType: STRING
    defaults:
      - brand
      - price

tasks:
  - id: extract
    type: io.kestra.plugin.core.http.Download
    uri: https://dummyjson.com/products

  - id: transform
    type: io.kestra.plugin.scripts.python.Script
    containerImage: python:3.11-alpine
    inputFiles:
      data.json: "{{outputs.extract.uri}}"
    outputFiles:
      - "*.json"
    env:
      COLUMNS_TO_KEEP: "{{inputs.columns_to_keep}}"
    script: |
      import json
      import os

      columns_to_keep_str = os.getenv("COLUMNS_TO_KEEP")
      columns_to_keep = json.loads(columns_to_keep_str)

      with open("data.json", "r") as file:
          data = json.load(file)

      filtered_data = [
          {column: product.get(column, "N/A") for column in columns_to_keep}
          for product in data["products"]
      ]

      with open("products.json", "w") as file:
          json.dump(filtered_data, file, indent=4)

  - id: query
    type: io.kestra.plugin.jdbc.duckdb.Queries
    inputFiles:
      products.json: "{{outputs.transform.outputFiles['products.json']}}"
    sql: |
      INSTALL json;
      LOAD json;
      SELECT brand, round(avg(price), 2) as avg_price
      FROM read_json_auto('{{workingDir}}/products.json')
      GROUP BY brand
      ORDER BY avg_price DESC;
    fetchType: STORE

2. Inputs (입력값 설정)

YAML

inputs:

    itemType: STRING
    defaults: ["brand", "price"] # 기본적으로 브랜드와 가격 컬럼만 남기도록 설정
작동 원리: 파이썬 코드에 어떤 데이터를 남길지 전달하는 역할을 합니다. 나중에 "나는 색상(color)도 보고 싶어"라고 하면 코드 수정 없이 실행 시점에 입력값만 바꾸면 됩니다.

3. Task 1: Extract (데이터 추출)
YAML

  - id: extract
    type: io.kestra.plugin.core.http.Download
    uri: https://dummyjson.com/products
작동 원리: Download 플러그인을 사용하여 외부 API(URL)에서 데이터를 가져옵니다.

결과: 가져온 데이터는 Kestra 내부 저장소에 임시 파일로 저장되며, 이 파일의 주소(URI)는 {{outputs.extract.uri}}를 통해 다음 단계로 전달됩니다.

4. Task 2: Transform (데이터 변환 - Python)
가장 핵심적인 부분으로, 가져온 원본 데이터를 요리하는 과정입니다.

YAML

  - id: transform
    type: io.kestra.plugin.scripts.python.Script
    containerImage: python:3.11-alpine # 가벼운 파이썬 도커 이미지 사용
    inputFiles:
      data.json: "{{outputs.extract.uri}}" # 이전 단계의 파일을 'data.json'이라는 이름으로 가져옴
    outputFiles:
      - "*.json" # 작업 후 생성된 모든 json 파일을 결과물로 내보냄
    env:
      COLUMNS_TO_KEEP: "{{inputs.columns_to_keep}}" # 입력을 환경변수로 전달
    script: |
      import json
      import os

      # 1. 환경변수에서 남길 컬럼 리스트를 가져와 해석
      columns_to_keep_str = os.getenv("COLUMNS_TO_KEEP")
      columns_to_keep = json.loads(columns_to_keep_str)

      # 2. Extract 단계에서 받은 원본 파일 읽기
      with open("data.json", "r") as file:
          data = json.load(file)

      # 3. 데이터 가공: 원하는 컬럼(brand, price)만 추출
      filtered_data = [
          {column: product.get(column, "N/A") for column in columns_to_keep}
          for product in data["products"]
      ]

      # 4. 가공된 데이터를 새로운 파일로 저장
      with open("products.json", "w") as file:
          json.dump(filtered_data, file, indent=4)
작동 원리: Kestra가 독립된 파이썬 컨테이너를 띄우고, 그 안에 파일을 넣어준 뒤 스크립트를 실행합니다. 스크립트가 끝나면 products.json이라는 결과물을 다시 Kestra 저장소로 회수합니다.

5. Task 3: Query (데이터 분석 - DuckDB)
가공된 데이터를 SQL로 조회하는 단계입니다.

YAML

  - id: query
    type: io.kestra.plugin.jdbc.duckdb.Queries
    inputFiles:
      products.json: "{{outputs.transform.outputFiles['products.json']}}" # 파이썬이 만든 파일 로드
    sql: |
      INSTALL json; # DuckDB용 JSON 확장 설치
      LOAD json;
      -- 가공된 json 파일을 읽어서 브랜드별 평균 가격 계산
      SELECT brand, round(avg(price), 2) as avg_price
      FROM read_json_auto('{{workingDir}}/products.json')
      GROUP BY brand
      ORDER BY avg_price DESC;
    fetchType: STORE # 결과값을 Kestra UI에서 볼 수 있게 저장
작동 원리: DuckDB라는 가벼운 분석용 DB 엔진을 사용합니다. 별도의 DB 서버 설치 없이도 파일 자체를 테이블처럼 SQL로 쿼리할 수 있어 매우 빠르고 효율적입니다.

🚀 요약하자면
Extract: 외부 사이트에서 제품 정보를 내려받는다.

Transform: 파이썬을 시켜서 수많은 정보 중 내가 필요한 '브랜드'와 '가격'만 골라낸다.

Query: DuckDB를 이용해 "어떤 브랜드가 가장 비싼지" 통계를 낸다.

이제 이 코드를 Kestra UI의 Edit 탭에 붙여넣고 실행해 보세요! Gantt 차트에서는 작업 순서를, Outputs 탭에서는 DuckDB가 계산한 브랜드별 평균 가격 리스트를 확인하실 수 있습니다.

성공하시면 로그에 데이터가 어떻게 찍히는지 알려주세요! 😊

나> Flow 코드 프로세스 설명

GEM> 이 Flow는 단순한 데이터 전송을 넘어, 실제 기업 현장에서 사용하는 'Staging(임시 저장) 및 Merge(병합)' 전략을 그대로 구현한 프로급 파이프라인입니다.

핵심 로직을 단계별로 나누어 명쾌하게 설명해 드릴게요.

🏗️ 핵심 프로세스 5단계
Extract (추출): GitHub에서 특정 연도/월의 택시 CSV 파일을 다운로드합니다.

Staging (임시 로드): 원본 데이터를 가공 없이 그대로 staging 테이블에 쏟아붓습니다.

Transformation (ID 부여): 데이터 중복을 막기 위해 여러 컬럼을 조합해 고유 키(unique_row_id)를 생성합니다.

Merge (병합): 기존 데이터와 비교해서 새로운 데이터만 최종 테이블에 집어넣습니다. (Upsert 방식)

Purge (정리): 용량을 차지하는 임시 파일들을 삭제합니다.

🔍 주요 코드 상세 해석
1. 변수 설정 (Variables)
YAML

variables:
  file: "{{inputs.taxi}}_tripdata_{{inputs.year}}-{{inputs.month}}.csv"
  staging_table: "public.{{inputs.taxi}}_tripdata_staging"
작동 원리: 사용자가 선택한 값(yellow, 2019, 01)을 조합해 파일명과 테이블명을 자동으로 만듭니다. 반복되는 복잡한 표현식을 하나로 묶어 관리하는 '관리 포인트 단일화' 전략입니다.

2. 데이터 추출 (Extract)
YAML

commands:
  - wget -qO- https://url/{{render(vars.file)}}.gz | gunzip > {{render(vars.file)}}
작동 원리: 압축된(.gz) 파일을 내려받음과 동시에 파이프(|)를 통해 압축을 풀어 CSV로 변환합니다. render(vars.file)는 위에서 정의한 변수를 실제 이름으로 변환해주는 역할을 합니다.

3. 조건부 실행 (If Task)
YAML

  - id: if_yellow_taxi
    condition: "{{inputs.taxi == 'yellow'}}"
작동 원리: Yellow 택시와 Green 택시는 데이터 구조(컬럼명)가 미세하게 다릅니다. 이를 위해 조건문을 써서 각각에 맞는 테이블 생성 및 로드 로직을 실행합니다.

4. 초고속 로드 (CopyIn)
YAML

type: io.kestra.plugin.jdbc.postgresql.CopyIn
작동 원리: 한 줄씩 INSERT 하는 게 아니라, 파일을 통째로 DB에 들이붓는 방식입니다. 대용량 데이터 처리에 필수적인 플러그인입니다.

5. 고유 ID 생성 (MD5 Hash)
SQL

unique_row_id = md5(COALESCE(...) || COALESCE(...))
작동 원리: 벤더ID, 픽업시간, 요금 등을 합쳐서 **지문(Hash)**을 만듭니다. 이렇게 하면 똑같은 데이터가 두 번 들어와도 ID가 같으므로 중복을 완벽히 방지할 수 있습니다.

6. 데이터 병합 (Merge)
SQL

MERGE INTO {{vars.table}} AS T USING {{vars.staging_table}} AS S
ON T.unique_row_id = S.unique_row_id
WHEN NOT MATCHED THEN INSERT (...)
작동 원리: "지문(unique_row_id)을 대조해보고, 최종 테이블에 없는 녀석들만 새로 넣어라!"라는 뜻입니다. 이미 있는 데이터는 건드리지 않아 효율적입니다.

7. DB 연결 설정 (Plugin Defaults)
YAML

url: jdbc:postgresql://pgdatabase:5432/ny_taxi
작동 원리: 모든 DB 작업에 공통으로 적용될 주소와 계정 정보를 하단에 한 번만 적어줌으로써 코드를 깔끔하게 유지합니다.

💡 스마트한 관전 포인트
이 코드를 보면서 **"왜 바로 테이블에 안 넣고 Staging 테이블을 거치지?"**라고 생각하신다면 이미 엔지니어의 자질이 충분하신 겁니다.

이유: 원본 데이터에는 unique_row_id가 없기 때문입니다. 일단 임시 테이블에 넣고 SQL로 ID를 계산한 뒤, 정제된 데이터만 최종 테이블로 옮기는 것이 훨씬 안전하고 관리가 편하기 때문입니다.

GEM> 쉽게 설명해 드릴게요. **"원본 데이터에 지문(ID)이 없다"**는 건 데이터 엔지니어링에서 아주 피곤한 상황입니다.

1. 현실적인 비유
우리가 학생 명부를 만드는데, 원본 데이터에는 이름, 생일, 주소만 있고 **'학번(ID)'**이 없는 상태라고 생각해보세요.

만약 이 데이터를 그대로 명부에 넣으면, 나중에 "김철수"가 또 들어왔을 때 이 사람이 이미 있는 그 철수인지, 새로 온 동명이인인지 구분할 방법이 없습니다.

2. 왜 Staging(임시 테이블)이 필요한가?
그래서 다음과 같은 공정을 거치는 겁니다.

일단 임시 창고(Staging)에 들이붓기: 원본 CSV 데이터를 그대로 DB의 임시 테이블에 넣습니다. 이때는 학번이 없어도 일단 다 들어갑니다.

지문(unique_row_id) 만들기: SQL의 md5() 함수를 써서 **[VendorID + 픽업시간 + 요금 + 거리]**를 한데 섞어 고유한 문자열(지문)을 만듭니다.

똑같은 시간에 똑같은 거리를 가서 똑같은 요금을 낸 데이터라면 지문이 똑같이 나오겠죠?

검문소 통과(Merge): 이제 이 지문을 가지고 최종 테이블과 비교합니다.

"이 지문, 이미 최종 테이블에 있네? 그럼 가짜(중복)니까 버려!"

"이 지문은 처음 보네? 새로 들어온 데이터구나, 저장!"

3. 결론적으로 "이유"는 이렇습니다.
만약 임시 테이블(Staging) 없이 원본 데이터를 바로 최종 테이블에 넣으려고 하면, 중복 체크를 할 '기준'이 없어서 똑같은 택시 운행 기록이 실행할 때마다 2배, 3배로 계속 쌓이게 됩니다.

데이터가 뻥튀기되는 대참사를 막기 위해, 잠시 임시 테이블에 가둬두고 '지문'을 찍어준 뒤에 정식으로 입국(최종 테이블 저장)시키는 것입니다.

이해가 좀 되셨나요? 이 방식 덕분에 우리가 같은 연도/월 데이터를 실수로 두 번 실행해도 DB에는 중복 데이터 없이 깔끔하게 유지되는 겁니다. 이게 바로 '멱등성(Idempotency)'이라는 중요한 엔지니어링 개념이기도 합니다! 😊

2.4.1 - ETL vs ELT
2.3 버전에서 Kestra 내부에 ETL 파이프라인을 구축했습니다.

추출: 먼저 GitHub에서 데이터셋을 추출합니다.
변환: 다음으로 파이썬을 사용하여 변환합니다.

이는 업계 전반에 걸쳐 매우 표준적인 방식이지만, 클라우드 환경에서는 순서를 바꾸는 것이 더 나은 경우도 있습니다. 옐로우 택시 데이터처럼 대규모 데이터 세트를 다룰 때는 데이터를 추출하여 데이터 웨어하우스에 직접 로드한 다음, 데이터 웨어하우스에서 직접 변환 작업을 수행하는 것이 유리할 수 있습니다. BigQuery를 사용할 때는 ELT(추출 및 로드) 방식을 사용하겠습니다.

추출: 먼저 GitHub에서 데이터셋을 추출합니다.
로드: 다음으로, 이 데이터셋(이 경우 CSV 파일)을 데이터 레이크(Google Cloud Storage)에 로드합니다.
변환: 마지막으로, 데이터 레이크의 데이터를 사용하여 변환을 수행하는 

테이블을 데이터 웨어하우스(BigQuery) 내부에 생성할 수 있습니다.
