모듈 5: 데이터 플랫폼
개요
이 모듈에서는 데이터 플랫폼에 대해 알아봅니다. 데이터 플랫폼은 데이터 수집부터 분석에 이르기까지 전체 데이터 수명 주기를 관리하는 데 도움이 되는 도구입니다.

데이터 플랫폼의 예로 Bruin을 사용하겠습니다.
https://getbruin.com/

Bruin은 여러 도구를 하나의 플랫폼에 통합합니다.

* 데이터 수집(소스에서 데이터 웨어하우스로 데이터 추출)
* 데이터 변환(정제, 모델링, 집계)
* 데이터 오케스트레이션(일정 관리 및 종속성 관리)
* 데이터 품질(내장된 검사 및 유효성 검사)
* 메타데이터 관리(계보, 문서화)


Bruin 시작하기

설치
$curl -LsSf https://getbruin.com/install/cli | sh
$bruin version

프로젝트 초기화
$bruin init zoomcamp my-pipeline
$cd my-pipeline

핵심 개념
* 자산: 모든 데이터 아티팩트(테이블, 뷰, 파일, 머신러닝 모델 등)
* 파이프라인: 의존성 순서대로 함께 실행되는 자산 그룹
* 환경: 명명된 연결 구성(예: default, production)
* 연결: 데이터 소스 및 대상에 대한 자격 증명

파트 1: 데이터 플랫폼이란 무엇인가?

학습 목표
데이터 플랫폼의 정의와 필요성 이해

Bruin이 현대 데이터 스택(Modern Data Stack)에서 차지하는 위치 파악

Bruin의 핵심 개념(Abstractions)인 자산(Asset), 파이프라인(Pipeline), 환경(Environment), 연결(Connection) 이해

1.1 현대 데이터 스택의 구성 요소
데이터 플랫폼은 데이터의 수명 주기를 관리하기 위해 다음과 같은 필수 기능을 수행합니다.

데이터 추출 및 수집 (Data Extraction/Ingestion): 다양한 소스 시스템에서 데이터 웨어하우스로 데이터를 가져오는 과정

데이터 변환 (Data Transformation): raw 데이터를 정제, 모델링 및 집계하는 과정 (ELT 과정 중 **'T'**에 해당)

데이터 오케스트레이션 (Data Orchestration): 파이프라인의 실행 일정을 관리하고 자산 간의 의존 관계를 제어하는 과정

데이터 품질 및 거버넌스 (Data Quality/Governance): 데이터의 정확성과 일관성을 보장하고 검증하는 과정

메타데이터 관리 (Metadata Management): 데이터의 계보(Lineage), 소유권, 문서화 등을 추적하는 과정



1.2 Bruin의 역할
Bruin은 수집 + 변환 + 품질 + 오케스트레이션 기능을 단 하나의 도구로 통합한 플랫폼입니다.

Airflow와 유사하게 의존성 해결, 스케줄링, 재시도 등 파이프라인 오케스트레이션을 처리합니다.

**"Airbyte, Airflow, dbt, Great Expectations의 장점만을 모아 만든 도구"**라고 이해하면 쉽습니다.

로컬 환경, 가상 머신(VM), CI/CD 환경 어디서나 실행 가능하며 특정 vendor에 종속되지 않습니다.

Apache 라이선스를 따르는 오픈 소스 프로젝트입니다.



1.3 Bruin의 설계 원칙 (핵심 요약)
코드 중심 관리: 모든 설정은 버전 관리가 가능한 텍스트 파일로 관리됩니다. (UI나 별도의 데이터베이스 설정 불필요)

다양한 기술 스택 지원: 실제 파이프라인에서 필요한 SQL, Python, R 등 여러 언어를 혼합하여 사용할 수 있습니다.

유연한 연결: 단일 파이프라인 내에서 다양한 소스와 대상을 자유롭게 조합할 수 있습니다.

품질 우선주의: 데이터 품질 검사는 부수적인 기능이 아니라 플랫폼의 핵심 기능으로 내장되어 있습니다.

빠른 피드백 루프: 강력한 CLI를 통해 로컬에서도 신속하게 개발하고 테스트할 수 있습니다.



1.4 핵심 개념
자산 (Asset): 가치를 지닌 모든 데이터 결과물을 의미합니다. (테이블, 뷰, 파일, 머신러닝 모델 등)

파이프라인 (Pipeline): 의존성 순서에 따라 함께 실행되는 자산들의 그룹입니다.

환경 (Environment): 연결 설정(Connection Configs)에 붙여진 이름입니다. (예: default, production) 이를 통해 동일한 파이프라인을 로컬과 운영 환경에서 각각 실행할 수 있습니다.

연결 (Connection): 외부 데이터 소스 및 대상에 인증하기 위한 자격 증명(Credentials) 정보입니다.

파이프라인 실행 (Pipeline Run): 특정 날짜와 구성 설정을 가지고 실행되는 파이프라인의 개별 인스턴스입니다.

그 이유는 {{ var.xxx }} 문법은 pipeline.yml이 아니라, 이 파이프라인이 관리하는 "개별 에셋 파일(SQL이나 Python)" 안에서 쓰이기 때문입니다.

💡 왜 pipeline.yml에는 안 보이나요?
pipeline.yml은 전체 파이프라인의 **설계도(전역 설정)**입니다. 여기서 변수를 **정의(Define)**만 해두면, 실제로 그 변수를 **사용(Reference)**하는 곳은 개별 작업 파일들입니다.

예를 들어, 사용자님의 프로젝트 폴더 어딘가에 있을 SQL 파일들을 열어보시면 이런 식으로 적혀 있을 겁니다.

1. SQL 에셋 예시 (staging/trips.sql 등)

SQL
SELECT * FROM ingestion.trips
-- 여기서 변수를 사용합니다!
WHERE taxi_type IN {{ var.taxi_types | inclause }}
2. Python 에셋 예시 (ingestion/trips.py 등) Python에서는 템플릿 문법 대신 환경 변수를 통해 이 설정값을 읽어옵니다.

Python

import json

🛠️ pipeline.yml의 역할: "변수 선언"
현재 사용자님의 pipeline.yml 하단에 있는 이 부분이 바로 **"앞으로 모든 에셋에서 taxi_types라는 변수를 쓸 건데, 기본값은 'yellow'와 'green'이야"**라고 선언하는 문장입니다.

📝 요약
pipeline.yml: 변수를 정의하는 곳 (여기선 {{ }}를 쓰지 않음).

.sql 파일: 변수를 실제 쿼리에 박아넣는 곳 (여기서 {{ var.taxi_types }} 사용).

.py 파일: 변수를 프로그램 로직으로 읽어오는 곳.

사용자님이 보신 주석 # - In SQL/YAML assets: reference as {{ var.my_variable }}는 **"나중에 SQL 파일 짤 때 이렇게 써라~"**라는 친절한 가이드라인인 셈입니다.

혹시 SQL 파일 중에서 저 문법이 어떻게 쓰였는지 직접 확인해 보고 싶은 파일이 있으신가요? (예: staging/trips.sql) 그 파일을 열어보시면 주석의 의미를 바로 깨달으실 겁니다! 😊

파이썬 자산인 trips.py를 완성할 차례군요. 이 파일은 Bruin의 Python Materialization 기능을 사용하는 핵심 파일입니다.

Bruin의 특징은 파이썬 함수에서 pandas DataFrame을 return하기만 하면, 설정에 맞춰 대상 데이터베이스(DuckDB)에 테이블을 자동으로 생성하고 데이터를 넣어준다는 점입니다.

assets/ingestion/trips.py 전체 코드
기존 주석과 TODO를 모두 대체할 수 있는 완성된 코드입니다.

"""@bruin
name: ingestion.trips
type: python
connection: duckdb
image: python:3.11

materialization:
  type: table
  strategy: append

columns:
  - name: vendor_id
    type: integer
  - name: pickup_datetime
    type: timestamp
  - name: trip_distance
    type: float
  - name: payment_type
    type: integer
  - name: taxi_type
    type: string
  - name: extracted_at
    type: timestamp
@bruin"""

import os
import json
import pandas as pd
from datetime import datetime

def materialize():
    """
    Bruin의 Python Materialization 기능을 사용하여 데이터를 생성하고 
    자동으로 DuckDB의 ingestion.trips 테이블에 데이터를 추가(append)합니다.
    """
    
    # 1. 실행 기간(Window) 환경 변수 로드
    # Bruin run 실행 시 전달되는 시작 날짜를 사용합니다.
    start_date = os.getenv("BRUIN_START_DATE", "2024-04-01")
    
    # 2. 파이프라인 변수(taxi_types) 로드
    # pipeline.yml에 정의된 taxi_types 변수를 읽어옵니다.
    bruin_vars = json.loads(os.getenv("BRUIN_VARS", "{}"))
    taxi_types = bruin_vars.get("taxi_types", ["yellow", "green"])

    all_data = []

    # 3. 데이터 생성 비즈니스 로직
    for t_type in taxi_types:
        # 각 택시 타입별로 샘플 데이터 생성
        data = pd.DataFrame({
            'vendor_id': [1, 2],
            'pickup_datetime': [pd.to_datetime(start_date)] * 2,
            'trip_distance': [2.5, 3.8],
            'payment_type': [1, 2],
            'taxi_type': [t_type, t_type]
        })
        
        # 윈도우 환경에서 pyarrow 타임존 에러를 방지하기 위해 
        # 날짜 데이터를 안전하게 문자열로 변환합니다.
        data['pickup_datetime'] = data['pickup_datetime'].dt.strftime('%Y-%m-%d %H:%M:%S')
        all_data.append(data)

    # 생성된 데이터가 없을 경우 빈 데이터프레임 반환
    if not all_data:
        return pd.DataFrame()

    # 4. 최종 데이터 결합 및 추출 시간(lineage용) 추가
    final_df = pd.concat(all_data, ignore_index=True)
    final_df['extracted_at'] = datetime.now().strftime('%Y-%m-%d %H:%M:%S')

    # Bruin에게 데이터프레임을 반환하면, Bruin이 이를 연결된 DuckDB 테이블에 적재합니다.
    return final_df


💡 코드 포인트 가이드
@bruin 주석 블록: 파일 상단과 하단의 주석 안에 YAML 설정을 넣어야 Bruin이 이를 인식합니다.

strategy: append: 수집(Ingestion) 단계에서는 기존 데이터를 유지하면서 새로운 데이터를 쌓는 append 전략이 일반적입니다. (나중에 중복은 Staging에서 처리합니다.)

materialize() 함수: 이 함수 이름은 고정입니다. Bruin은 이 함수가 반환하는 객체를 추적합니다.

BRUIN_VARS: 우리가 pipeline.yml에서 설정한 변수들이 JSON 형태로 들어오므로 json.loads로 파싱해서 사용합니다.

    t.vendor_id,
    t.pickup_datetime,
    t.trip_distance,
    t.payment_type,
    p.payment_type_name as payment_type_description,
    t.taxi_type,
    t.extracted_at

    ON t.payment_type = p.payment_type_id

1. 왜 그 경로를 쓰나요?
물리적 위치: 실제로 윈도우 탐색기에서 e:/it_spaces/ai/zoomcamp/ 폴더로 들어가면 duckdb.db라는 이름의 파일이 존재하기 때문입니다.

2. 위치를 바꿀 수 있나요?

YAML
connections:
  duckdb:
    type: duckdb
    # 예: 바탕화면이나 다른 폴더로 바꾸고 싶을 때

이렇게 바꾸고 다시 bruin run을 하면, 이제부터는 모든 데이터가 저 새로운 경로에 쌓입니다.

방법 B: 이미 있는 파일 옮기기 이미 데이터가 들어있는 2.3MB짜리 파일을 옮기고 싶다면:

윈도우 탐색기에서 파일을 잘라내기 해서 원하는 곳에 붙여넣습니다.

조회할 때 터미널에서 바뀐 경로를 입력하면 됩니다.

예: duckdb d:/새폴더/duckdb.db

나> 간략설명
GEM> Part 3의 핵심은 **"데이터가 공장에서 완제품이 되는 과정"**을 설계하는 것입니다. 각 단계를 요약해 드릴게요.

1. 파이프라인 3단계 구조 (Architecture)
데이터는 총 세 곳의 레이어를 거치며 정제됩니다.

Ingestion (수집): 외부(NYC Taxi API 등)에서 가공되지 않은 날짜별 로우 데이터를 가져와 DB에 그대로 쌓는 단계입니다.

Staging (정제): 중복을 제거하고, 형식을 맞추고, 다른 테이블(결제 수단 등)과 결합하여 깨끗한 중간 데이터를 만듭니다.

Reports (보고): 정제된 데이터를 바탕으로 월별 매출, 총 승객 수 등 최종 분석 지표를 계산합니다.

2. 세 가지 자산 유형 (Asset Types)
Python: API 호출이나 복잡한 데이터 추출처럼 동적인 작업에 사용합니다 (trips.py).

SQL: DB 내부에서 데이터를 변환하고 가공할 때 사용합니다 (trips.sql).

Seed: 결제 타입 코드표처럼 변하지 않는 **고정된 데이터(CSV)**를 DB 테이블로 만들 때 씁니다.

3. 구체화 전략 (Materialization)
데이터를 매번 처음부터 다 새로 고침하면 비효율적입니다.

Append (추가): 수집 단계에서 기존 데이터 뒤에 새 데이터를 계속 붙입니다.

Time Interval (증분 처리): 특정 기간(예: 2024년 1월)의 데이터만 골라내어 처리함으로써 속도를 높이고 자원을 아낍니다.

4. 품질 검사 및 종속성 (Checks & Dependencies)
Quality Checks: "금액이 마이너스인가?", "ID가 비어있는가?" 같은 조건을 걸어 데이터 오류를 자동으로 잡아냅니다.

DAG (종속성): "수집이 끝나야 정제를 시작한다"는 순서를 Bruin에게 알려주어 파이프라인이 엉키지 않게 합니다.

한 줄 요약: "파이썬으로 가져오고, SQL로 닦아서, 최종 보고서를 만드는 자동화 흐름을 구축하는 과정"입니다.

3. 주의사항 (매우 중요)
DuckDB는 단일 프로세스 데이터베이스입니다.

중요: duckdb duckdb.db로 접속해서 세션을 열어두면, 파일이 잠기기 때문에 다시 bruin run을 실행할 때 에러가 날 수 있습니다. 확인이 끝나면 반드시 .exit 또는 Ctrl+D로 종료하고 나오셔야 합니다.
