Module 6: Batch Processing 


배치 처리(Batch Processing)는 데이터 엔지니어링의 핵심 중 하나로, 대량의 데이터를 일정 주기마다 한꺼번에 처리하는 방식입니다. 이 모듈에서는 주로 Apache Spark를 중심으로 분산 컴퓨팅의 원리와 대규모 데이터 처리 기법을 다루게 될 것입니다.

본격적인 시작에 앞서, 이번 모듈에서 핵심적으로 짚고 넘어가야 할 주요 키워드와 흐름을 정리해 드립니다.

1. 배치 처리의 핵심 개념
실시간(Streaming) 처리와 대비되는 배치 처리의 특징을 이해하는 것이 첫걸음입니다.

Latency vs Throughput: 지연 시간보다는 전체적인 처리량(Throughput)에 집중합니다.

분산 컴퓨팅: 데이터를 여러 노드에 나누어 병렬로 처리하는 메커니즘을 배웁니다.


2. Apache Spark Deep Dive
모듈 6의 주인공입니다. 단순히 코드 작성을 넘어 내부 동작 원리를 파악하는 것이 중요합니다.


Spark Cluster Architecture: Master와 Worker(Executor)의 관계.

DataFrames & Spark SQL: 정형 데이터를 다루는 효율적인 인터페이스.

Resilient Distributed Datasets (RDD): Spark의 근간이 되는 추상화 모델.

Transformations vs Actions: Lazy Evaluation(지연 실행)의 개념과 성능 최적화.

3. 성능 최적화 전략
실무에서 가장 많이 고민하게 될 부분입니다.

Partitioning: 데이터를 어떻게 나눌 것인가?

Shuffling: 네트워크를 통한 데이터 이동을 어떻게 최소화할 것인가?

Join Strategies: Broadcast Join 등 상황에 맞는 조인 방식 선택.

학습 팁
PySpark 환경 구축: 로컬 환경이나 클라우드(Databricks, GCP Dataproc 등)에서 Spark 세션을 생성하는 것부터 익숙해지세요.

UI 활용: Spark UI(4040 포트)를 통해 내가 짠 코드가 어떻게 Stage와 Task로 나뉘는지 시각적으로 확인하는 습관을 들이면 좋습니다.

준비되셨다면, **"특정 데이터셋을 활용한 PySpark 기초 실습"**이나 "Spark 아키텍처 상세 설명" 중 어떤 것부터 시작해 볼까요? 원하시는 부분을 말씀해 주시면 바로 가이드를 시작해 드리겠습니다.

GEM> python test_spark.py는 성공했는데 uv run python test_spark.py가 작동하지 않은 이유는 uv가 관리하는 가상환경과 지금 만든 venv가 서로 다르기 때문입니다.

이유를 명확히 정리해 드릴게요.

1. 가상환경의 불일치
python 사용 시: 현재 zakard님이 직접 만드신 venv를 source activate로 활성화한 상태죠? 그래서 그 안에 설치된 pyspark 라이브러리를 바로 찾아낼 수 있습니다.

uv run 사용 시: uv는 기본적으로 프로젝트 루트의 pyproject.toml이나 자체적인 관리 메커니즘을 따릅니다. 별도의 설정을 하지 않았다면 uv는 zakard님이 수동으로 만든 venv를 무시하고 자기만의 깨끗한 환경에서 실행하려고 합니다. 그 안에는 당연히 pyspark가 설치되어 있지 않으니 에러가 난 것입니다.

2. 환경 변수 인식 문제
uv run은 독립적인 실행 환경을 격리해서 구축하려고 합니다. 아까 우리가 설정한 JAVA_HOME이나 PATH가 uv의 격리된 실행 환경까지 제대로 전달되지 않았을 가능성도 큽니다.

3. 결론: 어떤 걸 써야 할까?
지금은 이미 직접 만드신 venv를 활성화해서 사용 중이므로, 굳이 uv를 섞어서 쓰실 필요가 없습니다.

GEM> zakard님, df.repartition(24)는 한마디로 **"거대한 작업을 24명의 일꾼에게 골고루 나눠주기 위한 준비 운동"**입니다.

📋 repartition(24)의 용도
1. "병렬 처리 극대화" (가장 큰 이유)
Spark는 데이터를 여러 개의 조각(Partition)으로 나누어 동시에 처리합니다.

만약 데이터 조각이 1개라면? 아무리 CPU 코어가 많아도 일꾼 1명만 일하고 나머지는 놉니다.

repartition(24)를 하면? 데이터를 24개로 쪼개서 24명의 일꾼(Core)이 동시에 달려들 수 있게 만듭니다.

2. "저장되는 파일 개수 결정"
이후에 df.write.parquet()을 실행하면, 쪼개진 개수만큼 파일이 생깁니다.

repartition(24) 후 저장하면 결과 폴더 안에 24개의 .parquet 파일이 생성됩니다.

나중에 이 데이터를 다시 읽을 때도 24개 조각을 동시에 읽어올 수 있어 훨씬 빨라집니다.

3. "데이터 섞기 (Shuffle)"
데이터가 특정 조각에만 너무 많이 몰려 있으면(Data Skew 현상), 어떤 일꾼은 금방 끝나고 어떤 일꾼은 밤을 샙니다. repartition은 데이터를 전체적으로 다시 골고루 섞어주는 역할을 합니다.

🔍 왜 하필 '24'인가요? (Data Camp/ZoomCamp 맥락)
보통 실습에서 24를 쓰는 이유는 해당 데이터(2021년 1월 FHVHV 데이터)의 크기가 약 700MB~1GB 정도 되기 때문입니다.

너무 잘게 쪼개면(1000 등) 관리 비용(Overhead)이 커집니다.

너무 크게 쪼개면(1 등) Spark의 장점인 병렬 처리를 못 합니다.

24는 개별 파일 크기를 적절하게(약 128MB 이하) 유지하면서 병렬성을 챙기기에 적당한 숫자입니다.

⚠️ 주의할 점
repartition은 데이터 전체를 네트워크를 통해 주고받으며 다시 섞는 작업(Shuffle)이기 때문에, 비용(시간)이 많이 드는 작업입니다. 그래서 꼭 필요한 때(저장 직전이나 대규모 연산 직전)에만 전략적으로 사용합니다.

좋은 질문입니다, zakard님! 분산 처리의 핵심 원리를 꿰뚫고 계시네요.

결론부터 말씀드리면, "남은 1개가 끝날 때까지 전체 작업은 종료되지 않고 기다려야 합니다." 하지만 Spark는 이미 24개로 분할된 데이터를 더 이상 쪼개지는 않습니다.

이 과정을 구체적으로 설명해 드릴게요.

1. "마지막 1개가 끝날 때까지 기다리는가?" → YES
Spark에서 하나의 작업(Job)은 여러 개의 단계(Stage)로 나뉩니다. repartition(24) 후에 파일을 저장하는 작업은 하나의 스테이지로 묶이는데, 이때 **동기화(Synchronization)**가 일어납니다.

23개의 조각(Task)이 1초 만에 끝나더라도, 마지막 1개가 데이터가 많거나 PC 사정으로 10초가 걸린다면 전체 저장 작업은 10초가 걸립니다.

이 현상을 데이터 엔지니어링 용어로 "Tail Latency" 또는 "Straggler(뒤처지는 일꾼)" 문제라고 부릅니다.

2. "데이터를 더 분할하는가?" → NO
이미 repartition(24)를 통해 **"이 데이터는 24개의 파티션이다"**라고 명시한 순간, Spark는 이를 24개의 독립된 태스크(Task)로 확정 짓습니다.

실행기(Executor)의 코어(Core)가 만약 4개뿐이라면, 한 번에 4개씩 6회에 걸쳐 24개를 처리합니다.

실행기가 아무리 많아도(예: 100개), 이미 파티션이 24개뿐이라면 24개만 일하고 나머지 76개는 놉니다.

즉, 한 번 정해진 24개의 파티션은 실행기 사정에 맞춰 더 잘게 쪼개지지 않습니다.

3. 왜 24개로 쪼개는 게 중요할까요?
만약 데이터를 쪼개지 않고 1개인 상태로 두면 어떻게 될까요?

아무리 좋은 엘리트북(코어가 여러 개라도)이라도 CPU 코어 1개만 열심히 일합니다.

데이터가 너무 크면 메모리 부족(Out Of Memory) 에러가 날 확률이 높습니다.

24개로 쪼개면:

데이터가 약 1/24 크기로 작아져서 메모리 부담이 줄어듭니다.

CPU 코어 여러 개가 동시에 작업을 나눠서 할 수 있습니다. (예: 8코어면 3바퀴만 돌면 끝남)

💡 요약하자면
"24개로 나눈 이상 Spark는 더 이상 쪼개지 않고 정해진 24개의 태스크를 수행합니다. 그리고 전체 작업이 완료되려면 가장 느린 마지막 1개가 끝날 때까지 기다려야 합니다."

그래서 데이터 엔지니어들은 데이터가 특정 파티션에 몰리지 않게(Data Skew) 골고루 나누는 것을 매우 중요하게 생각합니다.

Pandas와 Spark 데이터 프레임의 핵심 차이
첫째, 작업을 처리하는 방식이 다릅니다. Pandas는 코드를 입력하는 즉시 메모리에 데이터를 올리고 바로 계산해 버리는 '즉시 실행(Eager)' 방식입니다. 반면, Spark는 실제로 데이터를 눈으로 확인하거나 저장하라는 명령(show, write 등)을 내리기 전까지는 실제 계산을 하지 않고 어떻게 처리할지 **'계획(Lazy)'**만 세웁니다. 그래서 아까 repartition(24)를 했을 때도 바로 파일이 안 생기고 저장 명령(df.write.parquet('fhvhv/2021/01/', mode='overwrite'))을 할 때서야 움직였던 거예요.

둘째, 데이터가 어디에 위치하는지가 다릅니다. Pandas는 데이터를 내 컴퓨터의 메모리(RAM) 한 곳에 몽땅 다 집어넣고 처리합니다. 하지만 Spark는 방금 실습하신 것처럼 데이터를 여러 개의 **파티션(Partition)**으로 쪼개서, 여러 개의 CPU 코어나 여러 대의 컴퓨터에 분산시켜서 올려둡니다.

셋째, 처리할 수 있는 데이터의 한계가 다릅니다. Pandas는 내 컴퓨터 메모리 용량보다 데이터가 크면 바로 멈춰버립니다(OOM 에러). 하지만 Spark는 메모리보다 훨씬 큰 데이터라도 조각조각(718MB를 24개로 나눈 것처럼) 내서 차례대로 처리할 수 있기 때문에 훨씬 거대한 데이터를 다루기에 유리합니다.

💡 "스레드 파일 처리" 한 줄 요약
아까 718MB 파일을 처리할 때, 컴퓨터 안의 여러 일꾼(Thread)이 각각의 파티션을 동시에 붙잡고 처리했다는 뜻입니다. "한 명의 요리사가 큰 통을 젓는 게 아니라, 24명의 요리사가 작은 냄비를 동시에 끓였다"고 생각하시면 정확합니다.

이제 이 '분산된 조각들'을 가지고 필터링을 하거나 합계를 구하는 Spark 전용 조작법을 배울 차례라는 뜻입니다.

데이터가 잘 저장된 걸 확인하셨으니, 이제 이 24개 조각에서 "전체 데이터가 총 몇 줄인지" 한 번 세어보시겠어요? 🦾



💡 "스레드 파일 처리"는 또 무슨 말?
아까 repartition(24)를 하셨죠?

스레드(Thread) 처리: 24개의 조각을 각각의 일꾼(Thread/Core)이 동시에 처리했다는 뜻입니다.

하나의 큰 덩어리를 처리하는 게 아니라, 여러 줄기(스레드)로 나누어 병렬로 작업했다는 점을 강조하는 표현입니다.

왜 문제가 안 되는지 3가지 이유로 정리해 드릴게요.

1. 데이터는 안전합니다
아까 dir이나 ls에서 보신 깨진 글자(2썡, 삤썑)는 윈도우 운영체제가 파일의 "수정한 날짜"를 한글로 출력하려다 발생한 것입니다. 정작 중요한 Parquet 파일 내부의 데이터나 CSV 안의 내용물은 인코딩이 전혀 다른 체계(UTF-8)로 안전하게 저장되어 있습니다.

2. Spark는 똑똑합니다
다음 단원에서 Spark로 데이터를 읽고 분석할 때, Spark는 시스템의 한글 설정과 상관없이 파일의 바이너리 값을 직접 읽습니다. df.show()를 했을 때 데이터프레임 안의 숫자나 영문자들은 아주 깔끔하게 나올 거예요.

3. 분석 결과는 영어/숫자 위주입니다
데이터 엔지니어링 과정에서 다루는 컬럼명(hvfhs_license_num, pickup_datetime 등)과 데이터 값들은 대부분 영문과 숫자입니다. 윈도우 터미널이 "오후 8시"라는 글자를 못 보여준다고 해서, 1+1 계산 결과나 데이터 필터링 결과가 틀려지지는 않습니다.

가끔씩 등록이 지연되는 일이 있는데 이러한 작업들이 지연(lazy)실행되기 때문입니다. 

Spark에서는 즉시 실행되는 작업과 즉시 실행되지 않는 작업을 구분하는데, 이를 Actions vs Transformations(액션과 변환) 이라고 합니다. 즉시 실행되지 않는 작업은 변환이라고 하며 데이터를 변환하는데 사용됩니다. 예: 열선택, 함수적용 등. 

df.select('pickup_datetime','dropoff_datetime','PULocationID','DOLocationID').filter(df.hvfhs_license_num == 'HV0003').show()

의 생리:
df -> select (trans(lazy)) -> filter(trans(lazy)) -> show()(action(eager)).take(5)

즉, show는 전체실행을 트리거하는 역할을 합니다. 


Transformations - lazy(not executed immediately):
* Selecting columns
* Filtering
* joins
* group by
..

Actions - eager(executed immediately):
* show, take, head
* write

이것보다 다음에 다룰 SQL접근이 더 보기 좋고 표현력도 뛰어나다고 생각합니다. 

어쨌든, 이것이 Actions와 Transformations의 주요 차이점입니다.

🛠️ 코드 기능별 요약
1. 그룹화 기준 (Group By 1, 2, 3)
PULocationID (revenue_zone): 승차 위치별로 묶습니다.

date_trunc('month', ...): 날짜를 '월' 단위로 자릅니다. (예: 1월 15일 → 1월 1일로 통일)

각 항목별(fare, tip, tax, total 등) **합계(SUM)**를 구하여 해당 월, 해당 구역에서 발생한 매출의 총합을 계산합니다.

3. 추가 통계 (Additional calculations)
AVG: 한 달 동안 한 번의 운행당 평균 몇 명이 탔는지, 평균 얼마나 멀리 갔는지를 계산합니다.

🛠️ 코드 해석
.join(...): 두 개의 데이터프레임을 특정 기준에 따라 옆으로 이어 붙입니다.

on=['hour', 'zone']: 조인 기준(Key)입니다. **'시간(hour)'**과 **'지역(zone)'**이 정확히 일치하는 행끼리 매칭시킵니다.

how='outer': 외부 조인(Full Outer Join) 방식입니다.

Green 데이터만 있는 시간/지역도 포함합니다.

Yellow 데이터만 있는 시간/지역도 포함합니다.

둘 다 있는 경우엔 한 줄에 나란히 붙입니다.

어느 한 쪽에 데이터가 없다면 해당 컬럼은 null로 채워집니다.

💡 왜 이렇게 하나요?
데이터 유실 방지: inner 조인을 쓰면 Green이나 Yellow 중 한 곳에만 기록이 있는 시간/지역 데이터가 삭제됩니다. outer를 써야 전체 택시 시장의 규모를 정확히 파악할 수 있습니다.

비교 분석: 동일한 시간과 장소에서 Green과 Yellow의 수익(amount) 및 운행 건수(number_records)를 한눈에 비교하기 위해 컬럼을 옆으로 나열하는 것입니다.

왼쪽 테이블(df_join): 택시 운행 통계가 담긴 테이블로, 지역이 숫자 번호(zone)로 기록되어 있습니다 (예: 132).

데이터 병합:

나> rdd란
GEM> zakard님, **RDD(Resilient Distributed Dataset)**는 Spark의 가장 기초가 되는 데이터 구조이자 '뿌리'라고 할 수 있습니다. 지금 보시는 df_green.rdd 코드는 편리한 DataFrame이라는 껍데기를 벗기고, 그 안의 날것(Low-level)의 데이터를 직접 만지겠다는 뜻입니다.

주요 특징을 쉽게 풀어드릴게요.

💡 RDD의 핵심 3요소
Resilient (회복력 있는):
데이터 처리 중에 특정 서버(Node)가 고장 나도, 데이터를 어떻게 만들었는지 기록(Lineage)을 가지고 있어 스스로 복구할 수 있습니다.

Distributed (분산된):
하나의 큰 데이터를 여러 컴퓨터에 나누어서 저장하고 병렬로 처리합니다.

Dataset (데이터 세트):
단순한 파이썬 객체(리스트, 튜플 등)들의 모임입니다.


🔍 DataFrame vs RDD: 무엇이 다른가요? DataFrame과 RDD의 차이점

비유 (구조)
DataFrame은 제목(컬럼명)이 붙어 있는 엑셀 시트나 SQL 테이블과 같습니다. 데이터에 구조가 잡혀 있죠.

RDD는 이름표가 없는 그냥 데이터 상자입니다. 파이썬의 리스트(List)나 튜플(Tuple) 같은 객체들이 뭉텅이로 들어있다고 생각하면 됩니다.


최적화 (누가 똑똑한가)	

DataFrame은 **Spark 엔진(Catalyst Optimizer)**이 알아서 "이 쿼리를 어떻게 실행해야 제일 빠를까?" 고민하고 최적의 경로를 찾습니다 (자동모드).

RDD는 Spark가 개입하지 않습니다. 개발자가 직접 map, filter 같은 로직을 어떻게 짤지 고민해야 합니다 (수동모드).


사용성 (편의성)

DataFrame은 우리가 흔히 쓰는 SQL 쿼리나 Pandas 스타일의 함수로 아주 쉽고 빠르게 데이터를 가공할 수 있습니다.

RDD는 파이썬 함수를 직접 만들어서 데이터를 하나하나 주물러야 하므로 코드가 조금 더 복잡해질 수 있습니다.


용도 (언제 쓰는가)

DataFrame은 대부분의 일반적인 데이터 분석과 비즈니스 로직 처리에 사용됩니다.

RDD는 데이터의 구조가 너무 복잡하거나, Spark SQL에서 제공하지 않는 특수한 파이썬 라이브러리를 써서 세밀한 제어가 필요할 때 사용합니다.

💡 한 줄 요약
"DataFrame은 알아서 척척 해주는 스마트한 '자동 세차기'이고, RDD는 내 손으로 직접 꼼꼼히 닦는 '손 세차'입니다."

지금 노트북에서는 total_amount를 합산하고 날짜를 직접 조작하기 위해, 더 세밀한 컨트롤이 가능한 '손 세차(RDD)' 방식을 연습하고 계신 거예요



🛠️ 왜 지금 RDD를 쓰나요?
노트북 코드를 보시면 prepare_for_grouping 같은 **사용자 정의 함수(UDF)**를 직접 만들어서 데이터를 아주 세밀하게 가공하고 있습니다.

row.lpep_pickup_datetime.replace(...) 처럼 파이썬의 날짜 객체 기능을 직접 활용하거나,

(key, value) 형태의 튜플로 구조를 완전히 바꿔서 reduceByKey 같은 강력한 연산을 쓰기 위함입니다.

한 줄 요약: "Spark가 알아서 해주는 자동모드(DataFrame)를 끄고, 내 입맛대로 데이터를 주무르기 위해 **수동모드(RDD)**로 들어온 것"입니다.

이제 이 RDD를 가지고 map 연산을 통해 데이터를 어떻게 변형하는지 구체적으로 살펴볼까요?

def prepare_for_grouping(row): 
    hour = row.lpep_pickup_datetime.replace(minute=0, second=0, microsecond=0)
    zone = row.PULocationID
    key = (hour, zone)
    
    amount = row.total_amount
    count = 1
    value = (amount, count)

    return (key, value)

def calculate_revenue(left_value, right_value):
    left_amount, left_count = left_value
    right_amount, right_count = right_value

    output_count = left_count + right_count
    
    return (output_amount, output_count)

🚀 메모리 증설을 포함한 최종 실행 명령어

Bash
gcloud dataproc jobs submit pyspark \
    gs://de-zoomcamp-zakard-2026/code/spark_bigquery_v2.py \
    --cluster=de-zoomcamp-cluster \
    --region=us-central1 \
    --jars=gs://spark-lib/bigquery/spark-3.4-bigquery-0.44.0.jar \
    --properties=spark.driver.memory=4g,spark.executor.memory=4g


🔍 왜 메모리 부족이 발생했을까요?
데이터 셔플링: 파티션된 Parquet 파일을 읽어 BigQuery 전용 포맷으로 변환하는 과정에서 메모리 사용량이 일시적으로 급증합니다.

드라이버 역할: BigQuery 커넥터는 쓰기 작업을 관리할 때 드라이버의 메모리를 일부 사용합니다. 기본 설정(보통 1~2GB)으로는 부족할 수 있습니다.

데이터 크기: 2020년 전체 데이터를 처리하다 보니 메모리 압박이 생긴 것입니다.

간단히 말해서, 클러스터는 **"복잡하고 거대한 계산을 여러 대의 컴퓨터가 나누어 처리하도록 묶어놓은 팀"**입니다.

🏗️ Dataproc 클러스터의 3대 핵심 구성 요소
클러스터를 만들 때 우리가 설정했던 것들이 각각 이런 역할을 합니다.

마스터 노드 (Master Node / Driver):

역할: 팀장님입니다.

하는 일: zakard님이 던진 PySpark 코드를 분석해서 "이 일은 1번 컴퓨터가 하고, 저 일은 2번이 해!"라고 업무를 배분합니다. 전체 작업의 스케줄을 관리하죠.

워커 노드 (Worker Nodes / Executors):

역할: 실제 일꾼들입니다.

하는 일: 팀장이 시킨 대로 데이터를 실제로 읽고, 더하고, 정렬하는 노가다(?)를 수행합니다. 컴퓨터 대수가 많을수록(예: 2대 -> 10대) 180만 건의 데이터를 처리하는 속도가 기하급수적으로 빨라집니다.

Hadoop/Spark 에코시스템:

역할: 도구 상자입니다.

하는 일: 대용량 데이터를 다루기 위한 소프트웨어(Spark, Hive 등)가 미리 설치되어 있어, 우리가 복잡한 설치 과정 없이 바로 코드를 돌릴 수 있게 해줍니다.

💡 왜 클러스터를 썼다가 지웠다 하나요?
강력한 파워: 내 노트북(로컬)에서는 10분 걸릴 일이 클러스터에서는 수십 초 만에 끝날 수 있습니다.

휘발성 (Ephemeral): Dataproc의 최대 장점입니다. **"일할 때만 모였다가, 일 끝나면 해쳐모여!"**가 가능합니다.

비용 최적화: 데이터를 저장하는 곳(GCS)과 계산하는 곳(Dataproc)이 분리되어 있어서, 계산이 안 필요한 시간에는 클러스터를 지워버려도 데이터는 안전합니다. 그래서 우리가 계속 **"일 끝나면 지우세요!"**라고 하는 겁니다.
