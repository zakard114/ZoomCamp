[0:15~] 스트림 프로세싱의 기초
이번 주에는 스트림 프로세싱에 대해 집중적으로 다룹니다. 기본적으로 '스트림 프로세싱이란 무엇인가'라는 근본적인 개념부터 살펴볼 예정입니다.

[0:22~] Kafka의 역할과 특징
그다음으로는 Kafka가 무엇인지, 그리고 스트림 프로세싱에서 Kafka가 어떤 핵심적인 역할을 수행하는지 배웁니다. 특히 스트림 프로세싱 데이터가 갖는 메시지 특성(Message Properties)들을 함께 살펴볼 것입니다.

[0:30~] Kafka 핵심 설정 파라미터
Kafka를 제대로 다루기 위해 필수적인 설정값들도 공부합니다.

파티셔닝(Partitioning): 데이터를 어떻게 분산 저장하는가

복제(Replication): 데이터의 안정성을 위해 어떻게 복사본을 만드는가

보관 주기(Retention): 데이터를 얼마나 오래 보관하는가
이러한 파라미터들과 더불어 스트림 프로세싱에서의 시간 처리(Time handling) 개념도 다룹니다.

[0:36~] 프로그래밍 방식으로 데이터 주고받기
이론을 넘어 실제 코드 수준에서 데이터를 다루는 방법을 배웁니다. **Kafka Producer(생산자)**와 **Kafka Consumer(소비자)**를 사용하여 프로그래밍 방식으로 데이터를 Kafka에 넣고 가져오는 과정을 직접 확인하게 됩니다.

[0:52~] 데이터 분산과 실제 사례
스트림 내부에서 데이터가 실제로 어떻게 파티셔닝되어 처리되는지 구체적인 예시와 함께 살펴봅니다. Kafka Streams를 활용한 실무적인 워킹 예제들도 준비되어 있습니다.

[1:01~] Java와 Python(Spark) 예제
기본적인 세션은 Java를 기준으로 설명되지만, Python 사용자가 더 편한 분들을 위해 Spark Streaming을 활용한 Python 예제도 함께 구성했습니다. 본인에게 익숙한 언어로 실습을 따라오시면 됩니다.

[1:08~] 데이터의 규격: Schema와 도구들
마지막으로 스트림 프로세싱에서 **스키마(Schema)**가 왜 중요한지, 그리고 데이터 통합을 위한 Kafka Connect와 SQL로 스트림을 쿼리할 수 있는 ksqlDB에 대해서도 간단히 알아봅니다.


요약하자면: 이번 모듈은 개념 → Kafka 설정 → 프로그래밍 실습(Java/Python) → 고급 도구(Connect/ksqlDB) 순으로 이어지는 완벽한 스트림 프로세싱 풀코스입니다.

[0:09~] 데이터 교환(Data Exchange)의 본질
스트림 프로세싱을 본격적으로 정의하기 전에, 우리 주변에서 일어나는 '데이터 교환'에 대해 먼저 생각해 봅시다. 가장 고전적인 예시는 우편 서비스입니다. 편지에 정보를 적어 보내면 우체국이 적절한 수신자에게 전달하죠. 현대 컴퓨터 통신에서는 이를 **API(Rest, GraphQL, Webhooks 등)**가 대신하고 있지만, 한쪽에서 정보를 공유하고 다른 쪽에서 받는다는 본질은 같습니다.

[1:05~] 게시판으로 이해하는 프로듀서와 컨슈머
더 쉬운 비유로 **게시판(Notice Board)**을 떠올려 보세요.

프로듀서(Producer): 정보를 알리고 싶은 사람이 게시판에 전단지를 붙입니다.

컨슈머(Consumer): 게시판 앞을 지나가는 사람들이 그 정보를 읽습니다. 나에게 필요한 정보라면 반응(액션)을 보일 것이고, 관심 없는 내용이면 그냥 무시하겠죠.

[1:45~] 관심 주제(Topic)의 도입
이제 이 게시판을 조금 더 구체화해 봅시다. 여러분이 'Kafka', 'Spark', 'Big Data'라는 특정 주제에만 관심이 있다고 가정해 보죠.

제가(프로듀서) 'Kafka'라는 **주제(Topic)**로 전단지를 붙이면, 해당 주제를 구독(Subscribe)하고 있는 여러분(컨슈머)에게만 그 정보가 전달됩니다. 이처럼 데이터 교환은 특정 채널이나 주제를 통해 필터링되어 일어날 수 있습니다.

[2:46~] 배치(Batch) vs 스트림(Stream)
그렇다면 일반적인 데이터 교환과 '스트림 프로세싱'의 차이는 무엇일까요? 핵심은 시간입니다.

배치 방식: 이메일처럼 하루나 한 시간 뒤에 확인하거나, 게시판 앞을 지나갈 때만 정보를 확인하는 방식입니다. 데이터 전달에 지연이 발생하죠.

스트림 방식: 데이터가 **실시간(Real-time)**으로 교환됩니다. 프로듀서가 Kafka 토픽에 메시지를 생산하는 즉시, 그 메시지는 지체 없이 컨슈머에게 전달됩니다. Spark나 Kafka 토픽을 구독하고 있다면, 데이터가 발생하는 즉시 정보를 얻게 됩니다.

[3:56~] '실시간'의 진짜 의미
여기서 '실시간'이라는 말을 오해해서는 안 됩니다. 빛의 속도로 즉시 일어난다는 뜻이 아니라, 기존의 배치 방식보다 압도적으로 빠르다는 뜻입니다.

배치 월드: 분 단위, 시간 단위로 데이터를 모아서 처리합니다.

실시간(스트림) 월드: 단 몇 초 정도의 지연(Delay)은 있을 수 있지만, 메시지가 발생하는 대로 즉시 처리되어 사용자에게 도달합니다.

요약하자면: 스트림 프로세싱은 데이터를 쌓아두었다가 나중에 한꺼번에 처리하는 것이 아니라, 데이터가 발생하는 즉시(실시간성) 필요한 사람(구독자)에게 전달하고 처리하는 기술을 의미합니다.

다음 영상인 **'7.3 Kafka란 무엇인가?'**로 넘어가서 Kafka가 구체적으로 이 역할을 어떻게 수행하는지 알아볼까요?

🎥 7.3 Kafka란 무엇인가? (핵심 요약 가이드)
1. Kafka의 기본 개념: 토픽(Topic)과 이벤트(Event)
Kafka를 이해하는 가장 중요한 단위는 토픽입니다.

이벤트(Event): "무엇이 일어났는가"에 대한 기록입니다. 예를 들어, 30초마다 방의 온도를 재는 앱이 있다면, [14:00:00, 32도]라는 데이터 한 줄이 하나의 이벤트입니다.

토픽(Topic): 이러한 이벤트들이 시간에 따라 끊임없이 흘러 들어오는 연속적인 스트림입니다.

로그(Log): Kafka는 데이터를 데이터베이스처럼 복잡한 방식(B-Tree 등)으로 저장하지 않고, 단순히 로그(Log) 파일 형태로 차곡차곡 쌓아 저장합니다. 그래서 매우 빠르고 단순합니다.

2. 메시지의 구조 (Key, Value, Timestamp)
Kafka에 저장되는 각 메시지는 세 가지 핵심 요소를 가집니다.

Key(키): 메시지의 식별자입니다. 나중에 배울 '파티셔닝(데이터 분산)'의 기준이 됩니다.

Value(값): 실제 전달하고자 하는 데이터(예: 온도 32도)입니다.

Timestamp(타임스탬프): 메시지가 생성된 정확한 시각입니다.


3. 왜 Kafka가 특별한가? (3가지 핵심 장점)
다른 API나 통신 방식보다 Kafka가 강력한 이유는 다음과 같습니다.

강력한 복구 능력(Robustness/Replication): 서버 한두 대가 고장 나도 데이터가 사라지지 않도록 여러 곳에 **복제(Replication)**해 둡니다.

유연성(Flexibility): 아주 작은 데이터부터 거대한 데이터까지 모두 수용하며, 컨슈머(수신자)가 한 명든 백 명든 상관없이 안정적으로 작동합니다.

확장성(Scalability): 초당 10개의 이벤트가 들어오다가 갑자기 1,000개가 들어와도 서버를 늘려 쉽게 대응할 수 있습니다.


4. 데이터 보관 주기(Retention)
일반적인 메시지 큐와 달리, Kafka는 컨슈머가 메시지를 읽어갔다고 해서 바로 삭제하지 않습니다. 보관 주기(Retention) 설정에 따라 일정 기간 데이터를 유지하므로, 나중에 다른 컨슈머가 다시 읽거나 과거 데이터를 분석하는 것이 가능합니다.


5. 현대 아키텍처에서의 역할: 마이크로서비스의 연결 고리

과거(Monolith): 거대한 코드 덩어리가 하나의 중앙 데이터베이스에 연결되어 있었습니다.

현재(Microservices): 서비스가 수십 개로 쪼개지면서 이들끼리 서로 대화할 방법이 필요해졌습니다. API로 일일이 연결하면 너무 복잡해지는데, 이때 Kafka가 중앙의 '메시지 버스' 역할을 합니다.

한 서비스가 Kafka에 데이터를 던져두기만 하면, 필요한 다른 서비스들이 언제든 가져다 쓰는 방식입니다.


6. 브릿지 역할: CDC (Change Data Capture)
기존 데이터베이스와 새로운 마이크로서비스를 연결할 때 CDC라는 기술을 씁니다. 데이터베이스에 변화가 생기면 그 내용을 즉시 Kafka 토픽으로 기록하고, 이를 다른 서비스들이 실시간으로 읽어가는 방식입니다. (이는 나중에 배울 'Kafka Connect'의 핵심 기능입니다.)

요약하자면: Kafka는 단순히 데이터를 주고받는 통로를 넘어, 이벤트를 안전하게 저장하고, 실시간으로 배달하며, 복잡한 시스템들을 유연하게 연결해 주는 중앙 신경망과 같습니다.

Confluent Cloud 설정 가이드 
[0:10~] 왜 Confluent Cloud인가?
이번 영상에서는 조금 다른 길을 가보려 합니다. 바로 Confluent Cloud 무료 체험판을 설정하는 것인데요.

이유: 30일간 무료로 사용할 수 있고, 우리가 쓰는 Google Cloud(GCP) 계정과 연결이 매우 쉽기 때문입니다. 신용카드 정보 없이도 400달러 상당의 크레딧을 주므로 부담 없이 Kafka 클러스터를 구축할 수 있습니다.

참고: 만약 클라우드 설정이 불편하시다면, 로컬에서 실행할 수 있는 Docker 파일도 제공해 드립니다.


[1:04~] 클러스터(Cluster) 생성하기
로그인 후 인터페이스가 나오면, 테스트용 Basic 클러스터를 생성합니다.

클라우드 선택: Google Cloud를 선택합니다.

리전(Region): 본인의 위치와 가까운 곳(영상에서는 Frankfurt)을 선택하고, 가성비를 위해 'Single Zone'을 택합니다.

이름 설정: 'Kafka tutorial cluster'라고 이름 짓고 출시(Launch)합니다.

[2:13~] API 키 생성 (접속 자격 증명)
클러스터가 만들어지면 대시보드에서 상태를 볼 수 있습니다. Kafka에 접속하려면 API Key가 필수입니다.

'API Keys' 메뉴에서 키를 생성하고, 나중에 코드에서 쓸 수 있도록 안전하게 다운로드해 둡니다.

[3:01~] 토픽(Topic) 만들고 메시지 직접 보내기
이제 데이터를 담을 통인 '토픽'을 만듭니다.

이름: 'tutorial topic'으로 설정하고 파티션은 2개로 잡습니다.

고급 설정: 비용 절약을 위해 데이터 보관 주기(Retention)를 딱 1일로 설정합니다.

테스트: 'Produce a new message' 기능을 통해 샘플 메시지를 직접 날려봅니다. 그러면 화면에 Key, Value, 타임스탬프가 찍힌 메시지가 들어오는 것을 실시간으로 확인할 수 있습니다.

[4:30~] 데이터 생성기(Datagen Source) 연결하기
실제 데이터가 계속 흐르는 환경을 만들기 위해 'Dummy Connector'를 설정합니다.

Datagen Source 커넥터를 사용하면 주문(Orders)이나 클릭스트림 같은 가상 데이터를 자동으로 생성해 줍니다.

JSON 형식을 선택하고 'Orders' 템플릿을 고르면, 우리 토픽으로 가짜 주문 데이터가 막 쏟아지기 시작합니다.

[5:43~] 데이터 흐름 확인
커넥터가 실행(Running)되면 대시보드의 매트릭이 바뀝니다.

초당 전송되는 바이트 수와 레코드 수가 그래프로 나타납니다.

'Topic' 메뉴의 'Messages' 탭에 들어가면, 방금 만든 커넥터가 1초에도 수차례씩 주문 데이터를 Kafka로 밀어 넣고 있는 실제 모습을 볼 수 있습니다.

[6:46~] 마무리 및 주의사항
실습이 끝났다면 커넥터를 반드시 **종료(Shut down)**해야 합니다. 제공된 400달러 크레딧을 아껴야 하니까요!

결론: 이제 여러분은 클라우드에 나만의 Kafka 서버를 가졌고, 그 안에 자동으로 데이터가 쌓이는 환경까지 구축했습니다.

다음 영상에서는 이렇게 쌓인 데이터를 **'코드를 통해 직접 생산하고 소비하는 법'**을 배워보겠습니다. 바로 다음 단계로 갈까요?
