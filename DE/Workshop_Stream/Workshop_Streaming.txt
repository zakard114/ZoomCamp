from dataclasses import dataclass # 파이썬에서 데이터를 저장하는 용도의 클래스를 쉽게 만들게 해주는 도구를 가져옵니다.

@dataclass # 아래의 클래스가 '데이터 저장용'임을 선언합니다. (생성자 등을 자동으로 만들어줍니다.)
class Ride:
    PULocationID: int           # 승차 위치 ID (정수형)
    DOLocationID: int           # 하차 위치 ID (정수형)
    trip_distance: float        # 주행 거리 (실수형)
    total_amount: float         # 총 요금 (실수형)
    tpep_pickup_datetime: int   # 승차 시간 (유닉스 타임스탬프, 밀리초 단위 정수형)


DataFrame의 행을 Ride로 변환하는 함수를 작성하세요. pandas의 타임스탬프를 에포크 밀리초 형식으로 변환합니다. 이는 Flink가 나중에 요구하는 형식입니다.:

def ride_from_row(row):
    return Ride(
        # 1. 행의 'PULocationID'를 가져와 정수(int)로 변환해 담습니다.
        PULocationID=int(row['PULocationID']),
        
        # 2. 행의 'DOLocationID'를 가져와 정수(int)로 변환해 담습니다.
        DOLocationID=int(row['DOLocationID']),
        
        # 3. 주행 거리를 가져와 실수(float)로 변환해 담습니다.
        trip_distance=float(row['trip_distance']),
        
        # 4. 총 요금을 가져와 실수(float)로 변환해 담습니다.
        total_amount=float(row['total_amount']),

🔄 데이터의 변신 과정
Producer (보내는 쪽): 직렬화 (Serialization)

파이썬 객체(Ride)를 네트워크 선을 타고 흐를 수 있는 0과 1의 바이트(bytes) 뭉치로 바꿉니다.

이때 형식이 JSON이라면, "파이썬 객체 → JSON 문자열 → 바이트" 순으로 변합니다.

목적: 카프카 브로커가 데이터를 안전하게 저장하고 전달할 수 있게 하기 위함입니다.

Kafka Broker (중간 다리):

카프카는 내용이 뭔지 몰라도 됩니다. 그냥 우리가 준 바이트 뭉치를 그대로 보관만 합니다.

Consumer (받는 쪽): 역직렬화 (Deserialization)

받은 바이트 뭉치를 다시 우리가 읽을 수 있는 JSON이나 파이썬 딕셔너리/객체로 되돌립니다.

목적: 그래야 사람이 읽거나 분석 프로그램이 계산을 할 수 있기 때문입니다.


💡 핵심 요약
직렬화: 파이썬 객체 → 카프카가 이해하는 바이트 (보낼 때)

역직렬화: 바이트 → 컨슈머가 이해하는 JSON/객체 (받을 때)

import dataclasses

이 방식도 잘 작동하지만, 매번 dataclasses.asdict()를 호출하는 것은 번거로운 작업입니다. 그래서 데이터 클래스를 직접 처리할 수 있는 직렬화 도구(Serializer)를 만들어 이 과정을 자동화할 수 있습니다.


다음 코드는 파이썬의 Ride 객체를 네트워크로 전송 가능한 바이트(Bytes) 형태로 바꾸는 핵심 로직입니다. 각 줄의 역할은 다음과 같습니다.


def ride_serializer(ride):
    # 1. 파이썬 전용 객체(Dataclass)인 ride를 일반 딕셔너리({키: 값}) 형태로 변환합니다.
    ride_dict = dataclasses.asdict(ride)
    
    # 2. 딕셔너리 데이터를 어디서나 읽을 수 있는 표준 텍스트 형식인 JSON 문자열로 변환합니다.
    json_str = json.dumps(ride_dict)
    
    # 3. JSON 문자열을 UTF-8 방식의 0과 1로 이루어진 '바이트(Bytes)' 데이터로 인코딩하여 반환합니다.
    return json_str.encode('utf-8')



이제 새로운 직렬화기를 사용하여 프로듀서를 다시 생성해 보겠습니다. Ride 객체를 먼저 딕셔너리로 ​​변환하지 않고 직접 전달할 수 있습니다.


producer = KafkaProducer(
    # 데이터를 전송할 Kafka 브로커(Red Panda)의 서버 주소([server])를 설정합니다.
    bootstrap_servers=[server],
    
    # 데이터를 보낼 때마다 자동으로 호출될 직렬화 도구로 위에서 정의한 ride_serializer 함수를 지정합니다.
    value_serializer=ride_serializer
)


💡 핵심 포인트
bootstrap_servers: Producer가 처음 접속해서 클러스터 정보를 가져올 입구(Host:Port)를 알려줍니다. 여기서는 보통 localhost:9092가 들어있는 server 변수를 사용합니다.

value_serializer: 이 설정 덕분에 앞으로 producer.send(topic, ride)처럼 객체를 그냥 던지기만 해도, 내부적으로 ride_serializer가 작동하여 알아서 **바이트(Bytes)**로 변환해 보냅니다.

def ride_deserializer(data):

1. ride_deserializer 함수 (해독기)
네트워크를 타고 온 바이트 데이터를 해석해서 다시 Ride 상자에 담아주는 역할을 합니다.

import json

def ride_deserializer(data):
    # 1. 받은 바이트(data)를 다시 읽을 수 있는 'utf-8' 형식의 문자열로 변환합니다.
    json_str = data.decode('utf-8')
    
    # 2. JSON 형태의 문자열을 파이썬의 딕셔너리(Key:Value) 형태로 변환합니다.
    ride_dict = json.loads(json_str)
    
    # 3. 딕셔너리의 내용물(**)을 Ride 클래스에 쏟아부어 새로운 Ride 객체를 만들어 반환합니다.
    return Ride(**ride_dict)

컨슈머(Consumer)로서 Kafka에 연결합니다. auto_offset_reset='earliest'는 토픽의 맨 처음부터 읽기 시작한다는 의미입니다. (이 설정이 없으면 새로운 컨슈머는 기본값인 latest로 설정되어 연결된 이후의 새 메시지만 보게 됩니다.) group_id는 이 컨슈머 그룹을 식별합니다. 카프카는 각 그룹이 어디까지 읽었는지 추적하므로, 동일한 그룹 ID로 재시작하면 마지막으로 읽었던 지점부터 다시 시작할 수 있습니다.

GEM> Redpanda는 Kafka와 '똑같은 방식'으로 대화하지만, C++로 훨씬 빠르고 가볍게 만든 현대판 Kafka라고 이해하시면 됩니다.



from kafka import KafkaConsumer # 카프카로부터 메시지를 읽어오기 위한 KafkaConsumer 클래스를 가져옵니다.

server = 'localhost:9092' # 연결할 카프카(또는 Redpanda) 브로커의 주소입니다. 

topic_name = 'rides' # 데이터를 가져올 대상인 토픽의 이름입니다.


# KafkaConsumer 객체를 생성하여 수신 설정을 마칩니다. 
consumer = KafkaConsumer(
    topic_name,                       # 구독할 토픽 이름을 첫 번째 인자로 전달합니다.
    bootstrap_servers=[server],       # 접속할 브로커 서버 정보를 리스트 형태로 전달합니다.
    auto_offset_reset='earliest',     # 토픽에 저장된 가장 오래된 메시지부터 읽도록 설정합니다.
    group_id='rides-console',         # 이 컨슈머가 속한 그룹의 ID를 지정하여 읽은 위치(offset)를 관리합니다.
    value_deserializer=ride_deserializer # 수신한 바이트 데이터를 Ride 객체로 자동 변환하도록 설정합니다.
)


본문
메시지를 읽어와서 출력합니다. value_deserializer가 이미 Ride 객체를 반환하도록 설정되어 있기 때문에, message.value는 이미 Ride 객체인 상태입니다. 따라서 별도의 추가 변환 작업이 전혀 필요하지 않습니다.

GEM> 
이제 컨슈머를 통해 실제로 데이터를 뽑아내어 화면에 출력하는 최종 실행 단계입니다. 이 코드는 실시간으로 들어오는 메시지를 하나씩 가공하여 읽기 좋은 형태로 보여줍니다.


from datetime import datetime  # 타임스탬프 숫자를 읽기 쉬운 날짜 형식으로 바꾸기 위해 가져옵니다.

print(f"Listening to {topic_name}...")  # 'rides' 토픽에서 데이터를 기다리고 있다는 안내 문구를 출력합니다.

count = 0  # 받은 메시지의 개수를 세기 위한 변수입니다.
for message in consumer:
    ride = message.value  # 미리 설정한 역직렬화 도구 덕분에 message.value는 이미 'Ride' 객체입니다.
    
    # 밀리초 단위의 타임스탬프를 1000으로 나눠 초 단위로 바꾼 뒤, 파이썬 날짜(datetime) 객체로 변환합니다.
    pickup_dt = datetime.fromtimestamp(ride.tpep_pickup_datetime / 1000)
    
    # 받아온 Ride 객체의 속성들을 보기 좋게 포맷팅하여 출력합니다. (금액은 소수점 2자리까지)
    print(f"Received: PU={ride.PULocationID}, DO={ride.DOLocationID}, "
          f"distance={ride.trip_distance}, amount=${ride.total_amount:.2f}, "
          f"pickup={pickup_dt}")
    
    count += 1
    # 데모를 위해 10개의 메시지만 받고 루프를 중단하도록 설정했습니다.
    if count >= 10:
        print(f"\n... received {count} messages so far (stopping after 10 for demo)")
        break

consumer.close()  # 데이터 수신이 끝났으므로 컨슈머 연결을 안전하게 닫습니다.


💡 여기서 핵심 로직은?
for message in consumer: 이 루프는 카프카 브로커에 새로운 데이터가 들어올 때까지 **실시간으로 대기(Blocking)**하며, 메시지가 도착하는 즉시 하나씩 꺼내옵니다.

datetime.fromtimestamp: 사람이 읽기 힘든 큰 숫자(예: 1730429702000)를 2024-11-01 10:35:02와 같은 친숙한 날짜 형식으로 바꿔줍니다.

1. 왜 계속 뺑뺑 돌아가나요? (Blocking)
for message in consumer: 이 문법은 **"새로운 데이터가 올 때까지 무한히 대기하라"**는 명령입니다.

데이터가 10개 미만일 때: 만약 프로듀서(Producer)가 데이터를 아직 10개까지 쏘지 않았다면, 컨슈머는 10개를 다 채울 때까지 다음 데이터를 기다리며 루프를 종료하지 않고 계속 대기합니다.

네트워크 지연: 브로커로부터 데이터를 가져오는 데 시간이 걸리거나, 설정된 group_id가 이전 데이터를 다 읽었다고 판단하여 새 데이터를 기다리는 중일 수 있습니다.

A. 강제 종료

PostgreSQL 연결 설정


Python
import psycopg2

# PostgreSQL 데이터베이스에 연결합니다.
conn = psycopg2.connect(
    host='localhost',    # 데이터베이스 서버 주소
    port=5432,           # PostgreSQL 기본 포트 번호
    database='postgres', # 연결할 데이터베이스 이름
    user='postgres',     # 접속 계정명
    password='postgres'  # 계정 비밀번호
)

# autocommit을 True로 설정하면 각 INSERT 작업이 즉시 반영됩니다.
# 행마다 conn.commit()을 호출할 필요가 없어 편리합니다.
conn.autocommit = True

# 데이터베이스 명령(SQL)을 실행하기 위한 커서를 생성합니다.
cur = conn.cursor()



autocommit = True는 각 행을 삽입할 때마다 자동으로 확정(Commit)한다는 의미입니다. 행마다 별도로 conn.commit()을 호출할 필요가 없습니다.

Python
from datetime import datetime

# 시작 알림 문구를 출력합니다.
print(f"Listening to {topic_name} and writing to PostgreSQL...")

count = 0 # 삽입된 행의 개수를 세기 위한 변수입니다.

# 카프카 컨슈머로부터 메시지를 하나씩 가져옵니다.
for message in consumer:
    ride = message.value # 역직렬화된 Ride 객체를 가져옵니다.
    
    # 밀리초 단위의 타임스탬프를 파이썬 datetime 객체로 변환합니다.
    pickup_dt = datetime.fromtimestamp(ride.tpep_pickup_datetime / 1000)
    
    # SQL INSERT 문을 실행하여 데이터를 테이블에 저장합니다.
    cur.execute(
        """INSERT INTO processed_events 
           (PULocationID, DOLocationID, trip_distance, total_amount, pickup_datetime) 
           VALUES (%s, %s, %s, %s, %s)""",
        (ride.PULocationID, ride.DOLocationID, 
         ride.trip_distance, ride.total_amount, pickup_dt)
    )
    
    count += 1
    # 100행마다 진행 상황을 화면에 출력합니다.
    if count % 100 == 0:
        print(f"Inserted {count} rows...")

# 작업이 끝나면 자원을 안전하게 해제합니다.
consumer.close() # 카프카 컨슈머 연결 종료
cur.close()      # DB 커서 닫기
conn.close()     # DB 연결 종료

GEM> zakard님, **cur (Cursor, 커서)**는 쉽게 말해 "데이터베이스와 대화하기 위한 리모컨" 또는 **"메모장"**이라고 이해하시면 됩니다.

cur (Cursor)의 핵심 역할 3가지
명령 전달 (Executor):
파이썬 코드에서 작성한 SQL 문장(SELECT, INSERT, TRUNCATE 등)을 실제 데이터베이스 엔진으로 전달하고 실행하는 역할을 합니다.

예: cur.execute("TRUNCATE ...")

결과 보관 (Buffer):
데이터베이스에서 조회한 데이터(SELECT)를 잠시 들고 있는 임시 저장소입니다. 데이터가 너무 많을 경우, 한꺼번에 가져오지 않고 줄 단위로 읽어올 수 있게 해줍니다.

위치 가리키기 (Pointer):
이름 그대로(Cursor), 여러 줄의 결과 데이터 중 현재 내가 읽고 있는 지점이 어디인지를 가리킵니다.

비유로 이해하기
conn (Connection): 우리 집과 데이터베이스 서버 사이에 연결된 전화선입니다.

cur (Cursor): 그 전화선으로 말을 전하고 대답을 받아 적는 **상담원(또는 리모컨)**입니다.

주요 명령어 한눈에 보기

cur.execute(sql)	SQL 문을 실행합니다.
cur.fetchone()	결과 중 한 줄만 가져옵니다.
cur.fetchall()	결과 전체를 리스트로 가져옵니다.
cur.close()	리모컨 사용을 마치고 반납합니다.

왜 Flink인가? (Why Flink?)
Flink는 스트림 처리의 복잡한 문제들을 자동으로 해결해주는 프레임워크입니다:

윈도잉(Windowing): 고정 시간(Tumbling), 슬라이딩(Sliding), 세션(Session) 단위의 데이터 처리가 내장되어 있습니다.



//
GEM> zakard님, 실시간으로 쏟아지는 데이터(강물)를 **'어떤 바구니에 담아서 계산할 것인가'**를 결정하는 게 바로 **윈도잉(Windowing)**입니다.

데이터는 끝없이 흘러오기 때문에 "전체 평균 내줘!"라고 하면 끝이 안 나겠죠? 그래서 시간 단위로 뚝 끊어서 계산하는 건데, 그 방식이 3가지입니다.

1. 고정 시간 윈도우 (Tumbling Window)
특징: 시간이 겹치지 않게 딱딱 끊어지는 바구니입니다.

예시: "매 5분마다 지난 5분간의 택시 승차 횟수 합산"

동작: 0~5분 계산 종료 → 5~10분 계산 시작. (가장 깔끔하고 흔한 방식)

2. 슬라이딩 윈도우 (Sliding Window)
특징: 일정한 간격으로 옆으로 미끄러지듯 이동하며, 이전 바구니와 데이터가 겹칩니다.

예시: "1분마다, 최근 5분간의 평균 기온 계산"

동작: 1시에 (12:55~1:00) 계산 → 1시 1분에 (12:56~1:01) 계산.

용도: "최근 N분간"의 추세를 실시간으로 아주 부드럽게 보고 싶을 때 씁니다.

3. 세션 윈도우 (Session Window)
특징: 시간이 아니라 '활동' 기준입니다. 데이터가 안 들어오는 **'정적 시간(Gap)'**이 생기면 하나의 묶음으로 간주합니다.

예시: "사용자가 앱에 접속해서 활동하다가, 30분간 아무것도 안 하면 로그아웃(세션 종료)으로 처리"

동작: 데이터가 계속 들어오면 바구니가 계속 커지다가, 설정한 시간만큼 데이터가 끊기면 그 바구니를 닫고 계산합니다.

체크포인트(Checkpointing): 장애 발생 시 상태를 자동으로 복구합니다. (수동으로 오프셋을 관리할 필요가 없습니다.)

병렬 처리(Parallelism): 여러 작업자(Worker)에게 처리를 분산시켜 속도를 높입니다.

커넥터(Connectors): JDBC, Kafka, 파일 시스템용 싱크(Sink)가 내장되어 있습니다. (즉, 더 이상 psycopg2 코드를 직접 짤 필요가 없습니다.)

SQL 인터페이스: SQL 쿼리만으로 스트림 처리를 표현할 수 있습니다.

Flink는 카프카 외에도 REST API, 웹소켓(Websocket), 파일 시스템 등 다양한 소스에 연결할 수 있습니다. 물론 스트림 처리에서 카프카가 가장 일반적인 소스이긴 합니다.

**트레이드오프(Trade-off)**는 인프라의 복잡성입니다. JobManager와 TaskManager 컨테이너가 필요하며, 스트리밍 작업은 일반적인 배치 파이프라인보다는 서버 운영에 가깝습니다. 24시간 내내 돌아가며 모니터링이 필요하죠.

번역: Flink 서비스를 docker-compose.yml에 추가하기
이제 docker-compose.yml에 Flink 서비스들을 추가해 봅시다. Flink 클러스터는 두 가지 유형의 프로세스로 구성되는데, 하나씩 추가해 보겠습니다.

JobManager는 조정자(Coordinator)입니다. 작업을 접수하고, 체크포인트를 관리하며, 태스크 매니저(Task Manager)들에게 할당량을 배정합니다. 여러분은 웹 UI(8081 포트)를 통해 JobManager와 상호작용하고, RPC 포트(6123)를 통해 작업을 제출하게 됩니다.

코드 분석 및 상세 주석
YAML
  jobmanager:
    # 1. 빌드 설정: 현재 경로(.)에 있는 Dockerfile.flink를 사용하여 이미지를 만듭니다.
    build:
      context: .
      dockerfile: ./Dockerfile.flink
    
    # 2. 이미지 이름: 빌드된 이미지의 이름을 'pyflink-workshop'으로 지정합니다.
    image: pyflink-workshop
    
    # 3. 풀 정책: 로컬에서 직접 빌드한 이미지이므로, 외부(Docker Hub)에서 다운로드하지 않도록 설정합니다.
    pull_policy: never
    
    # 4. 내부 노출 포트: 컨테이너들끼리 통신할 때 사용할 RPC 포트입니다.
    expose:
      - "6123"
    
    # 5. 외부 개방 포트: 우리 호스트(PC)에서 Flink 관리 화면(대시보드)을 볼 수 있게 8081 포트를 연결합니다.
    ports:
      - "8081:8081"
    
    # 6. 볼륨 마운트: 로컬의 소스 코드와 라이브러리를 컨테이너 내부로 연결합니다.
    # 코드를 수정해도 이미지를 다시 빌드할 필요 없이 바로 반영됩니다.
    volumes:
      - ./:/opt/flink/usrlib
      - ./src/:/opt/src
    
    # 7. 실행 명령: 이 컨테이너가 'jobmanager' 역할을 수행하도록 명령을 내립니다.
    command: jobmanager
    
    # 8. 환경 변수: Flink의 세부 설정을 주입합니다.
    environment:
      - |
        FLINK_PROPERTIES=
        jobmanager.rpc.address: jobmanager      # 조정자(JobManager)의 주소를 지정합니다.
        jobmanager.memory.process.size: 1600m   # JobManager가 사용할 메모리 크기를 설정합니다.


핵심 용어 설명
build + image: pyflink-workshop: 우리가 만든 커스텀 이미지를 'pyflink-workshop'이라는 이름표를 붙여 빌드합니다. 나중에 추가할 TaskManager는 이 이미지를 그대로 재사용하므로 다시 빌드할 필요가 없습니다.

pull_policy: never: "이 이미지는 내가 직접 만든 거니까 인터넷에서 찾지 마!"라고 도커에게 알려주는 것입니다.

volumes: 내 컴퓨터의 src 폴더와 컨테이너 안을 연결해 줍니다. 덕분에 코드를 고칠 때마다 이미지를 새로 구울 필요가 없어 아주 편리합니다.

FLINK_PROPERTIES: Flink 엔진의 옵션을 설정합니다. 여기서 jobmanager.rpc.address: jobmanager는 일꾼(TaskManager)들이 사장님(JobManager)을 찾아올 수 있도록 "내 이름은 jobmanager야"라고 알려주는 역할을 합니다.

TaskManager 및 실행 설정
TaskManager는 실제 데이터 처리를 수행하는 일꾼(Worker)입니다.

코드 분석 및 상세 주석
YAML
  taskmanager:
    # 1. 이미지 재사용: jobmanager 서비스에서 빌드한 'pyflink-workshop' 이미지를 그대로 사용합니다.
    image: pyflink-workshop
    
    # 2. 풀 정책: 로컬 이미지를 사용하므로 외부에서 찾지 않도록 설정합니다.
    pull_policy: never
    
    # 3. 내부 노출 포트: 데이터 전송 및 관리를 위한 통신 포트들을 엽니다.
    expose:
      - "6121"
      - "6122"
      
    # 4. 볼륨 마운트: 로컬 소스 코드(src)를 컨테이너 안으로 연결하여 실시간 수정을 반영합니다.
    volumes:
      - ./:/opt/flink/usrlib
      - ./src/:/opt/src
      
    # 5. 의존성: 조정자(jobmanager)가 먼저 실행된 후에 일꾼(taskmanager)이 뜹니다.
    depends_on:
      - jobmanager
      
    # 6. 실행 명령: taskmanager 역할을 수행하며, 시작 시 사장님(jobmanager)을 찾는 대기 시간을 5분으로 늘립니다.
    command: taskmanager --taskmanager.registration.timeout 5 min
    
    # 7. 환경 변수 및 상세 설정
    environment:
      - |
        FLINK_PROPERTIES=
        jobmanager.rpc.address: jobmanager         # 찾아갈 사장님(JobManager) 주소
        taskmanager.memory.process.size: 1728m    # 일꾼이 사용할 총 메모리 크기
        taskmanager.numberOfTaskSlots: 15         # 이 일꾼이 동시에 처리할 수 있는 작업 칸(Slot) 개수
        parallelism.default: 3                    # 기본적으로 한 작업을 3개로 쪼개서 병렬 처리


핵심 개념 이해: "태스크 슬롯(Task Slot)"이란?
태스크 슬롯은 하나의 병렬 작업을 수행할 수 있는 **메모리와 CPU의 단위(바구니)**입니다.

비유: 고속도로의 차선이라고 생각하세요. 차선이 많을수록 더 많은 데이터가 한꺼번에 흐를 수 있습니다.

병렬 처리(Parallelism): 만약 병렬도를 3으로 설정하면, 그 작업은 3개의 슬롯을 사용합니다.

계산: 현재 15개의 슬롯이 있으므로, 병렬도 3짜리 작업을 동시에 5개까지 돌릴 수 있습니다.

1. RPC(Remote Procedure Call)란 무엇인가?

**RPC(원격 프로시저 호출)**는 아주 쉽게 말해 **"네트워크로 연결된 다른 컴퓨터에 있는 함수를 마치 내 컴퓨터에 있는 것처럼 실행하는 기술"**입니다.

일반적인 함수 호출: 내 컴퓨터 메모리에 있는 add(1, 2)를 실행.
RPC 호출: 내가 jobmanager.start_job()이라고 명령하면, 네트워크를 타고 JobManager 컴퓨터로 넘어가서 그곳의 함수가 실행됨.


2. 각각의 포트는 어떤 역할을 하나요?도커 설정에 나온 포트들은 Flink라는 '조직'의 전용 내선 번호와 같습니다.

포트 번호	소속	주요 기능	비유

6123	JobManager	RPC 서비스 포트. 작업 제출 및 클러스터 관리 명령을 받음.	사장님의 직통 비서실 전화
6121	TaskManager	데이터 전송 포트. 일꾼들끼리 처리 중인 데이터를 주고받음.	공장 라인 사이의 컨베이어 벨트 연결부
6122	TaskManager	RPC 서비스 포트. 사장님(JobManager)의 명령을 받는 포트.	일꾼이 찬 무전기


3. RPC는 JobManager와 TaskManager 사이에서 어떻게 작동하나?
zakard님이 언급하신 "조정자"와 "일꾼" 사이에서 RPC는 다음과 같은 **'명령 체계'**로 작동합니다.

① Job 제출 (사용자 → JobManager: 6123 포트)
우리가 파이썬 코드를 실행하여 Flink에 작업을 던지면, 6123 포트로 RPC 호출이 갑니다.

명령: "사장님, 이 엑셀(데이터 처리 로직) 좀 돌려주세요!"

② 할당량 배정 (JobManager → TaskManager: 6122 포트)
JobManager는 작업을 분석한 뒤, TaskManager의 6122 포트로 RPC를 날립니다.

명령: "일꾼1, 너는 1번 슬롯에서 데이터 필터링해. 일꾼2, 너는 2번 슬롯에서 DB에 저장해!"

③ 상태 보고 (TaskManager → JobManager: 6123 포트)
작업 도중 일꾼이 사장님에게 RPC로 보고합니다.

명령: "사장님, 저 방금 데이터 100개 처리 완료했습니다(체크포인트 저장 완료)!"

④ 데이터 이동 (TaskManager ↔ TaskManager: 6121 포트)
이건 RPC(명령)라기보다는 실제 물류(Data) 이동입니다.

상황: "내가 필터링 끝낸 데이터 너한테 보낼 테니, 네가 DB에 넣어!" (이때 6121 포트가 쓰입니다.)

💡 요약하자면
6123 (사장님실): 명령을 내리고 보고를 받는 메인 채널 (RPC).

6122 (일꾼 무전기): 사장님의 지시를 직접 수신하는 채널 (RPC).

6121 (작업장 벨트): 일꾼들끼리 실제 데이터를 쏟아붓는 채널 (Data Transfer).

명령(RPC - 6122, 6123): "지금부터 100개씩 처리해!", "알겠습니다!" 같은 짧고 중요한 메시지가 오갑니다. (비유: 관제탑의 무전)

GEM> zakard님, YAML 문법에서 이 부분은 처음 보면 정말 생소할 수 있습니다. 결론부터 말씀드리면 - |는 **"리스트 항목(-)을 시작하되, 그 내용은 여러 줄로 된 문자열(|)로 채우겠다"**는 뜻입니다.

구체적으로 쪼개서 설명해 드릴게요.

1. - (하이픈): "리스트의 요소"
YAML에서 하이픈은 파이썬의 리스트([])와 같습니다.
environment: 설정은 여러 개의 환경 변수를 가질 수 있기 때문에 리스트 형식을 사용합니다.

2. | (파이프): "리터럴 블록 스칼라(Literal Block Scalar)"
이게 핵심입니다. YAML에서 이 기호는 **"다음에 오는 문장들을 적힌 그대로(줄바꿈 포함) 하나의 덩어리로 인식해라"**라는 지시어입니다.

왜 이걸 쓰나요?: Flink 설정(FLINK_PROPERTIES)은 여러 줄의 설정값들을 하나의 환경 변수 안에 한꺼번에 담아서 전달해야 하기 때문입니다.

3. 실제 해석 예시
만약 - |를 쓰지 않고 한 줄로 쓴다면 파이썬에서는 아래처럼 보일 것입니다:

Python
# 일반적인 방식
environment = ["FLINK_PROPERTIES=jobmanager.rpc.address: jobmanager"]
하지만 - |를 쓰면 줄바꿈이 포함된 통째로의 값이 전달됩니다:

Python
# - | 를 썼을 때의 내부 처리 방식
environment = [
    "FLINK_PROPERTIES=\njobmanager.rpc.address: jobmanager\ntaskmanager.numberOfTaskSlots: 15"
]
4. 왜 이렇게 복잡하게 쓰나요?
Flink는 FLINK_PROPERTIES라는 단 하나의 환경 변수를 읽어서 그 안의 여러 줄을 다시 분석하도록 설계되어 있습니다.

만약 |가 없다면: YAML은 줄바꿈을 인식하지 못하거나 에러를 낼 것입니다.

| 덕분에: 우리는 마치 메모장에 글을 쓰듯이 편하게 아래로 줄을 바꿔가며 Flink 설정을 적을 수 있는 것입니다.

1. 카프카 소스 테이블 정의
카프카에서 데이터를 읽어오기 위한 가상 테이블을 정의합니다.

Python
def create_events_source_kafka(t_env):
    table_name = "events"
    # Flink SQL DDL 문법을 사용하여 카프카와 연결된 테이블을 생성합니다.
    source_ddl = f"""
        CREATE TABLE {table_name} (
            PULocationID INTEGER,      -- 승차 위치 ID
            DOLocationID INTEGER,      -- 하차 위치 ID
            trip_distance DOUBLE,      -- 주행 거리
            total_amount DOUBLE,       -- 총 요금
            tpep_pickup_datetime BIGINT -- Unix 타임스탬프 (밀리초 단위)
        ) WITH (
            'connector' = 'kafka',     -- 카프카 커넥터 사용
            'properties.bootstrap.servers' = 'redpanda:29092', -- 도커 내부 네트워크의 Redpanda 주소
            'topic' = 'rides',         -- 구독할 카프카 토픽 이름
            'scan.startup.mode' = 'latest-offset', -- 잡 시작 이후에 들어온 메시지만 읽음
            'properties.auto.offset.reset' = 'latest', -- 오프셋 초기값이 없을 경우 최신부터 시작
            'format' = 'json'          -- 데이터 포맷은 JSON으로 자동 역직렬화
        );
        """
    t_env.execute_sql(source_ddl) # SQL문을 실행하여 환경에 테이블을 등록합니다.
    return table_name


참고: 주소값이 localhost가 아닌 redpanda:29092인 이유는 Flink가 도커 컨테이너 내부에서 실행 중이기 때문입니다.

2. PostgreSQL 싱크(Sink) 테이블 정의
데이터를 내보낼 목적지(Postgres)를 정의합니다.

Python
def create_processed_events_sink_postgres(t_env):
    table_name = 'processed_events'
    # JDBC 커넥터를 사용하여 PostgreSQL 테이블과 연결합니다.
    sink_ddl = f"""
        CREATE TABLE {table_name} (
            PULocationID INTEGER,
            DOLocationID INTEGER,
            trip_distance DOUBLE,
            total_amount DOUBLE,
            pickup_datetime TIMESTAMP -- 가공된 타임스탬프 저장용
        ) WITH (
            'connector' = 'jdbc',      -- JDBC 커넥터 사용
            'url' = 'jdbc:postgresql://postgres:5432/postgres', -- 도커 내부의 Postgres 주소
            'table-name' = '{table_name}', -- 실제 DB 내 테이블 이름
            'username' = 'postgres',
            'password' = 'postgres',
            'driver' = 'org.postgresql.Driver' -- Postgres JDBC 드라이버 지정
        );
        """
    t_env.execute_sql(sink_ddl)
    return table_name
장점: psycopg2 라이브러리나 복잡한 INSERT 문을 직접 작성할 필요가 없습니다.


3. 실행 로직 (Main Execution)
Python
from pyflink.datastream import StreamExecutionEnvironment
from pyflink.table import EnvironmentSettings, StreamTableEnvironment

def log_processing():
    # 1. 스트리밍 실행 환경을 설정합니다.
    env = StreamExecutionEnvironment.get_execution_environment()
    
    # 2. 체크포인팅 활성화 (10초마다 상태를 저장합니다).
    # 장애 발생 시 마지막 저장 지점부터 자동으로 복구하게 해줍니다.
    env.enable_checkpointing(10 * 1000) 

    # 3. 테이블 환경 설정을 생성하고 스트리밍 모드로 지정합니다.
    settings = EnvironmentSettings.new_instance().in_streaming_mode().build()
    t_env = StreamTableEnvironment.create(env, environment_settings=settings)

    # 4. 소스(카프카)와 싱크(Postgres) 테이블을 생성합니다.
    source_table = create_events_source_kafka(t_env)
    postgres_sink = create_processed_events_sink_postgres(t_env)

    # 5. SQL을 실행하여 파이프라인을 가동합니다.
    # TO_TIMESTAMP_LTZ 함수를 사용하여 숫자형 타임스탬프를 시간 형식으로 바꿉니다.
    t_env.execute_sql(
        f"""
        INSERT INTO {postgres_sink}
        SELECT
            PULocationID,
            DOLocationID,
            trip_distance,
            total_amount,
            TO_TIMESTAMP_LTZ(tpep_pickup_datetime, 3) as pickup_datetime
        FROM {source_table}
        """
    ).wait() # 잡이 종료될 때까지 대기합니다 (스트리밍이므로 사실상 계속 실행됨).

if __name__ == '__main__':
    log_processing()


핵심 개념: 체크포인팅(Checkpointing)
Flink는 10초마다 현재 어디까지 읽었는지(Offset)와 가공 중인 데이터를 스냅샷으로 찍어둡니다.

복구력 vs 효율성: 1초마다 찍으면 복구는 빠르지만 시스템에 부하가 큽니다. 10초 정도가 적당한 기본값입니다.

오프셋(Offsets) - Earliest vs Latest
Flink가 카프카에 연결될 때, 어디서부터 데이터를 읽어야 할지 알아야 합니다. 이것이 바로 scan.startup.mode 설정입니다.

모드 (Mode)	동작 (Behavior)
latest-offset	잡이 시작된 이후에 도착한 메시지만 읽습니다.
earliest-offset	토픽의 맨 처음부터 모든 데이터를 다 읽습니다.
timestamp	특정 시점부터 데이터를 읽기 시작합니다.

earliest: 주로 **과거 데이터 재처리(Backfilling)**를 위해 사용됩니다. 카프카에 쌓여있던 오래된 데이터를 처리해야 할 때 씁니다.

latest: 실제 운영 환경(Production)에서 가장 흔한 설정입니다. 웹사이트 클릭 등 지금 이 순간 발생하는 실시간 이벤트만 처리합니다.

실습: Earliest-offset의 위력 확인하기
현재 우리 잡은 latest-offset을 쓰고 있습니다. 이걸 earliest로 바꿔서 과거 데이터를 다 긁어오는지 확인해 봅시다.

왜 중복 데이터가 생기나요?
체크포인트(Checkpoint)는 특정 잡 인스턴스에 귀속됩니다. 잡을 취소하고 새로 제출하면, 이전 잡의 체크포인트 기록(어디까지 읽었는지)은 사라집니다. 이때 earliest-offset 설정을 쓰면 Flink는 "아, 처음부터 다 읽으라는 뜻이구나!"라고 판단해서 과거 데이터를 다시 다 가져오는 것이죠.

운영 팁: Timestamp 모드와 람다 아키텍처
timestamp 모드: 오후 2시에 잡이 죽었다면, 오후 2시 시점부터 다시 시작하도록 설정할 수 있습니다. 데이터 누락이나 과도한 재처리를 막는 아주 유용한 방법입니다.

운영 패턴 (Lambda Architecture): 실시간 작업은 latest-offset으로 빠르게 돌리고, 만약 서버가 다운되어 공백이 생겼다면 별도의 배치(Batch) 잡이나 earliest 설정을 쓴 잡을 돌려 그 틈새를 메우는 방식을 사용합니다.

Consumer는 반대로 이 바이트를 다시 객체로 역직렬화(Deserialization)합니다. 이제 Producer가 1,000개의 이벤트를 보내면 Consumer가 이를 실시간으로 출력하는 것을 확인할 수 있습니다.

## 파트 2: 데이터베이스 연동 및 Flink 도입
42:14
방금까지는 데이터를 단순히 출력만 했는데, 이제 이 데이터를 PostgreSQL 데이터베이스에 넣어보겠습니다. docker-compose에 Postgres 설정을 추가하고 실행합니다. DB에 processed_events라는 테이블을 만들고, 파이썬 Consumer가 스트림에서 데이터를 읽을 때마다 DB에 INSERT하도록 코드를 수정하겠습니다.

48:06
Producer가 데이터를 보내면 Consumer가 이를 즉시 DB에 쌓는 것을 볼 수 있습니다. 이건 아주 기초적인 흐름입니다. 하지만 현실에서는 더 복잡한 요구사항이 생깁니다. 실시간으로 '특정 위치에서 특정 시간 동안 몇 건의 호출이 있었는지' 집계(Aggregation)하고 싶다면 어떻게 할까요?

50:54
직접 코드를 짤 수도 있겠지만, 재시도(Retry) 처리, 장애 복구, 혹은 터널을 통과하느라 늦게 도착한 이벤트(Late events) 처리 등을 직접 구현하려면 매우 복잡합니다. 이런 문제를 해결해 주는 전문적인 시스템이 바로 Apache Flink입니다. Flink는 결함 허용(Fault tolerance) 기능이 강력하고 실시간 분석에 최적화된 플랫폼입니다.

52:52
Flink는 Job Manager(작업 관리)와 Task Manager(실제 처리 수행)로 구성됩니다. 우리는 PyFlink와 필요한 커넥터(Kafka, JDBC, Postgres 드라이버 등)가 포함된 커스텀 Docker 이미지를 빌드하여 환경을 구축하겠습니다.

1:03:31
Flink 환경이 준비되면 먼저 Pass-through Job을 실행해 보겠습니다. 가공 없이 데이터를 소스(Kafka)에서 싱크(Postgres)로 그대로 전달하는 작업입니다. Flink는 SQL과 유사한 DDL(Data Definition Language)을 사용하여 소스와 싱크를 정의합니다. 작업을 제출(Submit)하면 Flink 대시보드에서 실행 상태를 확인할 수 있으며, 데이터가 DB에 실시간으로 들어오는 것을 볼 수 있습니다.

## 파트 3: 윈도우 집계와 Watermark
1:12:47
이제 Flink의 진정한 강점인 **윈도우 집계(Window Aggregation)**를 해보겠습니다. 특정 시간 범위(예: 1시간) 동안의 데이터를 집계하는 것입니다. 이를 위해 실시간 데이터를 생성하는 새로운 Producer를 실행하겠습니다. 이 Producer는 20% 확률로 데이터가 3~10초 정도 늦게 도착하도록 시뮬레이션합니다.

1:19:39
여기서 **Watermark(워터마크)**라는 개념이 등장합니다. 워터마크는 '지연된 이벤트를 얼마나 기다려줄 것인가'에 대한 허용 오차입니다. 예를 들어 워터마크를 5초로 설정하면, 시스템은 이벤트 시간이 현재보다 5초 늦은 것까지는 정상 범위로 간주하여 기다려줍니다.

1:24:25
만약 정해진 시간보다 훨씬 늦게 도착하면 어떻게 될까요? Flink는 이미 결과를 DB에 보냈더라도, 나중에 도착한 지연 이벤트를 확인하여 기존 집계값을 업데이트(Upsert)할 수 있습니다.

1:27:02
이제 집계 Job을 제출해 보겠습니다. 이 Job은 1시간 단위 윈도우로 pickup_location_id별 트립 횟수와 총 요금을 계산합니다. Postgres에서 processed_events_aggregated 테이블을 확인하면 데이터가 실시간으로 업데이트되는 것을 볼 수 있습니다. 이제 이 데이터를 바탕으로 실시간 분석 대시보드를 만들 수 있게 된 것입니다.

1:30:52
워크숍을 마치며, 워터마크는 '지연 허용' 혹은 '숙제 제출 기한'과 비슷하다고 이해하시면 편합니다. 오늘 다룬 모든 코드는 설명란의 링크에서 확인하실 수 있습니다. 데이터 엔지니어링에 관심이 있다면 코스를 확인해 보시고, Data Talks Club 커뮤니티(슬랙)에도 참여해 보세요. 시청해 주셔서 감사합니다!
