1.1 LLM과 RAG 입문 (번역본)
[0:00 - 0:26] 코스 소개
안녕하세요 여러분, 우리 코스의 첫 번째 모듈에 오신 것을 환영합니다. 이 코스의 이름은 **'LLM 줌캠프(LLM Zoomcamp)'**입니다. 우리는 여기서 LLM의 실제적인 활용법을 배울 것이며, 특히 **RAG(Retrieval Augmented Generation, 검색 증강 생성)**에 초점을 맞출 것입니다. RAG가 무엇인지, 우리가 정확히 무엇을 할 것인지 곧 자세히 설명해 드릴게요.

[0:26 - 1:04] 우리가 해결하려는 문제
우선, 이 코스 전체에서 우리가 해결하고자 하는 문제를 설명하며 시작하고 싶습니다. 우리 'DataTalksClub' 커뮤니티에는 여러 코스가 있는데, 이 LLM 줌캠프는 벌써 다섯 번째 코스입니다. 보통 코스를 운영하다 보면 수강생분들이 자주 묻는 질문(FAQ)이 생기기 마련이죠. 영상에는 답이 없거나, 답이 있더라도 찾기 어려운 경우들이 있습니다.

[1:04 - 1:57] 방대한 데이터의 한계
우리는 이런 FAQ 문서들을 가지고 있습니다. 하나 보여드릴게요. 예를 들어 데이터 엔지니어링 줌캠프의 FAQ 문서는 무려 321페이지나 됩니다. 질문-답변-질문-답변 형식으로 되어 있죠. 보통 우리는 학생들에게 질문하기 전에 이 문서를 먼저 확인해 보라고 합니다. 슬랙(Slack) 채널에 물어보기 전에 말이죠.

[1:57 - 2:58] 목표: 질문 답변(Q&A) 시스템 구축
물론 대부분의 답은 이 안에 있습니다. 하지만 문제는 **'찾기가 너무 어렵다'**는 것입니다. 321페이지나 되는 문서에서 나에게 필요한 정보를 어떻게 찾아낼까요? 결코 쉽지 않죠. 그래서 우리는 세 개 코스의 FAQ 데이터를 활용해서 Q&A 시스템을 만들 겁니다. 학생이 질문을 던지면, 시스템이 이 문서들을 뒤져서 답을 찾아주는 방식이죠. 최종적으로는 질문을 입력하면 답변을 받는 간단한 폼(Form) 형태가 될 것입니다.

[2:58 - 4:04] LLM이란 무엇인가?
어떻게 이걸 만들까요? 바로 LLM과 RAG를 사용합니다. 우선 LLM(Large Language Model)은 '거대 언어 모델'의 약자입니다. '언어 모델'부터 설명하자면, 지금까지 입력된 단어들을 바탕으로 그다음에 올 가장 적절한 단어(토큰)를 예측하는 도구입니다.

[4:04 - 5:18] 스마트폰의 예시
스마트폰의 자동 완성 기능을 생각해보세요. "How are"라고 치면 폰이 "you"를 추천하죠? "How are you"가 가장 논리적이니까요. 이런 건 보통 파라미터(매개변수)가 적은 '작은 언어 모델'입니다. 단순하고, 가끔은 좀 '멍청'하게 느껴질 수도 있죠.

[5:18 - 6:15] '거대' 언어 모델의 힘
반면 '거대' 언어 모델은 이름처럼 수십억 개의 파라미터를 가지고 방대한 양의 데이터로 학습되었습니다. 작동 방식은 다음 단어를 예측하는 것으로 같지만, 결과물은 마치 지능이 있는 인간과 대화하는 느낌을 줍니다. ChatGPT처럼요.

[6:15 - 7:36] 블랙박스로서의 LLM
내부적으로는 트랜스포머(Transformers) 같은 신경망을 사용하지만, 이 코스에서 이론이나 내부 구조를 깊게 파고들지는 않을 겁니다. 우리는 LLM을 **'블랙박스'**로 취급할 거예요. 질문을 이해하고 의미 있는 답을 내놓는 아주 똑똑한 상자로 보는 것이죠. 여기서 입력값을 **'프롬프트(Prompt)'**라고 부르고, 결과값을 **'답변(Answer)'**이라고 합니다.

[7:36 - 9:09] 프롬프트의 예시
예를 들어 프롬프트를 "질문: 코스에 어떻게 등록하나요? / 컨텍스트: [참고 자료] / 답변:" 이런 식으로 구성하면, LLM은 컨텍스트를 바탕으로 논리적인 답변을 완성해 줍니다.

[9:09 - 10:44] RAG: 검색 증강 생성
그다음은 RAG입니다. RAG는 **Retrieval(검색), Augmented(증강), Generation(생성)**의 약자입니다. 생성(LLM)을 검색(Search)으로 보강한다는 뜻이죠. 왜 이게 필요할까요?
예를 들어 ChatGPT에게 "연어 요리법"을 물으면 아주 잘 대답합니다. 이건 이미 학습 데이터에 있는 내용이니까요.

[10:44 - 12:24] RAG가 필요한 이유
하지만 "이 코스에 지금 들어가도 늦지 않았나요?"라고 물으면 LLM은 대답하지 못합니다. 어떤 코스인지 알 수 없으니까요. 이때 검색이 필요합니다. 검색을 통해 관련 정보를 찾아서 LLM에게 전달해주면, LLM은 그 컨텍스트를 바탕으로 정확한 답을 줄 수 있게 됩니다. 이것이 RAG의 핵심입니다.

[12:24 - 15:05] RAG 프레임워크의 작동 원리

지식 베이스(데이터베이스): 우리의 FAQ 문서 같은 데이터가 저장된 곳입니다.

사용자 질문(Q): 사용자가 질문을 던집니다.

검색: 질문을 지식 베이스로 보내 관련 문서(D1~D5)를 찾아옵니다.

프롬프트 생성: 찾은 문서들을 LLM에게 줄 프롬프트 안에 '컨텍스트'로 집어넣습니다.

생성: LLM이 질문과 컨텍스트를 보고 최종 답변을 만들어 사용자에게 전달합니다.

[15:05 - 17:17] 코스 계획
이 코스에서는 이 구성 요소들을 하나씩 배워나갈 겁니다. 처음에는 아주 단순한 '장난감' 같은 검색 엔진으로 시작해서, 나중에는 Elasticsearch로 바꾸고, 더 나아가 **벡터 서치(Vector Search)**까지 다룰 거예요. LLM도 OpenAI뿐만 아니라 오픈소스 모델로 교체해보는 법을 배울 겁니다. 마지막에는 Streamlit 같은 도구로 멋진 화면(UI)까지 입혀볼 거예요. 자, 이제 환경 구축부터 시작해 봅시다!

# 1. 검색 엔진 도구(minsearch.py)를 가져옵니다.
import minsearch
import json  # JSON 파일을 다루기 위한 파이썬 기본 도구를 불러옵니다.

# 2. 'documents.json' 파일을 컴퓨터 메모리로 읽어옵니다.
# 'rt'의 의미: 
#   - 'r' (Read): 읽기 전용으로 열겠다.
#   - 't' (Text): 이미지나 실행 파일이 아닌, 글자(텍스트) 파일로 읽겠다.
# f_in: 파일을 가리키는 '통로' 이름을 관습적으로 f_in(File Input)이라고 지은 것입니다.

with open('documents.json', 'rt') as f_in:
    # json.load(f_in): 통로(f_in)를 통해 들어온 텍스트를 파이썬이 이해하는 '리스트와 딕셔너리' 구조로 자동 변환합니다.
    docs_raw = json.load(f_in)

# 3. 모든 데이터를 한 줄씩 평평하게 펼쳐서 담을 빈 주머니를 만듭니다.
documents = []

# 4. 큰 상자(코스 단위)를 하나씩 꺼냅니다. (예: 데이터 엔지니어링 코스 상자)
for course_dict in docs_raw:
    # course_dict['course']에는 "data-engineering-zoomcamp" 같은 코스 이름이 들어있습니다.
    course_name = course_dict['course']
    
    # 5. 큰 상자 안에 담긴 작은 봉투(개별 질문/답변 문서)들을 하나씩 꺼냅니다.
    for doc in course_dict['documents']:
        # 6. [중요] 작은 봉투(doc)에는 자기가 어느 코스 출신인지 적혀있지 않습니다.
        # 그래서 부모 상자에서 확인한 코스 이름(course_name)을 봉투 겉면에 'course'라는 이름표로 붙여줍니다.
        doc['course'] = course_name
        
        # 7. 이제 이름표가 붙은 봉투를 전체 목록(documents)에 차곡차곡 쌓습니다.
        documents.append(doc)

# 8. 작업이 잘 끝났는지 숫자로 확인합니다.
print(f"정제 완료! 전체 문서 개수: {len(documents)}개")
print("-" * 30)

# 1. minsearch 엔진 안에 있는 'Index'라는 기계를 꺼내서 설정을 시작합니다.
# 이 기계는 나중에 사용자의 질문을 받으면 어디를 뒤져야 할지 미리 약속하는 단계입니다.
index = minsearch.Index(
    # text_fields: "내용 기반 검색"을 할 구역입니다.
    # 사용자가 던진 질문의 '의미'를 파악해서 이 세 곳(질문, 본문, 섹션)에서 유사한 단어를 찾습니다.
    text_fields=["question", "text", "section"],
    
    # keyword_fields: "정확한 필터링"을 할 구역입니다.
    # 의미를 따지지 않고, SQL의 'WHERE' 절처럼 정확히 일치하는 데이터만 골라낼 때 사용합니다.
    # 여기서는 "어느 코스인지"만 딱 구분하기 위해 'course'를 지정했습니다.
    keyword_fields=["course"]
)

# 2. .fit(documents): 위에서 정한 규칙대로 실제 데이터(948개의 문서)를 공부시킵니다.
# 'fit'은 "딱 맞추다"라는 뜻으로, 엔진이 데이터를 훑으며 단어들의 점수판(TF-IDF 행렬)을 
# 완성하여 메모리에 올리는 과정입니다. 이 작업이 끝나야 비로소 검색할 준비가 끝납니다.

keyword_fields (필터 구역): "오직 데이터 엔지니어링 코스에서만 찾아!"라고 명령할 때 사용합니다. 이 구역은 점수를 계산하지 않고, 단순히 예/아니오로 데이터를 걸러내는 역할을 합니다.

제4장: 쿼리 실행 및 검색 (Retrieval) (8:56 ~ 14:37)
"이제 쿼리를 날려볼까요? 사용자가 '강의가 이미 시작되었는데 지금 등록할 수 있나요?'라고 물었다고 칩시다. 우리는 이 질문에 대한 답을 포함할 가능성이 있는 문서들을 데이터베이스에서 찾아내야(Retrieve) 합니다.

이때 index.fit() 메서드를 쓰는데, 이건 사이킷런(Scikit-learn) API와 비슷하게 동작합니다. 엔진이 모든 문서를 분석해서 어떤 게 텍스트고 키워드인지 파악하게 되죠. 그다음 search() 함수를 쓰는데, 여기에 아주 재미있는 인자들이 들어갑니다.

바로 **부스팅(Boost)**입니다. 어떤 필드가 더 중요한지 정해주는 거죠. 예를 들어, 사용자가 물어본 단어가 '질문(Question)' 필드에 들어있다면, '본문(Text)'에 들어있는 것보다 훨씬 더 중요할 확률이 높습니다. 그래서 질문 필드에 3.0 정도의 부스트를 주면 질문 필드의 중요도가 3배 높아집니다. 기본값은 1.0이고 중요도를 낮추고 싶으면 0.5 같은 값을 줄 수도 있죠.

결과를 보면, 우리가 'enroll(등록)'이라는 단어를 썼는데 엔진은 'join(참여)'이라는 단어가 포함된 아주 적절한 문서를 찾아냅니다. 그런데 결과 중에 우리가 원치 않는 다른 코스의 답변이 섞여 나올 수도 있어요. 그래서 필터(Filter) 인자를 추가해서 '오직 데이터 엔지니어링 코스만 검색해줘'라고 명령하면, 이제 완벽하게 우리가 원하는 코스의 관련 문서들만 상위 5개(num_results) 뽑아낼 수 있습니다.

왜 boost를 설정하는지, search 함수 안의 인자들이 각각 어떤 역할을 하는지 초보자 눈높이에서 아주 친절하게 주석을 달아 드릴게요.


📍 [매핑 코드 4] 쿼리 실행 및 필터/부스팅 적용

Python
# 1. 사용자가 궁금해하는 질문(Query)을 문장으로 정의합니다.
query = 'the course has already started, can I still enroll?'

# 2. 부스팅(Boost) 설정: "어느 구역을 더 집중해서 볼까?"를 정합니다.
# 질문(question) 필드에 3.0을 주면, 본문(text)보다 3배 더 중요하게 취급합니다.
# 섹션(section)에 0.5를 주면, 중요도를 절반으로 낮춰서 참고만 하겠다는 뜻입니다.
# (기본값은 모두 1.0입니다.)
boost = {'question': 3.0, 'section': 0.5}

# 3. 실제 검색 엔진 가동! (search 함수 호출)
results = index.search(
    query=query,                      # 사용자의 질문 내용을 전달합니다.
    filter_dict={'course': 'data-engineering-zoomcamp'}, # [필터] 지정한 코스 데이터만 뒤집니다.
    boost_dict=boost,                 # [가중치] 위에서 설정한 중요도를 적용합니다.
    num_results=5                     # [개수] 가장 점수가 높은 결과 5개만 가져옵니다.
)

# 4. 결과 확인: 엔진이 찾아온 5개의 문서 뭉치를 하나씩 꺼내서 화면에 출력합니다.
for res in results:
    # 각 결과(res)는 딕셔너리 형태이며, 질문/답변/코스 정보가 들어있습니다.

제3장: 프롬프트 템플릿 설계 (3:10 ~ 6:42)
"좋은 프롬프트 엔지니어링의 관습 중 하나는 LLM에게 **역할(Role)**을 부여하는 것입니다. 여기서는 '너는 코스 조교(Teaching Assistant)야'라는 역할을 주겠습니다. GPT-4 같은 고급 모델일수록 이런 역할 부여가 효과적입니다. 물론 이건 과학이라기보다 예술에 가까워서, 여러분이 직접 여러 번 실험하며 최적의 문구를 찾아야 합니다.

우리가 사용할 프롬프트 템플릿을 만들어 봅시다.

역할 부여: 당신은 코스 조교입니다.

지시: 제공된 내용을 바탕으로 질문에 답하세요.

제약 조건: 맥락(Context)에 있는 사실만 사용하세요. 만약 답이 없다면 '답을 찾을 수 없습니다'라고 출력하세요.


Python
# [단계 2] 프롬프트 설계도(Template) 정의
# AI에게 어떤 페르소나(조교)를 가질지, 어떤 규칙을 지킬지 미리 정해두는 작업입니다.

# 💡 영상 3:33~6:34 구간 내용
# 괄호 {question}과 {context}는 나중에 .format()으로 채워질 빈칸입니다.

prompt_template = """
You're a course teaching assistant. Answer the QUESTION based on the CONTEXT from the FAQ database.
Use only the facts from the CONTEXT when answering the QUESTION.

QUESTION: {question}

CONTEXT: 
{context}
""".strip()

파이썬의 중괄호({})를 사용해서 나중에 실제 질문과 맥락이 들어갈 자리를 비워둔 템플릿을 완성했습니다. 이제 여기에 실제 데이터를 채워 넣을 차례입니다."


제4장: 맥락(Context) 데이터 조립하기 (6:42 ~ 9:00)
"검색 엔진이 찾아준 5개의 문서(results)를 하나의 긴 문자열로 합쳐야 합니다. 이를 **맥락(Context)**이라고 부릅니다.


Python
# [단계 3] 검색 결과(results)를 하나의 문자열 'context'로 조립
# 💡 영상 6:42 ~ 8:13 구간 내용

# 검색 결과들을 담을 빈 그릇(문자열)을 만듭니다.
context = ""

# 1.3장에서 찾은 5개의 결과(results)를 하나씩 꺼내서 합칩니다.
for doc in results:
    # 각 문서의 섹션, 질문, 답변 내용을 알아보기 쉽게 양식을 맞춥니다.
    # \n은 줄바꿈입니다. 정보 간의 경계를 주어 LLM이 혼동하지 않게 합니다.
    context = context + f"section: {doc['section']}\nquestion: {doc['question']}\nanswer: {doc['text']}\n\n"


루프(for문)를 돌면서 각 문서의 섹션(Section), 질문(Question), 본문(Answer)을 예쁘게 배치합니다. 문서와 문서 사이에는 줄 바꿈을 넣어 구분해 주고요. 이렇게 하면 LLM이 '아, 이 여러 개의 문서 중에서 내가 답을 찾아야겠구나'라고 쉽게 이해할 수 있습니다.


이제 prompt_template.format(question=q, context=context) 명령을 통해 비어있던 템플릿에 우리의 질문과 방금 만든 맥락을 쏙 집어넣습니다.

# 💡 영상 8:13 ~ 8:52 구간 내용

# 미리 만들어둔 설계도(prompt_template)의 {question}과 {context} 자리에 
# 실제 사용자의 질문(q)과 위에서 만든 지식 베이스 내용(context)을 집어넣습니다.
prompt = prompt_template.format(question=q, context=context).strip()

1. prompt vs response: 무엇이 다른가?
결론부터 말씀드리면, **prompt는 우리가 AI에게 보낸 "편지 본문"**이고, **response는 AI가 답장을 담아 보낸 "택배 상자 전체"**입니다.

prompt (질문+맥락):

우리가 format() 함수를 통해 직접 만든 **단순한 문자열(String)**입니다.

여기에는 우리가 지식 베이스에서 찾은 5개의 FAQ 내용(Context)이 모두 들어있기 때문에 양이 굉장히 많고 세세해 보일 수밖에 없습니다.

AI가 공부해야 할 참고서라고 보시면 됩니다.


response (응답 객체):

OpenAI 서버가 보낸 **복잡한 데이터 뭉치(Object)**입니다.

단순한 답변만 있는 게 아니라, "어떤 모델을 썼는지", "토큰을 얼마나 썼는지", "답변이 왜 끝났는지" 같은 부가 정보들이 가득 들어있습니다.

그래서 그냥 print(response)를 하면 답변 내용 외에 잡다한 정보가 다 보이는 것입니다.

📍 [전체 매핑 코드 4-1] OpenAI 호출 및 프롬프트 구성 맛보기

# [단계 1] 프롬프트 설계도(Template) 정의
# AI에게 어떤 페르소나(조교)를 가질지, 어떤 규칙을 지킬지 미리 정해두는 작업입니다.
prompt_template = """
You're a course teaching assistant. Answer the QUESTION based on the CONTEXT from the FAQ database.
Use only the facts from the CONTEXT when answering the QUESTION.

QUESTION: {question}

CONTEXT: 
{context}
""".strip()

# [단계 2] 검색 결과(results)를 하나의 문자열 'context'로 조립
# 1.3장에서 인덱싱한 지식 베이스의 내용을 LLM이 이해하기 쉬운 텍스트 뭉치로 변환합니다.
context = ""
for doc in results:
    # 섹션별로 구분하고 질문과 답변을 명시하여 데이터의 가독성을 높입니다.
    context = context + f"section: {doc['section']}\nquestion: {doc['question']}\nanswer: {doc['text']}\n\n"

# [단계 3] 질문과 맥락을 템플릿에 주입
# 설계도의 빈칸을 실제 데이터로 채워 최종 '명령서(Prompt)'를 완성합니다.
prompt = prompt_template.format(question=q, context=context)

# [단계 4] GPT-4o에게 최종 답변 요청
# 이제 완성된 명령서를 AI에게 전달합니다. 
# 이 방식이 바로 검색 증강 생성(RAG)의 핵심인 'Augmentation(증강)' 단계입니다.
response = client.chat.completions.create(
    model='gpt-4o',
    messages=[{"role": "user", "content": prompt}]
)

# [단계 5] 결과 확인
# AI가 FAQ 데이터를 바탕으로 생성한 '근거 있는 답변'을 확인합니다.
print(response.choices[0].message.content)

# 3. 답변 생성 시 모델 이름만 해당 서비스 것으로 교체
def llm(prompt):

    )
    return response.choices[0].message.content

def search(query):
    # 검색 시 제목(question)에 3배, 섹션에 0.5배의 가중치를 주는 설정입니다.
    boost = {'question': 3.0, 'section': 0.5}

    # 1.3장에서 인덱싱한 index 객체를 사용하여 검색을 수행합니다.
    results = index.search(
        query=query, # 사용자가 입력한 질문이 들어옵니다.

    )

# 💡 영상 2:33 ~ 3:34 구간 내용

def build_prompt(query, search_results):
    # AI에게 줄 역할과 제약 사항이 담긴 설계도입니다.
    prompt_template = """
You're a course teaching assistant. Answer the QUESTION based on the CONTEXT from the FAQ database.
Use only the facts from the CONTEXT when answering the QUESTION.

QUESTION: {question}

CONTEXT: 
{context}
""".strip()

    # 검색된 문서들을 하나의 긴 문자열(Context)로 조립합니다.
    context = ""
    for doc in search_results:
        # 각 문서의 섹션, 질문, 답변을 구분해서 텍스트로 합칩니다.
        context = context + f"section: {doc['section']}\nquestion: {doc['question']}\nanswer: {doc['text']}\n\n"
    
    # 설계도의 {question}과 {context} 자리에 실제 데이터를 집어넣습니다.
    prompt = prompt_template.format(question=query, context=context)
    return prompt # 완성된 최종 명령서를 반환합니다.

def rag(query):
    # 1단계: 검색 엔진에서 관련 정보를 찾습니다. (Retrieval)
    search_results = search(query)
    
    # 2단계: 찾은 정보와 질문을 합쳐 명령서를 만듭니다. (Augmentation)
    prompt = build_prompt(query, search_results)
    
    # 3단계: AI에게 답변 생성을 요청합니다. (Generation)
    answer = llm(prompt)
    
    return answer

GEM> zakard님, 아주 중요한 질문입니다. 데이터베이스 세계에서 '인덱스(Index)'라는 용어는 상황에 따라 조금씩 다르게 쓰여서 헷갈릴 수 있습니다. 초보자 관점에서 가장 쉽게 이해하실 수 있도록 비유와 함께 설명해 드릴게요.

1. 일상생활에서의 비유: 도서관의 '색인'
가장 고전적인 비유는 책 뒷면에 있는 색인(Index)입니다.

만약 책에서 "Kafka"라는 단어가 어디 있는지 찾으려면, 첫 페이지부터 끝까지 다 읽어야 합니다. (Full Scan)

하지만 뒷면의 '색인'을 보면 "Kafka: 120, 154, 200페이지"라고 적혀 있죠. 이걸 보고 바로 해당 페이지로 점프할 수 있습니다. (Index Search)

2. Elasticsearch에서의 '인덱스' (테이블 그 자체)
일반적인 SQL 데이터베이스(MySQL 등)에서는 데이터를 저장하는 통을 '테이블(Table)'이라고 부르지만, Elasticsearch에서는 이 통 자체를 '인덱스(Index)'라고 부릅니다.

RDBMS (MySQL 등): 데이터베이스 > 테이블 > 행(Row)

Elasticsearch: 클러스터 > 인덱스 > 문서(Document)

즉, index_name = "course-questions"라는 코드는 "앞으로 우리가 FAQ 데이터를 담아둘 거대한 저장 창고(테이블)의 이름을 'course-questions'라고 짓겠다"는 뜻입니다.

3. 왜 '인덱스'라는 이름을 쓸까요? (작동 원리)
Elasticsearch는 데이터를 저장할 때 그냥 쌓아두는 게 아니라, 저장하는 순간 검색하기 좋게 단어별로 쪼개서 사전처럼 정리해버립니다.

예를 들어 "How to run Kafka"라는 문서를 저장하면, Elasticsearch는 내부적으로 이런 표를 만듭니다:

GEM> zakard님, 알렉세이가 왜 하필 question에 3배의 보너스 점수를 줬을까요? 이는 검색의 '의도(Intent)'와 '정확도' 때문입니다.

그 이유를 세 가지 핵심 포인트로 정리해 드릴게요.

1. 질문과 질문의 일치 (Intent Matching)
사용자가 검색창에 입력하는 문장은 보통 질문 형태입니다.

사용자 입력: "수업이 시작했는데 지금 들어갈 수 있나요?"

문서 구조: 이 데이터는 question(질문)과 text(답변)로 나뉘어 있습니다.

사용자의 질문은 답변(text)보다는 FAQ의 제목(question)과 일치할 확률이 가장 높고, 그 제목과 매칭되었을 때 사용자가 원하는 정답일 가능성이 압도적으로 높습니다. 그래서 제목에 힘을 실어주는 것입니다.

2. 답변(text) 필드의 노이즈(Noise) 방지
답변 필드는 보통 문장이 길고 단어가 많습니다.

만약 text 필드에 "네, 가능합니다. 하지만 수업 자료를 지금 확인하시고..." 같은 문장이 있다면, 단순히 '수업', '지금' 같은 흔한 단어 때문에 엉뚱한 문서가 검색 상단에 걸릴 수 있습니다.

반면 question 필드는 핵심 키워드 위주로 압축되어 있죠. 여기에 가중치를 주면 핵심 키워드가 제목에 포함된 진짜 관련 있는 문서가 답변만 길게 늘어놓은 문서보다 위로 올라오게 됩니다.


3. 실무적인 '튜닝'의 영역
사실 '왜 하필 3배인가?'에 대한 수학적인 정답은 없습니다.

알렉세이는 수년간의 경험을 통해 "보통 제목에 2~3배 정도 가중치를 주면 검색 결과가 훨씬 만족스럽다"는 것을 알고 있는 겁니다.

만약 검색 결과가 여전히 엉뚱하다면 5배(^5)로 올릴 수도 있고, 결과가 너무 편협하면 1.5배(^1.5)로 낮출 수도 있습니다. 이를 리랭킹(Re-ranking) 또는 튜닝이라고 부릅니다.

from elasticsearch import Elasticsearch

# 1. 연결
es_client = Elasticsearch('http://localhost:9200')

# 2. 검색 함수 정의
def elastic_search(query):
    search_query = {
        "size": 5,
        "query": {
            "bool": {
                "must": {
                    "multi_match": {
                        "query": query,
                        "fields": ["question^3", "text", "section"],
                        "type": "best_fields"
                    }
                },
                "filter": {
                    "term": {
                        "course": "data-engineering-zoomcamp"
                    }
                }
            }
        }
    }
    response = es_client.search(index="course-questions", body=search_query)
    return [hit['_source'] for hit in response['hits']['hits']]

# 3. 통합 RAG 실행
def rag(query):
    search_results = elastic_search(query)
    prompt = build_prompt(query, search_results)
    return llm(prompt)

2. RAG의 3단계 흐름 (우리가 코딩한 것)

③ Generation (생성)
역할: 완성된 프롬프트를 보고 답변을 생성하는 것.

도구: OpenAI API.

핵심: LLM은 이제 자기 기억이 아니라 우리가 준 신선한 데이터를 바탕으로 답변하게 되었습니다.

영속성: 도커를 꺼도 데이터가 인덱스에 저장되어 남습니다.

YAML
services:
  elasticsearch:
    image: elasticsearch:8.4.3
    volumes:
      # [내 컴퓨터 E: 경로] : [컨테이너 내부 경로]
      - E:/DockerVolumes/elasticsearch-data:/usr/share/elasticsearch/data

      - "9200:9200"
이렇게 해두면 docker-compose up 딸깍 한 번으로, 어떤 루트에서 실행하든 데이터는 무조건 E: 드라이브로 흘러들어갑니다. 커서에게 "이 프로젝트용 docker-compose 파일 만들어줘, 데이터는 E:에 쌓이게"라고 한 번만 말하면 됩니다.

2. '이사'를 완벽히 끝내면 이런 걱정 자체가 사라집니다
가장 깔끔한 건 아까 말씀드린 도커 전체 이사(Export → Import)입니다.

이사를 성공하면: E:\DockerStorage 자체가 도커의 안방이 됩니다.

## 실행한 작업

1. **`e:\IT_SPACES\AI\ZoomCamp\LLM\docker-compose.elasticsearch.yml`** 추가  
   - 이미지·환경변수·포트는 기존 `docker run` / 강의와 동일

## 여기서 `docker compose up`이 안 된 이유

이 환경에서는 **Docker 데몬에 연결되지 않음** (`docker_engine` 파이프 없음).  
**Docker Desktop을 켠 뒤**, 로컬 터미널에서 아래만 실행하면 됩니다.

```powershell
cd E:\IT_SPACES\AI\ZoomCamp\LLM
docker compose -f docker-compose.elasticsearch.yml up -d
```

또는 Git Bash:

```bash
bash scripts/run-elasticsearch-e.sh
```

확인:

```powershell
curl.exe http://127.0.0.1:9200/
```

| 방식 | 역할 |
|------|------|
| **`docker-compose.elasticsearch.yml`** | E: 볼륨·설정의 **단일 기준** |
| **`run-elasticsearch-e.sh`** | 같은 compose를 **짧게 켜기** |

다른 프로젝트(NYC 택시 등)도 같은 패턴으로 **`docker-compose.yml` 하나 + `E:/DockerVolumes/프로젝트명`** 만 두면 되고, 매번 “전용 `.sh` 만들어줘”까지는 필요 없습니다.
