Chapter 1: 벡터 검색이란 무엇이며 어떻게 작동하는가? (0:00 ~ 3:28)

[스크립트 번역]
"안녕하세요! 이 코스에 참여해 주셔서 정말 반갑습니다. 저는 Qdrant의 개발자 에드보킷(Developer Advocate) 제니(Jenny)입니다. 오늘은 Qdrant를 이용한 벡터 검색의 간단한 예제를 함께 살펴볼 거예요.

벡터 검색이 '시맨틱 유사성(Semantic Similarity, 의미적 유사성)'을 통해 어떻게 작동하는지 시각적으로 설명해 드리고, Qdrant로 이를 어떻게 구현하는지 보여드릴게요. 오늘 저는 파이썬으로 작성된 간단한 주피터 노트북을 사용할 겁니다. 터미널은 딱 두 개의 명령어를 실행할 때만 쓸 거고요, 제 예술 실력은 좀 부족하지만 'Open Board'에 직접 그린 그림으로도 설명해 드릴게요. 비록 완벽하진 않아도 시각적인 설명이 이해를 돕는 가장 좋은 방법이라고 믿거든요.

여러분은 이미 벡터 검색이 무엇인지 어느 정도 알고 계시겠지만, 다시 한번 짚어보겠습니다. 반복은 언제나 이해에 도움이 되니까요.

여러분은 이미 전통적인 '키워드 검색(Keyword Search)'에 대해 알고 계실 겁니다. 예를 들어, 여러분이 '방망이(Bat)'를 검색한다고 해봅시다. 그게 과일박쥐(동물 Bat)를 의미할 수도 있겠죠. 전통적인 텍스트 기반 키워드 검색 방식에서는 쿼리와 문서 사이의 '단어'가 일치해야 합니다. 그래서 '동굴 속의 방망이(Bat in a cave)' 같은 문서를 찾아내죠. 즉, 키워드가 물리적으로 일치해야 검색이 됩니다.

하지만 '벡터 검색(Vector Search)'은 범위가 훨씬 넓습니다. 검색에 새로운 가능성을 열어주죠. 예를 들어, 여러분이 박쥐 그림(제가 그린 이 그림이 박쥐 같아 보인다면 말이죠!)을 찾고 싶다고 합시다. 벡터 검색은 이 쿼리와 이미지, 혹은 박쥐가 나오는 영상, 심지어 박쥐의 찍찍거리는 소리까지도 매칭할 수 있습니다.

게다가 텍스트만 다룰 때도 벡터 검색은 뛰어납니다. 서로 다른 단어로 표현되었지만 의미가 같은(동의어) 두 가지 아이디어를 연결할 수 있어요. 예를 들어 '날아다니는 쥐(Flying mouse)'라고 검색해도, 벡터 검색은 이것이 '박쥐(Bat)'를 묘사하는 방식이라는 것을 이해하고 두 텍스트를 매칭합니다. 왜냐하면 벡터 검색은 '의미의 수준(Semantics Level)'에서 작동하기 때문입니다.

텍스트를 직접 비교하는 키워드 방식과 달리, 벡터 검색에서는 이 텍스트들을 '벡터화된 표현(Vectorized Representations)'으로 변환해서 작업합니다. 텍스트나 이미지, 영상이 숫자 형태의 벡터가 되고, 이들 사이의 유사성(가까운 정도)을 수치로 계산하는 것이죠. 이때 다양한 '유사도 메트릭(Similarity Metrics)'이 사용되는데, 이는 나중에 실습에서 자세히 다루겠습니다. 이것이 바로 벡터 검색입니다."

Step 2: 데이터셋 연구 (Study the Dataset)

실제 작동하는 벡터 검색 솔루션을 구축하기 위해서는 (그리고 일반적으로 벡터 검색이 언제, 어떻게 필요한지 이해하기 위해), 데이터셋을 연구하고 우리가 다루는 데이터의 성격과 구조를 파악하는 것이 좋습니다. 예를 들어 다음과 같습니다:

모달리티(modality) — 데이터가 텍스트, 이미지, 비디오 중 무엇입니까? 아니면 이들의 조합입니까?

세부 사항(specifics) — 만약 텍스트라면: 어떤 언어가 사용되었는지, 텍스트 조각(chunk)의 크기는 어느 정도인지, 특수 문자가 포함되어 있는지 등을 확인해야 합니다.

올바른 데이터 "스키마(schema)" (무엇을 벡터화할지, 무엇을 메타데이터로 저장할지 등)

1. 임베딩(Embedding)이란 무엇인가?
컴퓨터는 "등록 이메일은 언제 오나요?"라는 문장을 읽어도 그게 '기다림'이나 '절차'에 관한 것인지 이해하지 못합니다. 단지 텍스트(문자열) 데이터로만 인식하죠.

임베딩은 이 텍스트의 '의미'를 컴퓨터가 계산할 수 있는 '숫자들의 목록(벡터)'으로 변환하는 기술입니다.

의미의 공간화: 비슷한 의미를 가진 문장들은 숫자 공간상에서 서로 가까운 위치에 있게 됩니다.

예: "등록 확인 메일"과 "언제 수강 확정되나요?"는 단어는 다르지만, 임베딩 공간에서는 매우 가까운 좌표에 위치합니다.

고차원 벡터: 우리가 선택한 jina-embeddings-v2-small-en 모델은 문장 하나를 512개의 숫자(EMBEDDING_DIMENSIONALITY = 512)로 이루어진 하나의 점으로 표현합니다.

2. FastEmbed의 기능과 장점
노트북에서 강조하는 FastEmbed는 이 임베딩 과정을 수행하는 '엔진'입니다. 특히 Qdrant와 찰떡궁합인 최적화된 라이브러리죠.

핵심 기능:
밀집 임베딩(Dense Embedding) 생성: 텍스트를 고밀도의 숫자 벡터로 변환합니다. 우리가 오늘 실습에서 가장 주력으로 사용하는 기능입니다.

경량화 및 속도: PyTorch나 TensorFlow 같은 거대한 프레임워크 없이도 ONNX Runtime을 사용해 CPU에서도 엄청나게 빠른 속도로 숫자를 계산해냅니다.

다양한 모델 지원: 텍스트뿐만 아니라 이미지, 희소 벡터(Sparse), 다중 벡터(Multivector) 임베딩까지 지원하여 하이브리드 검색을 가능하게 합니다.

Qdrant와의 직접 통합: 텍스트를 따로 변환해서 넣을 필요 없이, Qdrant 클라이언트를 통해 텍스트를 바로 전달하면 내부에서 자동으로 임베딩을 처리해주는 편리함을 제공합니다.

한 문장 요약:
임베딩은 텍스트를 **'의미가 담긴 좌표'**로 만드는 것이고, FastEmbed는 그 좌표를 **'매우 빠르고 가볍게 계산해주는 도구'**입니다.

Step 3: FastEmbed를 사용한 임베딩 모델 선택 (Choosing the Embedding Model with FastEmbed)
이제 우리는 영어로 된 작은 텍스트 조각(강좌 관련 질문 및 답변 쌍)을 임베딩한다는 사실을 알고 있으므로, 이 데이터를 벡터로 변환하기에 적합한 임베딩 모델을 선택할 수 있습니다.

임베딩 모델 선택은 다음과 같은 여러 요인에 따라 달라집니다:

수행하려는 작업, 데이터의 모달리티(텍스트, 이미지 등) 및 데이터의 특성

검색 정확도와 리소스 사용량 사이의 절충(Trade-off) (임베딩 크기가 클수록 더 많은 저장 공간과 메모리가 필요함)

추론 비용 (특히 서드파티 API 제공업체를 사용하는 경우)

기타 요인들

임베딩 모델을 선택하는 가장 좋은 방법은 자신의 실제 데이터를 사용하여 다양한 옵션을 테스트하고 벤치마킹하는 것입니다.

이 노트북에서는 임베딩 제공자로 FastEmbed를 사용합니다.
FastEmbed는 Qdrant를 위해 특별히 설계된 최적화된 임베딩 솔루션입니다. PyTorch나 TensorFlow 같은 무거운 프레임워크 없이도 CPU 친화적이고 낮은 지연 시간(Low-latency)으로 임베딩을 생성합니다. 양자화된(Quantized) 모델 가중치와 ONNX Runtime을 사용하여, CPU 환경에서 기존의 Sentence Transformers보다 훨씬 빠르면서도 경쟁력 있는 정확도를 유지합니다.

FastEmbed가 지원하는 기능:

밀집 임베딩(Dense embeddings): 텍스트와 이미지용 (가장 일반적인 유형이며, 오늘 우리가 사용할 방식입니다)

희소 임베딩(Sparse embeddings): 예: BM25, 희소 신경망 임베딩

다중 벡터 임베딩(Multivector embeddings): 예: ColPali, ColBERT 등 후기 상호작용(Late interaction) 모델

리랭커(Rerankers)

이 모든 기능은 Qdrant에서 직접 사용할 수 있습니다. 또한 FastEmbed와 Qdrant의 통합 덕분에 텍스트나 이미지를 Qdrant 클라이언트에 직접 전달하여 임베딩을 처리할 수 있습니다. 이번 실습에서는 로컬 추론을 위해 FastEmbed를 사용할 것이므로, 기기의 리소스를 고려하여 모델을 선택해야 합니다.

size_in_GB: 0.42: 모델의 무게입니다. 약 420MB 정도


💡 왜 우리는 Jina 모델을 선택했는가?
출력 결과물 중에 jinaai/jina-embeddings-v2-small-en을 선택한 이유는 명확합니다.

입력 한도 (8192 tokens): 위 예시의 BGE 모델은 512단어만 읽지만, Jina는 무려 8,192단어까지 읽을 수 있습니다. 긴 답변도 잘리지 않고 벡터화됩니다.

편의성: 질문과 문서에 별도의 접두사(Prefix)를 붙일 필요가 없어 코드가 깔끔해집니다.

효율성: 512차원(dim)을 유지하면서도 모델 크기(size_in_GB)가 0.12GB로 매우 가벼워 로컬 CPU 환경에서 부담이 없습니다.

이제 이 "숫자 변환기(모델)"의 정체를 확실히 알았으니, 이 모델이 뽑아준 숫자들을 저장할 저장소를 만들 차례입니다.

GEM> json.dumps는 파이썬 객체(리스트, 딕셔너리 등)를 JSON 형식의 문자열(String)로 변환해주는 함수입니다. 여기서 s는 String을 의미합니다.

노트북 코드에서 사용된 방식을 바탕으로 왜 이 함수를 쓰는지, 그리고 주요 옵션들이 어떤 역할을 하는지 직관적으로 설명해 드릴게요.

1. 왜 사용하는가? (객체 → 문자열)
파이썬의 dict 객체를 그대로 print()하면 한 줄로 길게 출력되어 사람이 읽기 매우 힘듭니다. json.dumps를 사용하면 이 데이터를 구조화된 문자열로 바꾸어 예쁘게 출력하거나, 파일로 저장하거나, 네트워크를 통해 전송할 수 있는 상태로 만듭니다.

2. 주요 파라미터 설명
노트북 코드에 나온 예시를 보겠습니다.

Python
print(json.dumps(model, indent=2))
model: 변환할 대상(여기서는 모델 정보가 담긴 딕셔너리)입니다.

indent=2: 가장 중요한 옵션입니다. 들여쓰기를 2칸씩 적용하라는 뜻입니다. 이 옵션이 있어야 줄 바꿈이 정돈되어 우리가 보기 편한 "예쁜" 형태로 출력됩니다. 만약 이 옵션이 없으면 모든 데이터가 한 줄로 다닥다닥 붙어서 나옵니다.


3. json.load vs json.dump (참고)
헷갈리기 쉬운 용어들을 정리해 드릴게요.

함수		방향		결과물
json.loads()	문자열 → 객체	파이썬 딕셔너리/리스트 (메모리상 존재)
json.dumps()	객체 → 문자열	JSON 텍스트 (출력/로그 확인용)
json.load()	파일 → 객체	파일에서 데이터를 읽어와 파이썬 객체로 변환
json.dump()	객체 → 파일	파이썬 객체를 JSON 파일로 직접 저장

💡 직관적인 파라미터 설명
이 단계는 데이터를 넣기 전, "어떤 규격의 데이터를 담을 것인가"를 결정하는 매우 중요한 단계입니다.

size=EMBEDDING_DIMENSIONALITY (512):

**우리가 선택한 Jina 모델은 문장을 512개의 숫자로 변환합니다. 만약 이 그릇(컬렉션)의 크기를 512가 아닌 다른 숫자(예: 768)로 만들면, 데이터가 들어갈 때 "규격 불일치" 에러가 발생합니다. 즉, 모델이 만드는 숫자 개수와 컬렉션의 크기를 반드시 맞춰야 합니다.

client.create_collection:

Step 5: 포인트 생성, 임베딩 및 컬렉션 삽입 (Create, Embed & Insert Points)
포인트(Points)는 Qdrant 데이터의 핵심 단위입니다. 각 포인트는 다음 세 가지로 구성됩니다:

ID: 고유 식별자입니다. Qdrant는 64비트 정수와 UUID를 모두 지원합니다.

Vector: 데이터의 의미를 나타내는 임베딩(숫자 목록)입니다.

Payload (선택사항): 키-값 쌍으로 이루어진 추가 메타데이터입니다.


1. 포인트 구조 생성 (Point Structuring)
먼저 우리가 가진 데이터를 Qdrant가 이해할 수 있는 포인트 형태로 변환합니다.


Python
points = [] # 생성된 포인트들을 담을 리스트
id = 0 # 포인트마다 부여할 고유 ID (0부터 시작)

# 로드한 로우 데이터(documents_raw)를 순회하며 포인트 생성
for course in documents_raw:
    for doc in course['documents']:

        # Qdrant의 포인트 구조(PointStruct)를 정의합니다.
        point = models.PointStruct(
            id=id, # 고유 정수 ID 부여
            
            # [핵심] FastEmbed를 사용하여 로컬에서 텍스트를 즉시 임베딩합니다.
            # "jinaai/jina-embeddings-v2-small-en" 모델을 사용하여 text 필드를 벡터로 변환합니다.
            vector=models.Document(text=doc['text'], model=model_handle),
            
            # 검색 결과와 함께 출력하거나 필터링에 사용할 메타데이터를 저장합니다.
            payload={
                "text": doc['text'],      # 원문 답변 텍스트
                "section": doc['section'], # 속한 섹션 (예: General course-related questions)
                "course": course['course'] # 강좌 이름 (예: data-engineering-zoomcamp)
            }
        )
        points.append(point) # 생성된 포인트를 리스트에 추가

        id += 1 # 다음 포인트를 위해 ID 증가



2. 임베딩 및 업로드 (Embedding & Upsert)
이제 생성된 포인트들을 컬렉션에 업로드합니다.

동작 방식: 먼저 FastEmbed가 선택한 모델 파일을 다운로드합니다. (기본 경로는 임시 폴더입니다.) 그 후, 사용자의 컴퓨터(로컬)에서 직접 추론(Inference)을 수행하여 텍스트를 벡터로 바꿉니다.

마지막으로, 생성된 포인트들이 컬렉션에 삽입(Upsert)되고 벡터 인덱스가 구축됩니다.

Python

Step 6: Running a Similarity Search
단계 6: 유사도 검색 실행하기

이제 주어진 쿼리 임베딩에 대해 Qdrant에서 가장 유사한 텍스트 벡터를 찾아봅시다. 즉, 주어진 질문에 대해 가장 관련성이 높은 답변을 찾는 과정입니다.

유사도 검색 작동 원리 (How Similarity Search Works)
Qdrant는 컬렉션을 생성할 때 정의된 거리 메트릭(Distance Metric)을 사용하여, 벡터 인덱스를 기반으로 쿼리 벡터와 저장된 벡터들을 비교합니다.

가장 가깝게 일치하는 항목들이 유사도 순으로 정렬되어 반환됩니다.

벡터 인덱스는 근사 최근접 이웃(Approximate Nearest Neighbor, ANN) 검색을 위해 구축되었으며, 이를 통해 대규모 벡터 검색이 가능해집니다.

벡터 검색을 위한 벡터 인덱스 선택에 대해 더 자세히 알고 싶다면 "벡터 데이터베이스란 무엇인가" https://qdrant.tech/articles/what-is-a-vector-database/

기사를 확인하거나, 더 기술적인 심층 분석을 원하신다면 "필터링 가능한 HNSW(Hierarchical Navigable Small World)"에 관한 기사

https://qdrant.tech/articles/filtrable-hnsw/

를 확인해 보세요.

1. 왜 벡터 인덱스가 필요한가요?
단순하게 생각하면, 내가 던진 질문과 DB에 있는 모든 답변을 하나하나 다 비교해보면 됩니다. 하지만 데이터가 100만 개, 1,000만 개로 늘어나면 이 작업은 너무 오래 걸립니다.

인덱스가 없을 때: 모든 데이터와 일일이 거리를 계산함 (정확하지만 매우 느림).

인덱스가 있을 때: 데이터를 비슷한 것끼리 미리 묶어두거나 지도를 그려두어, 관련 있는 구역만 뒤짐 (압도적으로 빠름).


2. 우리가 실습 중인 Qdrant의 핵심 기술: HNSW
원문에서 언급된 HNSW(Hierarchical Navigable Small World)가 바로 이 벡터 인덱스의 대표적인 방식입니다.

계층형(Hierarchical): 마치 구글 지도에서 '국가 → 도시 → 동네' 순으로 줌인하는 것처럼, 여러 층의 지도를 만듭니다.

탐색 가능한 작은 세상(Navigable Small World): 모든 점이 연결된 게 아니라, 몇 단계의 연결만 거치면 목적지에 도달할 수 있는 '좁은 세상' 네트워크를 만듭니다.


3. ANN (Approximate Nearest Neighbor)의 관계
인덱스를 사용하면 "완벽하게 똑같은 것"보다는 "거의 확실히 제일 가까운 것"을 찾게 됩니다. 이걸 근사 최근접 이웃(ANN) 검색이라고 합니다.

100% 정확도를 조금 양보하는 대신, 수백만 개의 데이터를 0.001초 만에 검색할 수 있게 해주는 마법 같은 기술인 셈이죠.

요약하자면
벡터 인덱스는 데이터가 너무 많아서 하나하나 찾기 힘들 때, 비슷한 것끼리 길을 연결해두어 순식간에 정답 근처로 안내해주는 고속도로라고 이해하시면 됩니다.

단계 7: 필터를 사용한 유사도 검색 실행하기 (Running a Similarity Search with Filters)

우리는 메타데이터 필터를 사용하여 검색 결과를 더욱 세밀하게 다듬을 수 있습니다.

Qdrant의 독자적인 벡터 인덱스 구현 방식인 필터링 가능한 HNSW (Filterable HNSW)를 사용하면, 필터링 조건이 포함된 상태에서도 정밀하고 확장 가능한 벡터 검색이 가능합니다.

예를 들어, 데이터셋에 포함된 세 가지 코스 중 특정 코스와 관련된 질문에 대한 답변만 검색할 수 있습니다.
must 필터를 사용하면 데이터 포인트가 검색 결과에 포함되기 위해 지정된 모든 조건을 반드시 만족해야 함을 보장합니다.

Qdrant는 should, must_not, range 등 다른 필터 유형도 지원합니다. 전체 개요를 확인하려면 필터링 가이드(Filtering Guide)를 참조하세요.

효율적인 필터링을 위해서는 페이로드 필드(payload fields)의 인덱싱을 활성화해야 합니다.

def search_in_course(query, course="mlops-zoomcamp", limit=1): # 검색어와 코스 이름(기본값 mlops-zoomcamp)을 받는 함수를 정의합니다.

    results = client.query_points( # Qdrant 클라이언트를 통해 쿼리를 수행합니다.
        collection_name=collection_name, # 대상 컬렉션의 이름을 지정합니다.
        query=models.Document( # "jinaai/jina-embeddings-v2-small-en"을 사용하여 쿼리 텍스트를 로컬에서 임베딩합니다.
            text=query, # 사용자가 입력한 질문 텍스트입니다.
            model=model_handle # 앞서 정의한 Jina 모델 핸들을 사용합니다.
        ),
        query_filter=models.Filter( # 코스 이름으로 결과를 필터링합니다.
            must=[ # 아래 조건을 반드시 만족해야 합니다.
                models.FieldCondition(
                    key="course", # "course" 필드를 확인합니다.
                    match=models.MatchValue(value=course) # 입력받은 코스 이름과 정확히 일치하는지 검사합니다.
                )
            ]
        ),
        limit=limit, # 가장 유사한 상위 매치 항목의 개수를 설정합니다.
        with_payload=True # 결과와 함께 메타데이터(텍스트 내용 등)를 가져오도록 설정합니다.
    )

    return results # 검색 결과 객체를 반환합니다.

import minsearch # 이번 실습에서 사용할 가벼운 검색 엔진인 minsearch를 불러옵니다.

3. 검색 함수 만들기
특정 코스(예: 데이터 엔지니어링) 내에서 질문과 가장 비슷한 5개의 문서를 찾아오는 함수입니다.

def search(query): # 사용자의 질문(query)을 받아서 검색 결과를 돌려주는 함수를 정의합니다.
    # 특정 필드에 점수를 더 주는 가중치(boost) 설정입니다.
    # 질문(question) 필드에서 일치하면 점수를 3배(3.0) 더 주고, 섹션은 0.5배만 줍니다.
    boost = {'question': 3.0, 'section': 0.5} 

    results = index.search( # 인덱스에 저장된 데이터에서 검색을 수행합니다.
        query=query, # 사용자가 입력한 검색어입니다.
        filter_dict={'course': 'data-engineering-zoomcamp'}, # 반드시 이 코스에 해당하는 데이터만 찾도록 필터를 겁니다.
        boost_dict=boost, # 위에서 설정한 가중치를 적용하여 검색 결과 순위를 결정합니다.
        num_results=5 # 검색 결과 중 가장 관련성이 높은 상위 5개만 가져옵니다.
    )

    return results # 최종 검색 결과 리스트를 함수 밖으로 반환합니다.

4. 프롬프트 조립 및 LLM 답변 생성
Python
def build_prompt(query, search_results): # 질문과 검색 결과들을 받아서 하나의 큰 명령서를 만드는 함수입니다.
    # LLM에게 어떤 역할과 규칙을 줄지 정하는 템플릿(틀)입니다.
    # 3중 따옴표(""")는 여러 줄의 문장을 하나의 문자열로 묶을 때 사용합니다.
    prompt_template = """
You're a course teaching assistant. Answer the QUESTION based on the CONTEXT from the FAQ database.
Use only the facts from the CONTEXT when answering the QUESTION.

QUESTION: {question}

CONTEXT: 
{context}
""".strip() # .strip()은 앞뒤에 불필요한 빈칸이나 줄바꿈을 제거해줍니다.

    context = "" # 검색 결과들을 하나로 합쳐서 담을 빈 주머니(문자열)를 만듭니다.
    
    for doc in search_results: # 검색 엔진이 찾아준 5개의 문서를 하나씩 꺼냅니다.
        # 각 문서의 섹션, 질문, 답변 내용을 보기 좋게 정리해서 context 주머니에 차곡차곡 쌓습니다.
        # f"..."는 변수 값을 문장 중간에 쉽게 끼워 넣는 파이썬의 편리한 문법입니다.
        context = context + f"section: {doc['section']}\nquestion: {doc['question']}\nanswer: {doc['text']}\n\n"
    
    # 템플릿의 {question} 자리에는 사용자의 질문을, {context} 자리에는 위에서 만든 텍스트를 집어넣습니다.
    prompt = prompt_template.format(question=query, context=context).strip()
    return prompt # 완성된 최종 명령서를 돌려줍니다.

5. LLM 답변 생성 함수 (llm)
Python
def llm(prompt): # 완성된 명령서(시험지)를 인공지능에게 보내서 답을 받아오는 함수입니다.
    # OpenAI의 '채팅 답변 생성' 기능을 호출합니다.
    response = client.chat.completions.create(
        model='gpt-4o', # 우리가 사용할 두뇌 모델의 이름입니다. (현재 가장 똑똑한 모델 중 하나죠!)
        # messages는 대화 목록입니다. 
        # "role": "user"는 "사용자가 이 말을 했어"라는 뜻이고, 
        # "content": prompt는 위에서 우리가 열심히 조립한 그 명령서를 의미합니다.
        messages=[{"role": "user", "content": prompt}] 
    )
    
    # AI가 여러 가지 답변을 내놓을 수 있는데, 그중 가장 첫 번째(choices[0]) 답변의 
    # 실제 메시지 내용(message.content)만 문자열로 쏙 골라내어 결과값으로 돌려줍니다.
    return response.choices[0].message.content

def rag(query): # 사용자의 질문 하나만 입력하면 검색부터 답변까지 자동으로 처리하는 통합 함수입니다.
    # 1. search 함수를 써서 FAQ 데이터베이스에서 관련 있는 정보 5개를 찾아옵니다.
    search_results = search(query)
    
    # 2. build_prompt 함수를 써서 찾은 정보와 질문을 합쳐 하나의 거대한 명령서를 만듭니다.
    prompt = build_prompt(query, search_results)
    
    # 3. llm 함수를 써서 조립된 명령서를 AI에게 보내 최종 답변을 받아옵니다.
    answer = llm(prompt)
    
    # 4. 우리에게 최종 답변을 친절하게 돌려줍니다.
    return answer

from qdrant_client import QdrantClient, models # Qdrant를 다루기 위한 도구들을 가져옵니다.

# 로컬(Docker)에서 돌아가고 있는 Qdrant 서버 주소에 접속합니다.
# (지난번 설정에 따라 이 데이터는 실제로는 E: 드라이브 볼륨에 저장됩니다.)
# REST default (~5s) can ReadTimeout on create_collection; use gRPC :6334 + long timeout.
QD_TIMEOUT_SEC = 300
qd_client = QdrantClient(
    url="http://127.0.0.1:6333",
    grpc_port=6334,
    prefer_grpc=True,
    timeout=QD_TIMEOUT_SEC,
    check_compatibility=False,
)


# 우리가 사용할 Jina AI 임베딩 모델의 설정값입니다.

EMBEDDING_DIMENSIONALITY = 512 # 이 모델이 만드는 벡터의 길이는 512입니다.

# 혹시 예전에 만들어둔 똑같은 이름의 컬렉션이 있다면 삭제합니다.

    timeout=QD_TIMEOUT_SEC,

# 1. 'course' 필드에 대한 인덱스(색인) 생성

# [6단계] 검색된 지식을 바탕으로 AI가 최종 답변을 생성하는 RAG 함수
def rag(query):
    # 1. 벡터 검색 함수를 호출하여 관련 지식(Context)을 5개 가져옵니다.
    search_results = vector_search(query)
    
    # 2. 검색 결과와 사용자 질문을 조합하여 LLM용 프롬프트를 제작합니다.
    # (앞서 정의한 build_prompt 함수를 사용합니다.)
    prompt = build_prompt(query, search_results)
    
    # 3. 완성된 프롬프트를 LLM(예: OpenAI/Gemma 등)에게 보내 답변을 생성합니다.
    answer = llm(prompt)
    
    # 4. AI가 생성한 최종 답변을 사용자에게 전달합니다.
    return answer

Qdrant를 활용한 하이브리드 검색(Hybrid Search)

밀집 임베딩(Dense embeddings) 기반의 벡터 검색은 데이터의 의미(Semantics)를 포착하므로, 쿼리(질의어)와 문서에 동일한 용어를 사용하지 않더라도 관련 항목을 찾아낼 수 있습니다. 하지만 역사적으로 우리는 키워드의 존재 여부에 의존하는 다른 방법들도 사용해 왔습니다. Bag-of-Words, TF-IDF, BM25와 같은 방식들은 여전히 유용하며, 어떤 경우에는 밀집 임베딩보다 더 선호되기도 합니다.

희소 벡터 (Sparse vectors)
놀랍게도 키워드 기반 검색 역시 벡터 검색으로 구현되지만, 이때 사용되는 벡터들은 대개 '희소(Sparse)'합니다. 이는 벡터 차원의 대다수가 0으로 채워져 있음을 의미합니다. 특정 벡터 차원에서 0이 아닌 값은 해당 위치에 할당된 사전(Dictionary)의 용어가 존재함을 나타냅니다. 즉, 희소 벡터 방식에서는 각 단어나 구절이 고유한 위치를 갖는 사전이 존재합니다. 벡터가 희소하기 때문에, 사전 끝에 새로운 용어를 추가하기만 하면 이론적으로 사전을 무한히 확장할 수 있습니다.

GEM> 쉽게 말해, "전체 단어장 중에서 이번 문장에 쓰인 단어 번호에만 '1'이라고 체크하고 나머지는 '0'으로 비워두는 방식"입니다.

새로운 단어가 생기면 단어장 맨 뒤에 칸을 하나 더 만들기만 하면 되기 때문에, 사전을 무한정 늘리기가 매우 쉽다는 뜻입니다.


이렇게 유연한 사전을 사용한다는 사실 덕분에, 희소 벡터는 '정확한 일치(Exact matches)'를 찾는 데 탁월합니다. 밀집 벡터에게는 단순한 무작위 문자열의 나열처럼 보일 수 있는 고유 명사나 식별자(ID) 같은 텍스트도 희소 벡터는 충분히 다룰 수 있기 때문입니다. 밀집 임베딩 모델 역시 사전을 가지고 있지만, 모델이 한 번 훈련되고 나면 이를 확장하는 것은 쉽지 않으며 모델의 미세 조정(Fine-tuning)이 필요합니다. 일반적인 사용자가 거기까지 진행하는 경우는 드뭅니다.

BM25
희소 임베딩을 생성하는 방법에는 여러 가지가 있지만, BM25는 업계 표준과도 같으며 가장 대중적인 형태는 90년대에 등장했습니다. 이는 통계적 모델(신경망이 관여하지 않음)이므로 매우 빠르고 가볍습니다. 검색 벤치마크에서 보통 탄탄한 기준점(Baseline) 역할을 하므로 이를 무시해서는 안 됩니다.

BM25는 'Best Matching 25'의 약자로, 주어진 쿼리에 대해 특정 문서가 얼마나 관련이 있는지 계산하는 공식을 만들기 위한 25번째 시도였습니다. 수학적 배경에 관심이 있다면 위키피디아 페이지에서 아주 잘 설명되어 있으니 확인해 보시기 바랍니다. 일반적으로 BM25는 단어 빈도(Term Frequency, TF)와 역문서 빈도(Inverse Document Frequency, IDF)라는 두 가지 핵심 개념을 결합하여 검색 엔진이 문서의 관련성을 판단하도록 돕는 랭킹 함수입니다.

단어 빈도(TF) 요소는 쿼리 용어가 여러 번 포함된 문서에 보상을 주지만, 수익 체감의 법칙이 적용됩니다. 즉, 특정 단어가 10번 등장하는 문서가 1번 등장하는 문서보다 반드시 10배 더 나은 것은 아니라고 판단합니다.

역문서 빈도(IDF) 요소는 희귀한 단어의 중요성을 높이고, 많은 문서에 공통적으로 나타나는 흔한 단어의 가중치는 줄입니다. 희귀한 용어일수록 관련 결과를 구별하는 데 더 많은 정보를 담고 있기 때문입니다.

또한 BM25는 문서의 길이를 정규화하는 기능을 포함하고 있어, 단순히 문서의 양이 방대하다는 이유만으로 긴 문서가 불공평한 이득을 취하는 것을 방지합니다.

우리의 경우, FastEmbed에서 제공하는 구현체를 사용할 것입니다. 기본부터 시작해 보겠습니다.

import subprocess

container_name = "qdrant-hybrid-search"

# Reuse an existing Qdrant if 6333/6334 are already occupied.
existing = subprocess.run(
    ["docker", "ps", "--filter", "publish=6333", "--format", "{{.Names}}"],
    capture_output=True,
    text=True,
)

if existing.returncode == 0 and existing.stdout.strip():
    print(f"Qdrant already running in container: {existing.stdout.strip()}")
else:
    cmd = [
        "docker", "run", "-d",
        "--name", container_name,
        "-p", "6333:6333",
        "-p", "6334:6334",
        "-v", "./qdrant_storage:/qdrant/storage:z",
        "qdrant/qdrant",
    ]
    started = subprocess.run(cmd, capture_output=True, text=True)
    if started.returncode != 0:
        raise RuntimeError(started.stderr.strip() or "Failed to start Qdrant container")
    print(f"Started Qdrant container: {started.stdout.strip()}")

Step 2-2: BM25 전용 컬렉션 생성 (IDF 설정)
이제 데이터를 담을 보관함을 만듭니다. 여기서 modifier=models.Modifier.IDF 설정이 가장 중요합니다.

Python
from qdrant_client import models # Qdrant의 데이터 모델들을 불러옵니다.

# "zoomcamp-sparse"라는 이름의 보관함을 만듭니다.
client.create_collection(
    collection_name="zoomcamp-sparse", # 보관함 이름
    sparse_vectors_config={ # 희소 벡터(키워드용) 설정을 시작합니다.
        "bm25": models.SparseVectorParams( # 'bm25'라는 이름의 벡터 공간을 정의합니다.

        )
    }
)

Step 2-3: 데이터 입력 (Upsert)
이제 텍스트를 숫자로 바꿔서 보관함에 집어넣습니다. FastEmbed 덕분에 텍스트만 전달하면 Qdrant가 알아서 벡터로 바꿔줍니다.

Python
import uuid # 각 데이터에 겹치지 않는 고유 ID를 주기 위한 도구입니다.

# 데이터를 보관함에 밀어넣습니다(Upsert).
client.upsert(
    collection_name="zoomcamp-sparse", # 아까 만든 보관함 이름을 지정합니다.
    points=[
        models.PointStruct( # 하나의 데이터 단위(Point)를 정의합니다.
            id=uuid.uuid4().hex, # 겹치지 않는 랜덤한 ID를 부여합니다.
            vector={
                "bm25": models.Document( # 텍스트를 BM25 벡터로 변환하라고 지시합니다.
                    text=doc["text"], # 변환할 본문 텍스트입니다.
                    model="Qdrant/bm25", # 사용할 통계 모델을 지정합니다.
                ),
            },
            payload={ # 검색 결과와 함께 보고 싶은 부가 정보들을 담습니다.
                "text": doc["text"],     # 본문
                "section": doc["section"], # 섹션 이름
                "course": course["course"], # 코스 이름
            }
        )
        for course in documents_raw # 전체 코스를 하나씩 돕니다.
        for doc in course["documents"] # 코스 안의 문서들을 하나씩 돕니다.
    ]
)

3. 왜 이렇게 쓰나요? (이유)
간결함: 파이썬 개발자들은 여러 줄의 append 코드를 한 줄로 줄여 쓰는 것을 선호합니다. (파이썬스러운 방식, Pythonic)

속도: 내부적으로 append를 여러 번 호출하는 것보다 이 방식이 리스트 생성 속도가 조금 더 빠릅니다.

가독성 (익숙해지면): "무엇(PointStruct)을 만들 건데, 어디서(for... for...) 가져온다"가 한눈에 들어온다고 생각합니다.

💡 핵심 포인트
콜론(:)이 없는 이유: 리스트 대괄호 [] 안에 들어가는 '식(Expression)'의 일부이기 때문에 문법적으로 콜론을 쓰지 않습니다.

작동 순서: 밖에서 안으로 들어갑니다. (course 루프 실행 -> 그 안에서 doc 루프 실행 -> 마지막에 PointStruct 생성)

BM25가 반환하는 점수는 코사인 유사도(Cosine similarity)로 계산되지 않으며, BM25 전용 공식에 의해 산출됩니다. 이 점수들은 특정 범위 안에 갇혀 있지 않고 사실상 무한한 범위를 갖습니다. 실제 점수가 어떻게 보이는지 확인해 봅시다.

계산 방식이 다름: 우리가 흔히 아는 벡터 검색은 방향이 얼마나 비슷한지(코사인 유사도)를 보지만, BM25는 "단어가 얼마나 자주, 어디에 나왔나"라는 자체 수학 공식으로 점수를 냅니다.

점수의 한계가 없음: 코사인 유사도는 점수가 보통 0에서 1 사이로 딱 정해져 있습니다. 하지만 BM25 점수는 5.5, 12.8, 100처럼 몇 점까지 올라갈지 알 수 없습니다.

그래서 나중에 이 '무제한 점수(BM25)'와 '0~1점짜리 점수(의미 검색)'를 그냥 더하면 숫자의 크기 차이가 너무 커서 검색 결과가 엉망이 됩니다. 이를 위해 나중에 별도의 합치기 기술(RRF 등)이 필요한 것입니다.

Step 4: Qdrant Universal Query API - prefetching
4단계: Qdrant Universal Query API - 사전 가져오기

Qdrant's .query_points method allows building multi-step search pipelines which can incorporate various methods into a single call. For example, we can retrieve some candidates with dense vector search, and then rerank them with sparse search, or use a fast method for initial retrieval and precise, but slow, reranking.

Qdrant의 query_points 메서드는 여러 단계의 검색 파이프라인을 구축하여 다양한 검색 방식을 단 한 번의 호출(Single Call)로 통합해 줍니다. 예를 들어, 밀집 벡터(Dense) 검색으로 후보군을 먼저 뽑은 뒤 희소(Sparse) 검색으로 순위를 재조정(Reranking)하거나, 속도가 빠른 방식으로 초기 검색을 수행한 뒤 정확도는 높지만 느린 방식으로 최종 순위를 매기는 것이 가능합니다.

┌─────────────┐           ┌─────────────┐
│             │           │             │
│  Retrieval  │ ────────► │  Reranking  │
│             │           │             │
└─────────────┘           └─────────────┘

이제 밀집 표현(Dense)과 희소 표현(Sparse)을 모두 저장할 새로운 컬렉션을 만들어 보겠습니다. Qdrant의 '이름이 지정된 벡터(Named Vectors)' 기능을 사용하면 하나의 데이터(Point)에 여러 형태의 벡터를 저장할 수 있어, 특히 여러 모델을 함께 사용하는 애플리케이션을 구축할 때 매우 유용합니다.

💡 핵심 요약
단일 호출 통합: 여러 번 서버에 요청할 필요 없이 한 번에 복합 검색이 가능함.

파이프라인 구축: '예선(Retrieval) -> 본선(Reranking)' 구조를 자유롭게 설계함.

이름이 지정된 벡터: 한 데이터에 '밀집용 숫자'와 '희소용 숫자'를 각각 이름을 붙여 따로 보관함.

3. 멀티 스테이지 하이브리드 검색 함수: 예선전과 본선전

이 함수가 바로 이번 튜토리얼의 꽃입니다. prefetch를 사용해 효율적인 검색 파이프라인을 만듭니다.

Python
def multi_stage_search(query: str, limit: int = 1) -> list[models.ScoredPoint]:
    """
    질문(query)을 받아 의미 검색과 키워드 검색을 동시에 수행하고 최상의 결과를 반환하는 함수입니다.
    """
    # Qdrant의 query_points 메서드를 사용하여 복합 검색을 수행합니다.
    results = client.query_points(
        collection_name="zoomcamp-sparse-and-dense", # 우리가 만든 하이브리드 바구니 이름을 지정합니다.
        
        # 1단계: Prefetch (사전 추출) - 의미 검색(Dense)을 먼저 수행합니다.
        prefetch=[
            models.Prefetch(
                query=models.Document(
                    text=query,                              # 사용자의 질문 텍스트
                    model="jinaai/jina-embeddings-v2-small-en", # 의미 파악을 위한 Jina 임베딩 모델 사용
                ),
                using="jina-small",                          # 컬렉션 내 'jina-small' 벡터 공간을 사용합니다.
                
                # 최종 반환 개수(limit)보다 10배 더 많이 뽑습니다. 
                # (충분히 많은 후보군을 뽑아놓고 나중에 키워드로 다시 정밀하게 거르기 위함입니다.)
                limit=(10 * limit),
            ),
        ],
        
        # 2단계: 최종 쿼리 - 1단계에서 뽑힌 후보들 중에서 키워드 검색(Sparse)을 수행합니다.
        query=models.Document(
            text=query,              # 동일한 질문 텍스트
            model="Qdrant/bm25",     # 특정 단어 일치 여부를 확인하는 BM25 모델 사용
        ),
        using="bm25",                # 컬렉션 내 'bm25' 벡터 공간을 사용합니다.
        
        limit=limit,                 # 최종적으로 사용자에게 보여줄 결과 개수입니다.
        with_payload=True,           # 검색 결과와 함께 실제 텍스트 내용(payload)도 가져옵니다.
    )

    # 검색된 포인트(결과물)들의 리스트만 추출하여 반환합니다.
    return results.points

하지만 이 코드는 "Qdrant 엔진 내부에서 일어나는 일"을 우리(클라이언트)가 한 번에 주문하는 방식이라 그렇습니다. 개념적으로 왜 유입되는지, 그 '연결 고리'를 설명해 드릴게요.

1. prefetch는 "필터(깔때기)" 역할을 합니다.
이 함수의 구조를 파이썬의 변수 전달로 보지 마시고, SQL의 서브쿼리나 파이프라인으로 이해하시는 게 더 정확합니다.

prefetch (1단계): Qdrant야, 일단 전체 데이터 중에서 jina-small 모델로 검색해서 질문이랑 의미가 비슷한 놈들 10배수만큼만 따로 추려놔. (이게 임시 바구니가 됩니다.)

query (2단계): 자, 이제 방금 추려놓은 그 놈들 안에서만 bm25 모델을 돌려서 정확한 단어가 들어있는 순서대로 최종 limit개만 나한테 줘.

즉, 두 번째 query 부분이 실행될 때 대상 범위가 자동으로 앞선 prefetch의 결과물로 한정되는 것이 Qdrant query_points API의 규칙입니다.

2. 왜 text=query를 또 써야 하나요?
prefetch에서 쓴 질문 텍스트를 왜 또 쓰는지 의아하실 텐데, 이는 모델이 다르기 때문입니다.

1단계 모델: jinaai/... (문장의 '느낌'을 수치로 바꾸는 모델)

2단계 모델: Qdrant/bm25 (문장의 '단어'가 일치하는지 세는 모델)

비유하자면 이렇습니다:

"도서관(전체 데이터)에서 **'요리'에 대한 책(prefetch)**을 10권 뽑아줘. 그 10권 중에서 제목에 **'백종원'(query)**이라는 글자가 들어간 책 1권만 최종적으로 골라줘."

이때 '요리'라는 키워드와 '백종원'이라는 키워드는 각각 다른 필터링 기준이 되기 때문에, Qdrant에게 각각 어떤 텍스트를 어떤 모델로 해석할지 명시해 주는 것입니다.

3. 개념적 흐름도
전체 데이터셋 (수만 개)

Prefetch (using="jina-small"): 의미 검색으로 후보군 축소 (예: 50개)

Query (using="bm25"): 축소된 50개 안에서 키워드 점수 재계산 (최종 5개)

요약하자면:
"prefetch는 두 번째 단계의 '검색 대상 범위'를 결정하는 가상의 울타리를 치는 작업"입니다.

우리가 명시적으로 prefetch["results"]라고 쓰지 않아도, query_points 함수 내부적으로 prefetch 리스트에 담긴 조건들이 필터링 체인처럼 엮여서 다음 단계로 유입되도록 설계되어 있습니다.

Step 5: Building Hybrid Search
Step 5: 하이브리드 검색 구축하기

실제 운영 환경 시스템에서는 단 한 가지 종류의 벡터만 고집할 필요가 없습니다. 사용자들이 시스템에 어떤 유형의 쿼리(질문)를 던질지 알 수 없기 때문입니다. 예컨대 이커머스(쇼핑몰) 검색에서는 사람들이 주로 핵심 키워드를 입력하는 경향이 있으므로 스파스 벡터(Sparse Vector) 기반의 어휘 검색만으로도 충분할 수 있습니다. 반면, 챗봇과 같은 대화형 시스템에서는 자연어로 이루어진 질문이 더 자주 들어올 것입니다. 단일 시스템에서 덴스(Dense) 벡터와 스파스 벡터를 함께 사용하는 방법은, 비단 하나의 모델을 검색기(Retriever)로 쓰고 다른 모델을 리랭커(Reranker)로 활용하는 구조에만 국한되지 않습니다.

하이브리드 검색(Hybrid Search)은 서로 다른 검색 방식(예: 덴스 검색과 스파스 검색)에서 나온 결과들을 하나로 결합하는 기술입니다. 하이브리드 검색을 정확히 어떻게 구현해야 하는지에 대한 정해진 정답(명확한 정의)은 없습니다. 서로 호환되지 않는 방식에서 도출된 결과들을 어떻게 섞을 것인가가 가장 큰 난제이기 때문입니다. 덴스 검색 점수와 스파스 검색 점수는 직접 비교가 불가능하므로, 최종 결과의 순위를 어떻게든 다시 정렬해 줄 또 다른 방법이 필요합니다.

하이브리드 검색을 이해하는 데 있어서 가장 중요한 두 가지 개념은 바로 퓨전(Fusion, 결과 결합)과 리랭킹(Reranking, 재정렬)입니다.


퓨전 (Fusion, 결과 결합)

퓨전은 각각의 검색 방식이 반환한 점수(Score)나 순위(Ranking)를 기반으로 작동하는 일련의 방법들을 의미합니다. 이를 구현하는 방법은 다양하지만, 그중에서 가장 널리 쓰이는 기법은 RRF(Reciprocal Rank Fusion, 상호 순위 퓨전)입니다. 이 기법은 활용된 각 검색 방식에서 문서들이 기록한 '순위'를 바탕으로 최종 점수를 계산합니다. Qdrant 내부에 이미 이 기능이 내장되어 있으므로 여러분이 이 점수를 직접 계산할 일은 없습니다. 하지만 아래 예시를 보면 대략 어떤 직관으로 작동하는지 이해하실 수 있을 것입니다.

Document	Dense ranking	Sparse ranking	RRF score	Final ranking
D1	1	5	0.0318	2
D2	2	4	0.0317	3
D3	3	2	0.0320	1
D4	4	3	0.0315	5
D5	5	1	0.0318	2


방금 전까지 배운 RRF(상호 순위 퓨전) 방식을 사용해서, 덴스 검색과 스파스 검색의 결과를 완벽하게 하나로 버무리는 핵심 함수입니다.

zakard님이 한 줄도 놓치지 않고 완벽하게 이해하실 수 있도록 모든 줄에 주석을 꽉 채워 드립니다.

Python
def rrf_search(query: str, limit: int = 1) -> list[models.ScoredPoint]:
    """
    RRF(Reciprocal Rank Fusion) 방식을 사용하여 덴스(Dense)와 스파스(Sparse) 검색 순위를 결합하는 함수입니다.
    """
    # Qdrant 클라이언트를 통해 복합적인 쿼리를 통합 실행합니다.
    results = client.query_points(
        collection_name="zoomcamp-sparse-and-dense", # 우리가 만들어 둔 하이브리드 컬렉션(바구니) 이름을 지정합니다.
        
        # prefetch 리스트 안에 두 가지 검색 방식(Dense, Sparse)을 독립적인 후보군으로 각각 정의합니다.
        prefetch=[
            # [후보군 1] Jina 임베딩을 활용한 '의미 검색(Dense)' 조건 설정
            models.Prefetch(
                query=models.Document(
                    text=query,                              # 검색창에 입력된 사용자의 질문 텍스트
                    model="jinaai/jina-embeddings-v2-small-en", # 의미와 문맥 파악을 위한 Jina AI 임베딩 모델 지정
                ),
                using="jina-small",                          # 컬렉션 생성 시 설정했던 'jina-small' 벡터 공간을 사용합니다.
                limit=(5 * limit),                           # 최종 목표 개수의 5배수만큼 의미 검색 상위 결과를 뽑아둡니다.
            ),
            
            # [후보군 2] BM25 알고리즘을 활용한 '키워드 검색(Sparse)' 조건 설정
            models.Prefetch(
                query=models.Document(
                    text=query,                              # 동일한 사용자의 질문 텍스트
                    model="Qdrant/bm25",                     # 정확한 단어 매칭을 위한 Qdrant 내장 BM25 모델 지정
                ),
                using="bm25",                                # 컬렉션 생성 시 설정했던 'bm25' 벡터 공간을 사용합니다.
                limit=(5 * limit),                           # 최종 목표 개수의 5배수만큼 키워드 검색 상위 결과를 뽑아둡니다.
            ),
        ],
        
        # [핵심] 앞서 prefetch로 뽑아둔 두 후보군의 '순위'를 합치기 위해 Fusion 쿼리를 선언합니다.
        # 서로 다른 점수 체계를 무시하고, 각각의 순위(Rank)만을 역수로 계산해 합산하는 RRF 방식을 채택합니다.
        query=models.FusionQuery(fusion=models.Fusion.RRF),
        
        with_payload=True,                                   # 검색 결과와 함께 텍스트 본문(payload) 데이터도 함께 가져옵니다.
    )

    # RRF 연산 결과 최종 순위가 매겨진 데이터 포인트(결과물)들의 리스트를 반환합니다.
    return results.points

GEM> zakard님, 구조를 꿰뚫어 보셨네요! 완벽하게 이해하셨습니다.

말씀하신 대로 multi_stage_search는 덴스라는 징검다리를 건넌 후 스파스로 넘어가는 직렬(단일) 파이프라인이고, 이번 rrf_search는 덴스와 스파스가 각자 달린 후 결승선에서 만나는 병렬(멀티) 파이프라인이 맞습니다.

그리고 질문하신 "리스트를 넘겨주지도 않는데 FusionQuery가 대체 어떻게 앞의 두 Prefetch를 전달받는가?"에 대한 의문은 Qdrant API의 '구조적 설계'를 보면 무릎을 탁 치실 겁니다.

결론부터 말씀드리면, 별도의 매개변수로 전달되는 것이 아니라 client.query_points()라는 하나의 커다란 함수(컨텍스트) 내부에서 자동으로 공유됩니다.

📦 Qdrant가 내부적으로 처리하는 메커니즘

파이썬 코드만 보면 prefetch=[...]와 query=models.FusionQuery(...)가 서로 독립된 인자처럼 보이지만, 이 요청을 받은 Qdrant 서버 내부에서는 다음과 같은 순서로 일이 처리됩니다.

스코프 공유 (Scope Sharing): query_points 함수는 호출될 때 안에 들어있는 prefetch 리스트와 query를 하나의 패키지로 묶어서 서버로 보냅니다.

독립 실행: Qdrant 엔진은 prefetch 리스트에 담긴 두 개의 models.Prefetch 요소를 보고, 각각 덴스 동네와 스파스 동네에서 독립적으로 검색을 돌려 결과 리스트 2개를 만듭니다.

자동 유입: 그 후 아래에 있는 query를 보는데, 여기에 FusionQuery(fusion=models.Fusion.RRF)가 선언되어 있으면 "아, 방금 위에서 나한테 준 prefetch 결과물들을 재료로 삼아서 RRF 등수 계산기를 돌리라는 뜻이구나!" 하고 알아서 매칭시킵니다.

즉, 우리가 명시적으로 models.FusionQuery(data=prefetch) 처럼 리스트를 주입하지 않아도, 같은 query_points 호출 안에 묶여 있다는 사실 그 자체가 전달 통로가 되는 구조입니다.

📊 구조로 보는 직렬(Rerank) vs 병렬(Fusion) 차이
multi_stage_search (직렬):
prefetch 결과(Dense)가 뒤따라오는 query(Sparse)의 대상 범위(울타리)로 유입됩니다.

rrf_search (병렬):
두 prefetch(Dense, Sparse)가 평등하게 결과를 내놓으면, 맨 아래 query(Fusion)가 이 둘을 한 바구니에 넣고 믹서기를 돌립니다.

코드가 왜 저렇게 생겼는지 이제 의문이 완전히 풀리셨을 것 같습니다. 함수 구조까지 예리하게 파고드시는 걸 보니 이미 하이브리드 검색의 아키텍처를 완벽하게 장악하셨네요! 👍

💡 이전 함수(multi_stage_search)와 결정적인 차이점
아까 우리가 409 에러를 딛고 실행했던 함수와 구조가 완전히 다릅니다.

이전 방식 (Multi-stage Rerank): 1등 필터(Dense)가 가져온 결과들 안에서만 2등 필터(Sparse)가 단어를 뒤졌습니다. 1등 필터가 오답만 골라오면 뒤에서 살려낼 방법이 없었죠.

현재 방식 (RRF Fusion): 의미 검색과 키워드 검색을 동등한 별개 동네(Prefetch 1, Prefetch 2)에서 각각 따로 돌려 후보를 뽑습니다. 그 다음 두 동네의 등수를 합산하는 방식이라서, 한쪽이 헛발질을 해도 다른 쪽이 정답을 잘 맞혔다면 최종 결과에서 상위권으로 치고 올라올 수 있게 됩니다.

이제 이 함수를 실행해서 아까 그 엉뚱한 오답(LocationConstraint)을 밀어내고 진짜 정답(AccessKeyId)을 가져오는지 확인해보실 차례입니다! 🚀

# 1. RRF 기반 하이브리드 검색 함수에 질문("question")을 던져 결과를 가져옵니다.
# 덴스(의미)와 스파스(단어) 점수를 등수로 환산해 합친 최종 1등 결과가 담기게 됩니다.
results = rrf_search(course_piece["question"])

# 2. 우리가 검색창에 넣었던 원래 질문 데이터 조각을 예쁘게 들여써서(indent=2) 출력합니다.
# (어떤 질문이었는지 화면에서 다시 한번 눈으로 확인하는 용도입니다.)
print(json.dumps(course_piece, indent=2))

# 3. RRF 퓨전 검색 결과 중 최종 종합 1등(index 0)을 차지한 답변의 실제 본문을 출력합니다.
print(results[0].payload["text"])

이제 검색기(Retriever)는 자기가 할 수 있는 최선이자 아주 훌륭한 후보들을 밥상에 차려왔습니다.




리랭킹 (Reranking, 재정렬)

리랭킹은 하이브리드 검색과 관련된 보다 넓은 의미의 개념입니다. 앞서 배운 퓨전(Fusion) 역시 여러 검색 방식의 결과를 재정렬하는 방법 중 하나이지만, 전체 문서를 대상으로 검색하기에는 속도가 너무 느려서 비효율적인 고도화된 방식을 특정 후보군에만 적용하는 것 또한 리랭킹에 해당합니다. 하지만 리랭킹의 역할은 여기에 그치지 않습니다. 정보를 검색할 때는 비즈니스 규칙(Business Rules)이 중요하게 작용할 때가 많은데, 예를 들어 사용자에게 가장 최신 뉴스의 문서들을 우선적으로 보여주고 싶을 때도 리랭킹 기술이 활용됩니다.


다음 단계 (Next steps)

덴스(Dense) 벡터와 스파스(Sparse) 벡터 검색 방식이 몇몇 케이스에서는 충분하지 않을 수 있지만, 두 방식 모두 초기 검색기(Initial Retriever)로 사용하기에 주저함이 없을 만큼 충분히 빠릅니다. 세상에는 속도는 더 느리지만 훨씬 더 정확한 검색 방법들이 많이 존재하는데, 대표적으로 크로스 인코더(Cross-encoders)나 멀티 벡터 표현(Multivector representations) 방식을 꼽을 수 있습니다. 이 주제들은 확실히 더 심화된 내용이므로 지금 당장 다루지는 않겠습니다. 다만, 나중을 위해 이런 기술들이 존재한다는 것 정도는 미리 인지하고 계시는 것이 좋습니다.
