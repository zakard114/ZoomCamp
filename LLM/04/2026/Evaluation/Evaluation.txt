평가 (Evaluation)

이전 모듈에서 우리는 검색 엔진과 RAG 파이프라인을 구축했습니다. minsearch를 이용한 키워드 검색, 벡터 검색, 함수 호출을 사용하는 에이전트 등 다양한 접근 방식을 시도했죠. 이제 우리는 어떤 방식이 실제로 더 나은지 판단할 방법이 필요합니다.

몇 가지 쿼리를 직접 입력해 보고 결과가 괜찮아 보이는지 확인해 볼 수도 있습니다. 이는 간단한 정상 작동 확인(sanity check)에는 효과적이지만, 확장성이 떨어집니다. 따라서 접근 방식들을 비교할 체계적인 방법이 필요합니다.

그것이 바로 평가(Evaluation)가 필요한 이유입니다.
평가를 통해 우리는 다음과 같은 작업을 할 수 있습니다:

다양한 검색 방법 비교 (minsearch vs 벡터 검색 vs 하이브리드 검색)

파라미터 튜닝 (부스트 값, 결과 개수, 프롬프트 템플릿)

다양한 LLM 비교 (gpt-5.4-mini vs 기타 모델)

시간 경과에 따른 개선 사항 추적

평가에는 두 가지 유형이 있습니다:

오프라인 평가: 테스트 데이터셋에서 시스템을 실행하고 지표를 계산합니다.

온라인 평가: 프로덕션 환경에서 실제 사용자로부터 피드백을 수집합니다.

오프라인 평가는 변경 사항을 사용자에게 적용하기 전에 수행하는 작업입니다. 동일한 데이터셋에서 검색 설정, 프롬프트 또는 모델을 비교할 수 있게 해줍니다. 온라인 평가는 배포 후에 이루어지며, 실제 트래픽, 피드백, 로그 및 대시보드를 사용하여 품질을 모니터링합니다.

이 모듈에서는 오프라인 평가에 집중합니다. 테스트 데이터셋을 생성하고, 여기에 검색 및 RAG 시스템을 실행하여 성능을 측정할 것입니다.

우리는 다음 세 가지 수준의 평가를 다룰 것입니다:

검색 평가: 검색이 올바른 문서를 반환하는가?

RAG 평가: LLM이 좋은 답변을 생성하는가?

에이전트 평가: 에이전트가 도구를 효율적으로 사용하는가?

검색의 경우, 히트율(Hit Rate)과 MRR(Mean Reciprocal Rank, 평균 상호 순위)이라는 두 가지 지표를 사용합니다. RAG 품질은 'LLM 판정관(LLM-as-a-judge)' 방식을 사용합니다. 에이전트의 경우, 최종 답변과 도구 호출 궤적을 살펴볼 것입니다.

이제 필요한 테스트 데이터 생성부터 시작하겠습니다.

정답 데이터 생성하기 (Generating Ground Truth Data)

검색 시스템을 평가하려면 어떤 문서가 정답인지 우리가 알고 있는 질문 데이터셋이 필요합니다. 이를 정답지(Ground Truth) 또는 골드 스탠다드(Gold Standard) 데이터라고 부릅니다.

정답 데이터셋에 있는 각 질문에 대해, 지식 베이스에서 어떤 문서가 관련 있는지 이미 알고 있습니다. 검색을 실행할 때, 그 결과에 올바른 문서가 포함되어 있는지 확인하는 방식으로 평가합니다.

정답 데이터를 얻는 방법은 여러 가지가 있습니다:

수동 주석(Human annotators): 사람이 직접 문서를 보고 질문을 작성합니다. (품질은 가장 좋지만, 비용이 많이 듬)

실제 사용자 쿼리 수집: 운영 중인 시스템에서 실제 질문을 수집하고 라벨링합니다. (실제 운영 중인 시스템 필요)

LLM으로 합성 데이터 생성: LLM을 사용하여 질문을 만듭니다. (이번 모듈에서 우리가 수행할 방식)

우리는 아직 운영 중인 시스템이 없으므로 LLM을 활용해 질문을 생성할 것입니다. 각 FAQ 문서에 대해 LLM에게 해당 문서가 답변할 수 있는 5개의 질문을 작성하도록 요청합니다. 이렇게 하면 생성된 각 질문에 대해 해당 소스 문서가 정답이라는 것을 확신할 수 있습니다.

구조화된 출력(Structured Output)으로 질문 생성하기

우리는 LLM을 사용해 각 문서에 대한 질문을 생성합니다. 이번 강의에서 처음으로 구조화된 출력을 사용합니다. 구조화된 출력을 사용하면 자유 형식의 텍스트 대신 특정 형식으로 데이터를 반환하도록 LLM에게 요청할 수 있습니다. 예를 들어, 질문이 포함된 문단을 받는 대신 질문 필드가 있는 파이썬 객체를 요청할 수 있습니다.

이는 코드가 출력을 처리할 때 유용합니다. 모델은 매번 동일한 구조를 반환합니다. 텍스트를 수동으로 파싱할 필요 없이 생성된 질문에 직접 접근할 수 있습니다. 문자열 리스트로 결과를 원하므로 Pydantic 모델로 구조를 정의합니다:

Python
# Pydantic을 활용한 구조화된 출력 원리 설명 코드
# BaseModel: LLM에게 "이러한 JSON 구조로만 응답하라"는 데이터 계약서(Schema)를 정의함
from pydantic import BaseModel

# Questions: LLM의 응답을 파이썬 객체로 변환하기 위한 규격 클래스
# 1. 모델 정의: LLM에게 출력할 데이터의 '약속된 양식(Schema)'을 미리 규격화함.
#    LLM은 이 클래스 구조를 보고, 결과물을 텍스트가 아닌 JSON 데이터로 구성함.

class Questions(BaseModel):
    # 2. 타입 강제: 'questions' 필드는 반드시 문자열 리스트(list[str])여야 함을 정의.
    #    만약 LLM이 이 형식을 지키지 않으면 Pydantic이 파싱 에러를 발생시켜 데이터 무결성을 보장함.
# questions: 이 필드는 LLM이 JSON의 'questions' 키에 리스트 형태로 데이터를 담게 유도함
    # Pydantic이 이 구조를 기반으로 LLM의 응답 텍스트를 파싱하여 즉시 파이썬 list[str] 객체로 변환해줌[cite: 1]
    questions: list[str]

# [원리 요약]
# API 호출 시 text_format=Questions를 넘기면:
# 1) Pydantic 모델이 'JSON Schema'로 변환되어 LLM에게 전달됨.
# 2) LLM은 약속된 JSON 양식에 맞춰 답변을 생성함.
# 3) OpenAI 응답 파서(openai_client.responses.parse())가 해당 JSON을 파이썬 객체(Questions 인스턴스)로 자동 변환함.
# 4) 덕분에 result.questions 와 같이 리스트 객체처럼 즉시 접근 가능해짐.


LLM을 위한 지침:

LLM 호출을 위한 메시지 구성

이제 문서 정보를 프롬프트로 준비했으니, LLM이 이 FAQ를 보고 질문을 생성할 수 있도록 시스템 지침(Developer Role)과 사용자 데이터(User Role)를 하나의 메시지 리스트로 묶어야 합니다.

이 과정은 LLM에게 "너는 이제부터 학생들의 질문을 생성하는 교육용 에이전트야"라는 역할을 부여하는 단계입니다.


Python
# 1. 메시지 구성
# messages: 모델에게 시스템 지침과 참조할 문맥 데이터를 체계적으로 전달

# LLM에게 전달할 메시지 리스트를 구성합니다.
# "developer" 역할은 LLM의 행동 양식(질문 생성 규칙)을 정의합니다.
# "user" 역할은 우리가 방금 변환한 FAQ 문서(user_prompt)를 입력값으로 전달합니다.
messages = [
    {"role": "developer", "content": data_gen_instructions},

import re

def extract_questions_from_text(text):

질문 데이터의 부족: 기존 FAQ 데이터에는 보통 질문이 1개만 달려있습니다. 이렇게 되면 검색 평가를 할 때 데이터가 너무 적어 성능을 정확히 측정하기 어렵습니다.

데이터 증강(Data Augmentation): 그래서 우리는 모델을 이용해 "이 정답을 이끌어낼 수 있는 질문들을 최대한 다양하게(5가지 스타일로) 생성해 줘"라고 시키는 것입니다.

결국 우리 목표는 [1개의 문서(정답)] → [5개의 각기 다른 질문]으로 매핑하여, 검색 엔진이 어떤 방식으로 질문해도 해당 문서(ID)를 찾아내는지 테스트할 수 있는 '정답지(Ground Truth)'를 생성하는 것입니다.

그래서 앞으로 진행할 루프(Loop)의 핵심은:

기존 79개 문서(ID 포함) 각각에 대해

LLM이 5개의 질문을 뽑아내게 하고

결과적으로 79개 문서 * 5개 질문 = 약 395개의 정답 데이터셋을 만드는 것입니다.

왜 컨텐츠와 질문의 추출소스가 하나가 아니고 따로임? 

GEM> 아주 좋은 관찰입니다! LLM과 통신하는 과정에서 '모델의 응답 전체(Content)'와 '우리가 필요한 질문 리스트(Questions List)'를 분리해서 처리하는 이유는 데이터의 신뢰성(Integrity)과 형식을 제어하기 위해서입니다.

그 이유를 3가지로 정리해 드립니다.

1. LLM은 수다스러운 '사람'과 같습니다
LLM에게 "질문 5개를 만들어줘"라고 하면, 모델은 단순히 질문 리스트만 툭 던져주지 않습니다. 때로는 이렇게 말합니다.

"네, 알겠습니다. 요청하신 FAQ 내용을 바탕으로 5개의 질문을 생성했습니다: 1. ~~~, 2. ~~~ (중략)"

이때 content에는 이 모든 문장이 포함됩니다. 우리가 필요한 것은 오직 질문 내용(1~5번)뿐이기 때문에, 이 수다스러운 본문 중에서 질문만 쏙 뽑아내기 위해 extract_questions_from_text라는 별도의 필터(추출 함수)를 거치는 것입니다.

2. 정규식(Regex)을 통한 데이터 정제
LLM이 생성한 결과는 텍스트(String)입니다. 우리가 이 질문들을 프로그램에서 사용하려면(예: 리스트로 변환), 컴퓨터가 이해할 수 있는 구조화된 형태(List)로 바꾸어야 합니다.

content: LLM이 말한 원시 텍스트

extract_questions_from_text(content): 원시 텍스트에서 번호(1., 2. 등)를 찾아서 파이썬 리스트([])로 변환하는 작업

이 과정을 분리해두어야만, 혹시 나중에 LLM이 답변 형식을 조금 다르게 말하더라도(예: 번호를 1) 대신 -로 시작함), 추출 함수만 수정하면 전체 시스템을 갈아엎지 않고도 데이터를 깔끔하게 추출할 수 있습니다.

3. 유연한 대응 (Robustness)
만약 content를 그대로 사용한다면, 모델이 서론을 길게 쓸 때마다 전체 프로그램이 망가질 수 있습니다.

이 구조는 다음과 같은 파이프라인으로 작동합니다:

Input: 원본 텍스트 (content)

Filter: 질문만 골라내고 포맷을 맞춤 (extract_questions_from_text)

Output: 우리가 바로 루프에 태울 수 있는 깔끔한 리스트 (questions_list)

즉, content는 원재료(비정형 데이터)이고, questions_list는 조리된 요리(정형 데이터)라고 생각하시면 됩니다. 원재료를 바로 식탁에 올릴 수는 없으니, 우리가 조리 과정을 분리해 둔 것이죠.

3. 왜 논리적으로 이것만이 정답인가?
검색 엔진(Retrieval)을 평가하기 위해서는 '절대적인 정답 기준'이 필요하기 때문입니다. 만약 어떤 질문이 문서 1도 답이 되고, 문서 2도 답이 된다면, 검색 엔진은 어떤 것을 가져와도 맞다고 해야 할지 혼란에 빠집니다.

그래서 우리는 다음의 논리적 결론을 내립니다:

문서(doc): 정답이 담긴 유일한 주소.

질문(q): 그 주소를 찾아가기 위해 사람이 사용하는 다양한 언어적 시도.

이거 숙지후 방금 준 셀 해석

GEM> 제공해주신 자료는 Ground Truth(정답 데이터셋)를 생성하는 핵심 과정입니다. 이 자료의 핵심은 "전체 문서를 수동으로 처리하면 시간이 너무 오래 걸리니, LLM을 활용해 자동 생성하고 이를 병렬 처리(ThreadPoolExecutor)로 최적화하여 79개의 문서에 대한 정답셋을 빠르게 확보한다"는 것입니다.

방금 작성하신 셀들에 대한 해석을 해당 지침의 맥락에서 정리해 드립니다.

1. 과거의 병렬 처리 로직 (ThreadPoolExecutor 셀)
해석: 제공해주신 지침의 "Processing documents in parallel" 단계를 구현한 코드입니다. map_progress를 통해 79개의 문서 각각에 대해 generate_ground_truth를 호출하는데, 이 작업이 한 번에 하나씩 수행되면 매우 느리기 때문에 max_workers=6으로 설정하여 병렬로 처리하던 방식입니다.

현재 상태: 이미 CSV 형태로 정답 데이터가 확보되어 있으므로, 이 로직은 이제 generate_ground_truth를 실행하지 않으며 과거의 수행 방식을 기록으로 남기기 위해 주석 처리되었습니다.

2. 과거 데이터 취합 및 비용 계산 (for 루프 및 calc_price 셀)
해석: 지침의 마지막 부분인 "Collecting results and calculating costs" 단계입니다.

extend: 병렬 처리로 들어온 리스트 덩어리들을 '껍질을 벗겨서' 하나의 평평한(flat) 리스트로 합치는 필수 과정입니다.

calc_price: API를 사용했으므로 발생한 토큰 사용량(usage)을 기반으로 비용을 산정하던 단계입니다.

현재 상태: 지금은 데이터 생성 과정을 건너뛰고 이미 저장된 CSV를 로드하므로, 토큰 사용량 정보(usages)가 존재하지 않아 해당 로직과 비용 계산 함수 호출도 모두 생략되었습니다.

3. 데이터 로드 및 저장 (pandas 셀)
해석: 자료에 명시된 "Save the ground truth" 단계 이후의 작업입니다.

생성된 정답 데이터를 분석의 기준점으로 삼기 위해 파일(ground-truth-data.csv)로 저장해두고, 필요할 때마다 다시 불러와서 평가(Evaluation) 단계에 활용하겠다는 의도입니다.

현재 상태: 이 셀들은 "이미 생성된 정답 데이터를 불러와 평가를 준비하는 현재의 워크플로우"를 완벽하게 수행하고 있습니다.

제공해주신 GitHub 링크의 내용을 모두 숙지했습니다. 해당 문서는 LLM 평가를 위한 Ground Truth(정답 데이터셋)를 효율적으로 생성하고 관리하는 과정에 대해 다음과 같은 핵심 단계를 다루고 있습니다.

핵심 요약: Ground Truth Batch Processing
데이터 준비: 평가할 문서들을 로드합니다.

병렬 데이터 생성: ThreadPoolExecutor를 사용하여 여러 문서를 동시에 처리(API 병렬 호출)함으로써 생성 속도를 극대화합니다.

결과 취합: 각 스레드에서 생성된 결과를 extend()를 사용하여 하나의 평평한(Flat) 리스트로 병합합니다.

비용 및 추적: 각 작업의 토큰 사용량(usage)을 기록하고 이를 기반으로 총 비용을 계산합니다.

영속화: 최종적으로 완성된 정답셋을 CSV 파일로 저장하여, 향후 평가 시 다시 생성할 필요 없이 즉시 불러와 사용할 수 있게 합니다.

Zakard님의 코드에 대한 해석 및 평가

히스토리 관리: 병렬 처리와 비용 계산 루프를 주석으로 남겨두신 것은, 해당 코드가 어떤 과정(ThreadPoolExecutor 병렬 처리, calc_price 비용 산정)을 거쳐 정답 데이터셋을 만들어냈는지에 대한 '기술적 출처'를 명확히 남기는 좋은 방식입니다.

효율성: 매번 API 비용을 들여 데이터를 재생성하는 대신, 저장된 ground-truth-data.csv를 Pandas로 빠르게 불러오는 방식은 지침서에서 권장하는 "저장된 파일을 활용한 반복 평가"에 완벽히 부합합니다.

코드 구조: .extend()의 동작(리스트의 껍질을 벗겨 내용물만 합침)을 이해하고 이를 적절히 주석으로 처리하신 점은, 향후 데이터 구조가 복잡해지더라도 Pandas DataFrame 변환 시 에러를 방지할 수 있는 탄탄한 기초가 됩니다.

3. 관련성 계산 함수화
위의 로직을 함수로 만들어 어떤 질문에 대해서도 관련성 리스트를 쉽게 얻을 수 있도록 합니다.

Python
def compute_relevance_text(q):  # compute_relevance_text(q)로 질문 1건의 relevance 벡터를 계산하는 함수를 정의한다.
    doc_id = q["document"]  # q["document"]로 정답 id를 꺼내 검색 결과와 비교한다.
    results = text_search(query=q["question"])  # text_search(query=...)로 이 질문에 대한 top-5 검색을 수행한다.

    relevance = []  # relevance = []로 이 질문 전용 0/1 리스트를 초기화한다.
    for d in results:  # for d in results로 top-5를 순회한다.
        relevance.append(int(d["id"] == doc_id))  # append(int(...))로 순위별 hit 여부를 기록한다.

    return relevance  # return relevance로 한 질문의 평가 벡터를 호출부에 돌려준다.

from tqdm.auto import tqdm

# 전체 ground_truth에 대해 관련성 리스트를 생성하는 함수
def compute_relevance_total_text(ground_truth):
    relevance_total = []

    for q in tqdm(ground_truth):
        relevance = compute_relevance_text(q)
        relevance_total.append(relevance)

    return relevance_total

def compute_relevance(q, search_function):  # compute_relevance()에 search_function 인자를 넣어 boost 튜닝 시 함수만 바꿀 수 있게 한다.
    doc_id = q["document"]  # q["document"]로 정답 id를 가져온다.
    results = search_function(query=q["question"])  # search_function(query=...)로 text_search 대신 다른 검색 함수도 쓸 수 있게 한다.

    relevance = []  # relevance = []로 0/1 벡터를 초기화한다.
    for d in results:  # for d in results로 top-5를 순회한다.
        relevance.append(int(d["id"] == doc_id))  # append(int(...))로 hit 여부를 기록한다.

    return relevance  # return relevance로 한 질문 평가 결과를 반환한다.




# 전체 ground_truth에 대해 관련성 리스트를 구하는 함수
from tqdm.auto import tqdm

def compute_relevance_total(ground_truth, search_function):  # compute_relevance_total()로 전체 질문 + 임의 검색 함수 조합을 평가한다.
    relevance_total = []  # relevance_total = []로 전체 결과를 담을 리스트를 만든다.

    for q in tqdm(ground_truth):  # for q in tqdm(ground_truth)로 모든 질문을 돈다.
        relevance = compute_relevance(q, search_function)  # compute_relevance(q, search_function)로 검색 함수별 relevance를 구한다.
        relevance_total.append(relevance)  # append()로 질문별 벡터를 모은다.

    return relevance_total  # return relevance_total로 evaluate()에 넘길 데이터를 만든다.

이제 우리가 확보한 relevance_total 리스트를 활용해 Hit Rate(적중률)와 MRR(평균 상호 순위)을 계산할 차례입니다.

1. Hit Rate (적중률)
Hit Rate는 정답 문서가 상위 k개 결과 내에 포함된 질문의 비율을 측정합니다. 우리 시스템은 질문당 정답이 하나이므로, 여기서 Hit Rate는 Recall@k와 동일합니다.


Python
def hit_rate(relevance):  # hit_rate(relevance) 함수로 전체 relevance에서 Hit Rate를 계산한다.
    cnt = 0  # cnt = 0으로 hit 카운터를 초기화한다.
             # 정답이 포함된 질문의 개수를 담을 변수 초기화

    for line in relevance:  # for line in relevance로 모든 질문의 relevance 벡터를 본다.
                            # 각 질문의 관련성 리스트(0, 1)를 순회
        if 1 in line:  # if 1 in line이면 해당 질문은 검색 성공(hit)이다.
                       # 정답 문서가 검색 결과에 포함되어 있다면(1이 존재하면)
            cnt = cnt + 1  # 적중 횟수 증가. cnt를 올려 hit 개수를 센다.

    return cnt / len(relevance)  # return cnt/len(relevance)로 hit 비율을 반환한다.
                                # 전체 질문 개수로 나누어 비율 반환

2. Mean Reciprocal Rank (MRR, 평균 상호 순위)Hit Rate는 정답의 '유무'만 판단하지만, MRR은 '순위'까지 고려합니다. 정답이 상위권에 있을수록 더 높은 점수를 부여합니다.

각 질문에 대해 점수는 첫 번째 정답 문서의 순위를 기준으로 합니다.

1위: 점수 1.0

2위: 점수 0.5

3위: 점수 0.333

못 찾음: 점수 0

이 로직을 코드로 구현합니다. 파이썬은 순위를 0부터 세기 때문에 rank + 1을 사용합니다. 1위는 1/1 점수를 받아야 하며, +1을 하지 않으면 0으로 나누게 되기 때문입니다.

Python
total_score = 0.0  # total_score = 0.0으로 MRR 합계를 초기화한다.

for line in sample:  # for line in sample으로 샘플 질문별 relevance를 순회한다.
    for rank in range(len(line)):  # for rank in range(len(line))으로 0,1,2,... 순위를 본다.
        if line[rank] == 1:  # line[rank] == 1이면 그 순위에 정답 문서가 있다.
            score = 1 / (rank + 1)  # score = 1/(rank+1)로 reciprocal rank 점수를 구한다.
            total_score = total_score + score  # total_score에 더해 질문당 첫 정답 순위 점수만 반영한다.
            break  # break로 한 질문에서 첫 번째 정답 순위만 MRR에 넣는다.

total_score / len(sample)  # total_score/len(sample)로 샘플 MRR을 수동 계산한다.

이제 MRR까지 계산되었습니다. 다음은 지침에 따라 이 로직들을 evaluate라는 재사용 가능한 함수로 통합하고 최종 평가를 수행하는 단계입니다.

Python
def mrr(relevance):  # mrr(relevance)로 Mean Reciprocal Rank를 계산하는 함수를 정의한다.
                     # 각 질문별 점수를 합산할 변수 초기화
    total_score = 0.0  # total_score = 0.0으로 역순위 점수 합을 초기화한다.

    for line in relevance:  # for line in relevance로 각 질문의 relevance 벡터를 본다.
                            # 각 질문의 관련성 리스트 순회
        for rank in range(len(line)):  # for rank로 top-5 순위를 순회한다. 검색 결과의 순위(rank)를 확인
            if line[rank] == 1:  # line[rank] == 1이면 그 순위가 정답 문서 위치이다. 정답 문서가 해당 순위에서 발견되면
                score = 1 / (rank + 1)  # 순위에 따른 역수 점수 합산 score = 1/(rank+1)로 reciprocal rank를 계산한다.
                total_score = total_score + score  # total_score에 더한다.
                break  # break로 질문당 첫 정답만 반영한다. 정답을 찾았으므로 다음 질문으로 이동. 

    return total_score / len(relevance)  # 전체 평균 점수 반환. return total_score/len(relevance)로 평균 MRR을 반환한다.

3. 평가 함수 통합 (Putting it together)

이제 이 지표들을 한 번에 계산하는 evaluate 함수를 만들어, 어떤 검색 함수든 쉽게 평가할 수 있게 합니다.

Python
# 통합 평가 함수: 검색 함수를 인자로 받아 Hit Rate와 MRR을 한 번에 계산
def evaluate(ground_truth, search_function):
    # 전체 데이터에 대한 관련성 리스트를 먼저 계산
    relevance_total = compute_relevance_total(ground_truth, search_function)
    
    # 지표를 딕셔너리 형태로 반환
    return {
        "hit_rate": hit_rate(relevance_total),
        "mrr": mrr(relevance_total),
    }

# 전체 데이터셋(ground_truth)과 검색 함수(text_search)를 사용하여 최종 평가 수행

평가 지표 해석 시 주의사항 (Interpreting the metrics):

1. 정답의 다수성: 우리의 ground truth는 질문당 하나의 정답만 가정하지만, 실제로는 다른 문서도 관련이 있을 수 있습니다. Hit Rate가 50%라고 해서 결과의 절반이 쓸모없다는 뜻은 아닙니다.

정답의 다수성이 고려되지 않는 이유는 우리가 평가에 사용하는 ground_truth 데이터셋이 질문 하나당 단 하나의 문서만을 정답으로 연결하는 '단일 정답 구조'를 채택했기 때문입니다. 예를 들어, "강의를 늦게 시작해도 되나요?"라는 질문에 대해 FAQ 상에서는 특정 ID의 문서가 공식 정답으로 지정되어 있지만, 실제로는 강의 일정을 안내하는 다른 문서나 운영 정책 문서에도 관련 내용이 포함되어 있을 수 있습니다. 따라서 시스템이 비록 공식 정답 ID를 상위 5개 안에 포함하지 못해 Hit Rate 평가에서는 '실패(0)'로 기록될지라도, 검색 결과로 제공된 다른 문서들이 사용자의 의문을 충분히 해소할 수 있는 유용한 정보를 담고 있을 가능성이 매우 높으므로, 단순히 50%의 Hit Rate가 시스템 결과의 절반이 무용지물임을 의미하는 것은 아닙니다.

2. 합성 데이터의 한계: 생성된 질문이 FAQ 원문과 너무 비슷하면 수치가 비정상적으로 높게(예: 95% 이상) 나올 수 있습니다. 이 경우 현실적인 질문인지 확인이 필요합니다.

합성 데이터의 한계가 발생하는 이유는 대규모 언어 모델(LLM)이 FAQ의 원문 내용을 거의 그대로 가져와 질문을 생성하기 때문입니다. 예를 들어, FAQ에 "강의 시작일은 2026년 3월 4일입니다"라는 문장이 있을 때, 모델이 "2026년 3월 4일은 무슨 날인가요?"와 같은 질문을 생성하면, 검색 시스템은 해당 FAQ 문장의 키워드를 그대로 찾아내기만 해도 정답을 맞히게 되어 Hit Rate나 MRR이 95%를 넘기는 비정상적인 수치를 보일 수 있습니다. 이는 시스템의 검색 능력이 우수해서가 아니라, 질문이 원문과 지나치게 유사하여 발생한 '데이터 누수'와 비슷한 현상이므로, 평가 지표가 높게 나오더라도 실제 사용자가 던질 법한 다양하고 복잡한 질문에 대해서도 같은 성능을 보일지 의심해봐야 합니다.

3. 시스템 전체의 관점: 높은 MRR은 정답 문서가 상단에 있다는 뜻이므로 LLM이 맥락을 파악하기에 최적입니다. Hit Rate는 높은데 MRR이 낮다면, 정답이 있긴 하지만 다른 관련 없는 문서들에 묻혀 있다는 신호입니다.

가중치 과다 설정의 역효과: 이전에는 question 필드에 너무 높은 가중치(3.0)를 부여한 탓에, 질문과 키워드가 정확히 일치하지 않는 경우 검색 결과가 왜곡되었을 가능성이 있습니다. 가중치를 2.0으로 낮춤으로써 시스템이 답변(answer)이나 섹션(section) 정보에 조금 더 균형 있게 반응하게 되었을 것입니다.

검색 결과의 다양성 확보: 가중치가 너무 높으면 질문 텍스트와 완벽히 일치하는 문서만 상위권에 배치되려는 경향이 있습니다. 가중치를 완화하면서 질문의 의미는 유사하지만 키워드가 조금 다른 문서들이 검색 결과 상단으로 올라올 수 있게 되었고, 이것이 정답을 찾을 확률(Hit Rate)과 순위(MRR)를 높인 것으로 보입니다.


다음 단계 제안
가중치를 낮췄을 때 성능이 좋아졌다는 것은, 우리가 처음에 설정했던 "질문 가중치가 절대적으로 중요하다"는 직관이 틀렸을 가능성을 보여줍니다.

이제 우리는 개별 파라미터를 하나씩 조정하는 단계를 넘어, question, answer, section 모든 가중치를 한꺼번에 조합하여 최적의 값을 찾아내는 '그리드 탐색(Grid Search)'을 시작할 준비가 되었습니다.

이 단계로 넘어가서, 어떤 조합이 최선의 성능을 내는지 전체적으로 탐색해 볼까요? 허락해 주시면 다음 지침을 준비하겠습니다.

검색 파라미터 튜닝 (Search Parameter Tuning)

이전 단계에서 Hit Rate와 MRR, 그리고 evaluate 함수를 정의했으니, 이제 이를 활용해 검색 파라미터를 최적화할 수 있습니다.

우리는 어떤 설정이 더 나을지 단순히 추측하는 대신, 실제 ground truth 데이터셋을 통해 수치로 검증할 것입니다. 지금까지 우리는 question 필드의 가중치(boost)를 3.0으로 설정해 왔습니다. 사용자의 질문이 FAQ의 질문과 일치하는 것이 답변 텍스트와 일치하는 것보다 훨씬 중요할 것이라고 판단했기 때문입니다. 논리적으로는 타당해 보이지만, 이는 어디까지나 추측일 뿐입니다. 이제 우리는 막연한 믿음 대신 데이터라는 객관적인 근거로 이를 확인해 볼 것입니다.

이것이 바로 오프라인 평가(offline evaluation)가 가진 가장 큰 강점입니다. 동일한 데이터셋이라는 기준점을 고정한 채로 파라미터를 하나씩 조정해 보며, 그에 따라 성능 지표가 어떻게 변화하는지 공정하게 비교해 볼 수 있기 때문입니다.




좋습니다. 계속해서 '다양한 가중치(Boost) 시도' 단계입니다. 지침에 따라 가중치를 조절할 수 있는 search_boost 함수를 먼저 정의하겠습니다.



Trying different boosts
다양한 가중치(Boost) 시도

먼저 question 필드의 가중치를 유연하게 변경할 수 있도록 새로운 검색 함수를 만듭니다.

Python
# question 필드에 대한 가중치(boost)를 조절할 수 있는 검색 함수
def search_boost(query, question_boost):  # search_boost()로 question boost만 바꿔가며 실험한다.
    # question에는 파라미터로 받은 가중치를, section에는 0.5를 고정으로 부여
    boost_dict = {"question": question_boost, "section": 0.5}  # boost_dict에 question_boost 인자를 넣는다.

    return index.search(  # index.search()로 각 boost 값마다 top-5를 받는다.
        query,  # query에 질문 문자열을 넣는다.
        num_results=5,  # num_results=5로 고정한다.
        boost_dict=boost_dict,  # boost_dict로 가중치를 적용한다.
    )

이제 여러 가지 가중치 값을 테스트하며 어떤 설정이 최적인지 확인합니다.

Python
# 테스트할 가중치 목록
for boost in [0.5, 1.0, 3.0, 5.0, 10.0]:  # for boost in [...]로 question 가중치 후보를 순회한다.
    result = evaluate(  # evaluate()로 각 boost마다 Hit Rate/MRR을 계산한다.
        ground_truth,  # ground_truth로 동일 평가 집합을 쓴다.
        lambda query, boost=boost: search_boost(query, boost),  # lambda로 boost 값을 search_boost에 고정해 넘긴다.
    )
    print(f"boost={boost}: {result}")  # print()로 boost별 결과를 바로 비교한다.

나> 그러니까 애초에 우선순위 문제였다며 메커니즘을 꼬리를 물고 추적하면 evaluate -> ground_truth -> lambda query, boost -> search_boost 순으로 파일이 토스된다고 말했으면 됬을텐데. 그렇게 말했는데 내가 못알아 먹은건가?

GEM> 결론부터 말씀드리면, zakard 님이 못 알아먹으신 게 아니라, 제가 그 '파일 토스(데이터 흐름)'의 핵심을 말로만 설명하려다 보니 추상적으로 들렸던 것 같습니다.

시스템의 복잡함에 가려져서 놓치기 쉬웠던 '데이터가 튀어 오르는 경로'를 이번엔 정말 단순하게, '파일(데이터) 전달의 순서'만 딱 짚어드릴게요.

데이터 토스(Toss) 경로: 0단계에서 4단계까지
[0단계: 저장소] ground_truth (데이터의 원천)

질문과 정답이 담긴 리스트입니다. 이게 시작점입니다.

[1단계: 시작] evaluate(ground_truth, ...)

evaluate는 "자, 이 ground_truth 리스트를 하나씩 꺼내서 채점하자!"라고 선언하며 흐름을 시작합니다.

[2단계: 토스] compute_relevance(q, search_function)

evaluate는 ground_truth에서 질문 하나(q)를 꺼내서 compute_relevance에게 툭 던져줍니다.

여기서 중요한 건, compute_relevance가 다시 이 질문을 search_function(lambda)에게 "너 이거 처리해!" 하며 다시 토스한다는 점입니다.

[3단계: 변환] lambda query, boost=boost: ...

lambda는 compute_relevance가 던진 질문을 받아서(할당), search_boost가 요구하는 규격(query, boost)으로 포장합니다.

[4단계: 엔진] search_boost(query, boost)

포장된 데이터를 받아서 진짜 검색 엔진(index.search)을 돌립니다.

왜 헷갈렸을까요?
제가 답변할 때 이 경로를 '함수의 호출 관계'와 '데이터의 흐름'을 섞어서 설명했기 때문입니다.

함수 호출(의존성): evaluate → compute_relevance → lambda → search_boost

데이터 흐름(값의 이동): ground_truth → (evaluate가 꺼냄) → compute_relevance → (lambda로 뺌) → search_boost

"꼬리에 꼬리를 무는 추적"을 하려면, 함수가 호출되는 순서가 아니라 데이터(question이라는 값)가 어느 함수에서 어느 함수로 이동(인자로 전달)되는지만 따라가면 됩니다.

제가 처음에 "evaluate가 인자로 받아서 찔러준다"라고 했을 때, 그 '찔러주는 인자'가 결국 데이터의 흐름이라는 점을 훨씬 더 명확하게 끊어서 보여드렸어야 했습니다.

핵심 요약:
데이터(q["question"])는 evaluate에서 시작해서, compute_relevance를 거쳐, lambda의 입구에 도착하고, 최종적으로 search_boost의 안방(함수 내부)까지 도달합니다.

이제 이 '데이터의 토스 과정'이 머릿속에서 일직선으로 그려지시나요? 만약 이게 명확해졌다면, 이제 zakard 님은 이 시스템을 완전히 장악하신 겁니다. 그다음부터는 이 토스 경로에 방해되는 변수(boost)를 조절해서 결과를 확인하는 실험만 남은 거니까요.

zakard 님이 제공해주신 본문과 코드를 보니, 왜 그토록 치밀하게 인자를 람다로 넘겨주고, 또 람다 안에서 다시 파라미터를 고정(question_boost=question_boost 등)했는지 그 이유가 드러납니다.

1. 람다의 '인자 고정(Capture)'이 없었다면?
만약 람다를 쓰지 않고 evaluate(ground_truth, search_boosts)라고만 호출했다면, evaluate 함수는 search_boosts라는 함수만 달랑 받게 됩니다. 하지만 search_boosts는 인자가 4개(query, question_boost, answer_boost, section_boost)나 필요하죠.

evaluate가 던져주는 건 오직 query 하나뿐인데, 나머지 3개의 boost 값은 어디서 가져올까요? 바로 람다가 '지금 반복문에서 돌고 있는 그 순간의 값'을 낚아채서 가지고 있다가, 나중에 호출될 때 넘겨주는 '중계기' 역할을 했기 때문에 이 그리드 탐색이 가능한 것입니다.

2. 엔지니어링적 통찰 (이 시스템의 가치)
제공해주신 본문의 핵심 문장이 바로 이것입니다.

"The answer text matters more for retrieval than the question text. The intuition was wrong, and we'd never have known without measuring it. This is exactly why we evaluate instead of guess."

우리는 처음에 "질문이 중요할 거야"라고 직관적으로 생각했지만, 데이터를 돌려보니(그리드 탐색) 정답은 정반대(answer에 가중치를 두는 게 성능이 높음)였습니다.

zakard 님이 지금 분석하고 계신 이 코드는:

데이터를 기반으로(Offline Evaluation)

자동화된 시스템을 통해(Grid Search)

직관의 오류를 수정하는(Tuning Workflow)
현대 데이터 엔지니어링의 정수를 보여주고 있습니다.

이제 람다의 메커니즘과 그리드 탐색의 필요성을 완벽히 이해하셨으니, 다음 단계로 넘어가 볼까요? 본문 마지막에 적힌 것처럼 "이제 검색(Retrieval) 평가를 끝냈으니, 전체 RAG 파이프라인의 답변 품질(Answer Quality) 평가"로 넘어갈 차례입니다.

이 자동 배식 시스템의 설계 원리를 이제 마스터하셨는데, 실제 이 코드를 주피터 노트북에서 돌려서 '내가 처음에 생각했던 boost 값'보다 '데이터가 말해주는 최적값'이 얼마나 다른지 확인해 보시겠습니까? 거기서 오는 희열이 이 공부의 진짜 목적입니다.





질문(question) 부스트를 높이는 것은 메트릭(성능 지표)을 개선하는 것이 아니라, 오히려 악화시킵니다. 여기서 가장 좋은 값은 부스트가 전혀 없는 1.0입니다. 이는 이미 우리가 직관적으로 예측했던 것과 정반대의 결과입니다.

def search_boosts(query, question_boost, answer_boost, section_boost):  # search_boosts()로 세 필드 boost를 동시에 튜닝한다.
    boost_dict = {  # boost_dict에 question/section/answer 가중치를 모두 넣는다.
        "question": question_boost,  # question_boost로 질문 필드 비중을 조절한다.
        "section": section_boost,  # section_boost로 섹션 필드 비중을 조절한다.
        "answer": answer_boost,  # answer_boost로 답변 필드 비중을 조절한다.
    }

    return index.search(  # index.search()로 조합별 top-5를 반환한다.
        query,  # query로 검색한다.
        num_results=5,  # num_results=5로 유지한다.
        boost_dict=boost_dict,  # boost_dict로 세 가중치를 반영한다.
    )

메트릭의 중요성: Hit Rate는 문서의 '존재 여부', MRR은 '상단 노출 여부'를 판단합니다. 상단에 있을수록 RAG 프롬프트에 활용될 확률이 높습니다.

튜닝 워크플로우: 파라미터는 자의적일 수 있지만, 평가(Evaluation)를 통해 증거 기반의 비교가 가능합니다. 조합이 적을 땐 그리드 서치(Grid Search)가 효율적이지만, 평가 시간이 길어지면 hyperopt 같은 베이지안 최적화 도구를 사용해야 합니다.

Top-K 트레이드오프: 결과 개수(Top-K)를 늘리면 Hit Rate는 오르지만, LLM에게 전달할 문맥(Context)이 너무 많아져 비용이 증가하고 모델이 관련 정보를 찾기 어려워집니다. FAQ 스타일에는 5개가 적당합니다.

다음 단계: 이제 검색 품질 평가에서 답변 품질 평가(전체 RAG 파이프라인)로 넘어갑니다.

RAG and Agent Evaluation

[RAG 및 에이전트 평가]
영상: 이 강의 시청하기
https://www.youtube.com/watch?v=VKHBP0QSCFo&list=PL3MmuxUbc_hLZFNgSad56pDBKK8KO0XIv


지금까지 우리는 검색(retrieval)을 평가했습니다. 검색 결과가 질문에 답이 될 만한 문서를 반환하는지를 확인했죠.
하지만 그것은 첫 단계일 뿐입니다. 완벽한 애플리케이션이라면 최종 답변까지 도출해야 합니다. RAG의 경우 이는 생성된 답변을 확인하는 것을 의미합니다. 에이전트의 경우, 답변을 생성하기 전에 모델이 수행한 도구 호출(tool calls)까지 살펴보는 것을 의미합니다.

RAG 평가는 전체 흐름을 함께 검사합니다. 여기에는 다음이 포함됩니다:

검색(search)

프롬프트(prompt)

LLM

최종 답변이 좋지 않다면, 문제는 이 단계들 중 어디에서든 발생할 수 있습니다. 검색이 잘못된 문서를 가져왔거나, 프롬프트에서 중요한 문맥을 누락했거나, 혹은 LLM이 문맥을 무시했을 수 있습니다.

이번 파트에서 우리는 다음을 평가할 것입니다:

LLM 심판(judge)을 활용한 RAG 답변 평가

에이전트 답변 및 도구 호출 궤적(trajectory) 평가

여기서 에이전트 평가 프레임워크를 심도 있게 다루지는 않겠습니다. 대신 모듈 01에서 사용한 에이전트를 활용하여 최종 답변과 도구 호출 내용을 저장할 것입니다. 그런 다음 답변이 적절한지, 그리고 도구 호출 궤적이 합리적인지 검토할 것입니다.


LLM을 심판으로 활용하기 (LLM-as-a-judge)
RAG와 에이전트 평가를 위해, 우리는 생성된 답변을 원본 답변과 비교합니다. 생성된 답변은 원본과 완전히 같은 단어를 사용하지는 않을 것입니다. 생성형 모델이므로 의미가 같더라도 문구는 달라질 수밖에 없습니다.

이것이 우리가 비교를 위해 다른 LLM을 사용하는 이유입니다. 우리는 심판 역할을 할 LLM에게 질문, 원본 답변, 그리고 생성된 답변을 보여줍니다. 그런 다음 이 답변들이 의미적으로 동일한지 판단해달라고 요청합니다.

이러한 접근 방식을 'LLM-as-a-judge(심판으로서의 LLM)'라고 합니다. 평가를 수행하는 LLM이 곧 심판입니다. 이 모델은 각 답변을 '좋음' 또는 '나쁨'으로 분류하고 그 이유를 설명합니다. 심판에게 단순히 판결만 내리라고 하는 것보다, 왜 그런 결정을 내렸는지 설명하도록 요청하는 것이 일반적으로 더 나은 분류 결과를 만들어냅니다.

다음으로, RAG 사례부터 시작하여 Ground Truth(평가 데이터셋) 질문들에 대한 답변을 생성하겠습니다.

원문 충실 번역본입니다. 다음 단계(데이터셋을 활용한 평가 수행 등)로 넘어가시겠습니까? 허락해주시면 이어서 진행하겠습니다.

Generating RAG Answers
RAG 답변 생성

영상: 이 강의 시청하기
https://www.youtube.com/watch?v=utkcclfpj0g&list=PL3MmuxUbc_hLZFNgSad56pDBKK8KO0XIv

이 모듈의 첫 번째 파트에서는 검색 품질을 평가했습니다. 검색 결과에 올바른 문서가 나타나는지를 확인했죠.

이제는 전체 RAG 파이프라인을 평가합니다. 생성된 각 질문에 대해 RAG를 실행하고 LLM이 내놓은 답변을 저장합니다. 나중에 이 답변을 원래의 FAQ 답변과 비교할 것입니다.

이것은 A->Q->A' 구성입니다:

A = FAQ의 원본 답변

Q = 이 답변으로부터 생성된 질문

A' = 우리의 RAG 시스템이 생성한 답변

A'가 A와 가깝다면, RAG 시스템이 제 역할을 잘하고 있는 것입니다.

이는 여전히 오프라인 평가입니다. 우리의 질문들이 FAQ 레코드에서 나왔기 때문에 A와 A'를 비교할 수 있는 것입니다. 각 질문에 대해 그것이 어떤 원본 답변에서 유래했는지 알고 있기 때문입니다.

이게 필요한 결정적인 이유: RAG 과정에서 질문이 들어오면, 시스템은 "관련된 문서 ID"를 먼저 찾아냅니다. 이때 index가 없으면 매번 전체 리스트(documents)를 처음부터 끝까지 다 뒤져야 하므로 시스템이 굉장히 느려집니다.

# [강의 본 코드] generate_rag_answer(rec)로 ground_truth 1행마다 RAG 답변·원문을 묶는 배치 함수를 정의한다
def generate_rag_answer(rec):
    question = rec["question"]  # rec["question"]으로 학생 질문 문자열을 꺼낸다.
    doc_id = rec["document"]  # rec["document"]로 정답 FAQ id를 꺼낸다.
    original_doc = doc_idx[doc_id]  # doc_idx[doc_id]로 원문 FAQ를 조회한다.

    answer_llm = assistant.rag(question)  # assistant.rag(question)으로 검색+LLM 생성 답변을 받는다.
    answer_orig = original_doc["answer"]  # original_doc["answer"]로 평가·비교용 FAQ 정답 원문을 넣는다.

    result = {  # result dict로 04-llm-judge.ipynb가 기대하는 4개 필드를 만든다.
        "question": question,
        "answer_llm": answer_llm,
        "answer_orig": answer_orig,
        "document": doc_id,
    }
    return result  # return

우리의 RAG 파이프라인이 생성한 답변

LLM 평가자(LLM judge)는 이 세 가지 요소를 비교하는 또 다른 LLM 호출을 의미합니다. 우리는 LLM에게 RAG 답변이 원본 답변과 동일한 정보를 담고 있는지 질문합니다.

또한, LLM은 답변이 왜 잘못되었는지 설명할 수도 있습니다. 예를 들면 다음과 같은 경우입니다:

검색된 문서가 잘못되었을 수 있습니다.

답변이 핵심 내용을 놓쳤을 수 있습니다.

모델이 답변을 모르겠다고 응답했을 수 있습니다.

이 접근 방식은 정확한 텍스트 일치(exact text matching)만으로는 기준이 너무 엄격할 때 유용합니다. RAG 답변은 FAQ 답변을 토씨 하나 틀리지 않고 똑같이 복사할 필요는 없습니다. 대신, 질문에 대해 동일한 핵심 정보를 전달하며 답변해야 합니다.

이 방법은 전체 RAG 흐름을 한 번에 평가합니다:

검색(search): 답변을 포함하고 있는 문맥을 제대로 가져왔는가?

프롬프트(prompt): 모델이 답변하기에 충분한 문맥을 제공했는가?

LLM: 모델이 그 문맥으로부터 유용한 답변을 생성했는가?

만약 평가자가 답변을 '나쁨(bad)'으로 표시하더라도, 우리는 여전히 해당 사례를 직접 살펴볼 필요가 있습니다. 평가자는 어디를 조사해야 할지 알려주는 역할을 할 뿐, 실패한 사례를 직접 읽어보는 과정을 대신해주지는 않습니다.

2. 평가 실행 함수 구현

Python
# 평가 실행 함수(evaluate_aqa)]
# 질문과 답변 데이터를 입력받아 LLM을 통해 정답지와의 유사성을 평가합니다.
# AQA(Answer-Question-Answer) 방식의 평가를 수행하는 함수를 정의합니다.
def evaluate_aqa(question, answer_orig, answer_llm, model="gpt-5.4-mini"):
    # 전달받은 데이터(질문, 원본답변, AI답변)를 평가용 프롬프트 템플릿에 채워 넣습니다.
    prompt = aqa_judge_prompt.format(
    question=question,     # 사용자의 원본 질문을 프롬프트에 할당
    answer_orig=answer_orig, # 비교 대상인 정답 데이터를 프롬프트에 할당
    answer_llm=answer_llm    # 평가 대상인 LLM의 답변을 프롬프트에 할당
) # 템플릿의 각 항목에 데이터를 채워 최종 평가 문장(프롬프트) 완성

    # 정의된 구조(AnswerEvaluation)대로 결과를 반환받기 위해 LLM을 호출합니다.
    # 만약 호출에 실패하면 지정된 횟수만큼 자동으로 재시도합니다.
    result, usage = llm_structured_retry(
        openai_client,           # API 연결 클라이언트
        aqa_judge_instructions,  # LLM 평가자의 평가 지침(System Prompt)
        prompt,                  # 완성된 평가 프롬프트
        AnswerEvaluation,        # 출력 데이터의 스키마(형식)
        model=model,             # 사용할 모델명
    )

    # 평가 결과(객체)와 사용량(usage) 정보를 반환합니다.
    return result, usage


이 시스템을 통해 RAG 파이프라인에서 생성된 답변들이 얼마나 FAQ 정답에 부합하는지 정량적으로 수치화할 수 있습니다.

이 함수가 정의됨으로써 우리는 이제 395개나 되는 방대한 양의 RAG 답변을 일일이 읽어볼 필요 없이, 컴퓨터에게 이 함수를 반복해서 실행하도록 시킬 준비가 된 것입니다. 이렇게 자동화된 평가 시스템을 구축해두면 나중에 RAG 파이프라인의 설정을 바꾸거나 다른 모델로 교체했을 때, 성능이 얼마나 좋아졌는지 객관적인 수치로 바로 비교할 수 있습니다.

이제 이 함수가 실제로 어떻게 움직이는지 테스트해 볼 준비가 되셨나요? 다음 셀을 알려주시면 이어서 설명하겠습니다.

다음 셀은 앞서 정의했던 evaluate_aqa라는 '평가 엔진'을 실제 레코드 데이터 하나에 적용하기 좋게 감싸주는 '래퍼(Wrapper) 함수'를 만드는 단계입니다. 이 함수는 단순히 평가만 수행하는 것이 아니라, 평가 결과(점수, 근거)와 원본 데이터(질문, 문서)를 하나의 깔끔한 딕셔너리 형태로 묶어주는 데이터 관리자 역할을 수행합니다.


Python
# 레코드 하나를 입력받아 평가를 수행하고 결과를 반환하는 함수를 정의합니다.
def judge_record(rec):
    # evaluate_aqa 함수를 호출하여 LLM으로부터 평가 결과와 토큰 사용량을 가져옵니다.
    eval_result, usage = evaluate_aqa(
        question=rec["question"],     # 입력받은 레코드의 질문을 할당합니다.
        answer_orig=rec["answer_orig"], # 정답지(ground truth)를 할당합니다.
        answer_llm=rec["answer_llm"]    # AI가 생성한 답변을 할당합니다.
    )

    # 평가된 결과와 원본 데이터를 조합하여 새로운 딕셔너리 구조를 생성합니다.
    result = {
        "question": rec["question"],   # 원본 질문을 그대로 저장합니다.
        "document": rec["document"],   # 답변 생성에 사용된 문서를 저장합니다.
        "score": eval_result.score,    # LLM이 판정한 점수(good/bad)를 저장합니다.
        "reasoning": eval_result.reasoning, # LLM이 작성한 평가 근거를 저장합니다.
    }

    # 최종 결과물(딕셔너리)과 호출 시 발생한 토큰 사용량(usage)을 반환합니다.
    return result, usage

이 함수가 중요한 이유는 우리가 나중에 수백 개의 데이터를 루프(loop)로 돌릴 때, judge_record(data)라고만 호출하면 알아서 점수와 근거를 척척 정리해서 반환해주기 때문입니다. 데이터의 입력과 출력 구조를 통일시켜 놓으면, 나중에 결과 분석이나 시각화를 할 때 코드가 훨씬 간결해집니다.

이 judge_record 함수가 정의됨으로써, 이제 우리는 데이터를 하나씩 집어넣기만 하면 되는 '평가 파이프라인'의 핵심 엔진을 확보하게 되었습니다. 다음 단계로는 이 함수를 활용해서 여러 개의 데이터를 일괄 처리하는 루프를 만들어보실 건가요? 어떻게 진행할지 알려주세요.
